# AI Teacher Copilot：06–07 业务驱动的 Teacher Agent 设计

## 1. 设计目标

Step 1–5 已经确定 Teacher Copilot 的业务事实、学习画像、Tools（工具）和 Skills（技能）。

Step 6–7 不再从“Memory 怎么设计”“Intent Router 怎么设计”“需要几个 Agent”出发，而是从真实教师业务出发：

> **教师提出不同复杂度的任务时，Teacher Agent 应该采用什么最低成本、最低复杂度、但能够完整完成任务的执行方式。**

本阶段采用三个核心原则：

```text
Business-Driven（业务驱动）
= 先有真实教学任务，再决定需要什么 Agent 能力

Single-Agent First（单智能体优先）
= 能由一个 Teacher Lead Agent 完成，就不升级为 Multi-Agent

Harness Reuse First（Harness 复用优先）
= Agent 执行框架优先复用 DeerFlow
= 不重新实现第二套 LangGraph Agent Runtime
```

Multi-Agent（多智能体）只在真实业务满足以下条件时启用：

```text
① Parallelism（任务可并行）
   多个子任务之间基本没有前后依赖，可以同时执行

② Context Isolation（上下文隔离）
   单次任务需要处理大量学生 / 历史数据，拆开后能显著降低主 Agent 上下文压力

③ Independent Perspective（独立专业视角）
   需要独立审核、验证或不同专业角色，而不是同一个 Agent 连续完成线性任务
```

如果以上条件都不满足，则不使用 Multi-Agent。

# 2. Teacher Agent 总体架构

整个教师侧只有一个统一入口，但这个入口不是 Teacher Copilot 自己重新创建的一套 Agent Graph，而是 DeerFlow Lead Agent 的一个教育领域 Custom Agent 配置。

```text
Teacher UI
    ↓
DeerFlow Thread / Run
    ↓
assistant_id = Lead Agent
context.agent_name = teacher-copilot
    ↓
DeerFlow Lead Agent Runtime
    ↓
加载 teacher-copilot AgentConfig + SOUL.md
    ↓
Teacher Lead Agent（教师主智能体）
```

Teacher Lead Agent 负责：

```text
理解教师请求
+
解析请求中的业务对象
+
读取必要 Memory（记忆）
+
判断任务复杂度
+
选择 Tool / Skill
+
必要时自主组合多个 Tool / Skill
+
复杂任务时通过 DeerFlow task 委派 Sub-Agent
+
汇总结果并生成最终回答
```

整体关系：

```text
                         Teacher
                           ↓
                     DeerFlow Thread
                           ↓
                  teacher-copilot
                  Teacher Lead Agent
                           │
          ┌────────────────┼────────────────┐
          ↓                ↓                ↓
       Memory            Skills           Tools
   DeerFlow Memory    DeerFlow Skills   DeerFlow Tools
          │                │                │
          └────────────────┼────────────────┘
                           │
                    根据业务复杂度
                           │
        ┌──────────────────┼──────────────────┐
        ↓                  ↓                  ↓
   Direct Tool        Tool / Skill       DeerFlow task
   （直接工具）         灵活编排          Sub-Agent Delegation
                                                │
                                   ┌────────────┼────────────┐
                                   ↓            ↓            ↓
                              Diagnosis     Practice      Reviewer
                               Worker        Worker        Agent
                                                │
                                                ↓
                                       Teacher Lead Agent
                                                ↓
                                           Final Answer
```

这里不存在一个独立的 `Intent Router Agent（意图路由智能体）`。Intent Routing（意图与任务路由）是 Teacher Lead Agent 的职责：判断当前请求应该直接调用 Tool、执行 Skill、灵活组合多个 Tool / Skill，还是通过 DeerFlow `task` 委派 Sub-Agent。

Multi-Agent 也不是 Lead Agent 后面的另一套系统：

```text
DeerFlow Teacher Lead Agent
+
按需 task 启动的 Sub-Agents
=
Teacher Multi-Agent System（教师多智能体系统）
```

## 2.1 Teacher Copilot Custom Agent 配置

当前 MVP 固定创建一个名为：

```text
teacher-copilot
```

的 DeerFlow Custom Agent。逻辑配置如下：

```yaml
name: teacher-copilot
description: AI Teacher Copilot 教师主智能体

tool_groups:
  - teacher:data
  - teacher:resource

skills:
  - student-diagnosis
  - class-learning-analysis
  - homework-review
  - differentiated-practice

allowed_subagents:
  - diagnosis-worker
  - practice-worker
  - reviewer
```

`AgentConfig` 负责声明这个 Custom Agent 可以使用的模型、Tool Groups、Skills 和 Sub-Agent 类型；`SOUL.md` 负责 Teacher Copilot 的长期角色和执行规则。

`SOUL.md` 至少固定以下规则：

```text
教师助理角色
事实优先
Business Object Resolution 规则
Single-Agent First
已有稳定 Skill 优先
Skill 未命中时允许自主 Tool Calling
只有真实收益时才能 task 委派 Sub-Agent
Memory 不能覆盖业务事实
Sub-Agent 结果需要由 Lead Agent 汇总
```

因此当前不新增：

```text
teacher_agent_graph.py
TeacherSupervisorGraph
TeacherIntentRouterGraph
```

Teacher Copilot 的 Agent Runtime 直接复用 DeerFlow `backend/packages/harness/deerflow/agents/lead_agent/agent.py` 和 Custom Agent 配置系统。

## 2.2 业务事实、画像算法与 LLM 的边界

教师侧所有学习状态统一遵守：

```text
MySQL
= 原始业务事实
        ↓
ProfileAlgorithmV1（profile_v1）
= 确定性计算 mastery / trend / weak_point / recurring_error 等画像事实
        ↓
Profile Tools
= 返回结构化派生学习事实
        ↓
Teacher Lead Agent / Skill / Sub-Agent
= 解释、比较、下钻证据、制定教学计划
```

因此 LLM 不负责重新计算 `mastery`，也不允许自行改变 `< 0.60`、`attempt_count >= 3`、最近 14/28 天等画像阈值。需要修改画像判断，只修改 Step 3–5 中的 `ProfileAlgorithmV1`。

对于某次 Homework / Question 的即时分析，同样遵循：

```text
MySQL 当前有效 Grading Facts
        ↓
AnalysisCalculationV1
= 确定性计算成绩、错误率、知识点即时表现、
  成绩分布和 Homework 即时异常候选
        ↓
Analysis Tools
├── get_homework_analysis
└── get_question_analysis
        ↓
Teacher Lead Agent / Skill / Sub-Agent
= 解释、比较、下钻、形成教学判断
```

因此 LLM 同样不负责重新计算：

```text
avg_score_rate
error_rate
avg_performance
score_distribution
HomeworkAnalysis.attention_students
```

同时：

```text
Homework / Question low_performance
≠
ProfileAlgorithmV1 weak_point
```

一次作业问题是否同时属于长期问题，必须通过 Class / Student Profile 对照判断。

## 2.3 Teacher Business Context（教师业务上下文）

教师进入 Teacher Copilot 时，运行时可以携带当前页面已经明确的业务对象。第一版只保留真正有助于参数解析的轻量信息：

```text
TeacherBusinessContext
├── teacher_id
├── class_refs[]
│   ├── class_id
│   └── class_name
│
├── current_class_id        可选
├── current_homework_id     可选
├── current_question_id     可选
│
└── current_question_refs[] 可选
    ├── question_id
    └── question_no
```

其中：

```text
class_refs
= 当前教师可访问的少量班级引用
= 用于把“八三班”等名称映射到 class_id

current_class_id / current_homework_id / current_question_id
= 当前页面已经明确的业务对象

current_question_refs
= 当前作业中的题号与 question_id 对应关系
= 用于解析“第 8 题”等表达
```

Teacher Business Context 只是运行时参数，不新增数据库业务对象，也不要求单独持久化。页面已经明确的对象直接复用，不再让 Agent 重复查询或再次询问教师。

注意：这里的 `teacher_id` 只是业务上下文信息，**不能作为 Tool 权限校验的可信身份来源**。真正的当前用户身份仍然来自已认证的 DeerFlow / Backend Runtime Context，Tool Service 必须再次校验对象权限。

## 2.4 Teacher Business Context 如何接入 DeerFlow

DeerFlow `RunCreateRequest` 已提供通用 `context` 字段，因此 Teacher UI 发起 Teacher Agent Run 时把业务上下文放入 runtime context：

```text
Teacher Page
        ↓
RunCreateRequest.context
        ↓
teacher_business_context
        ↓
DeerFlow Lead Agent Runtime
```

但仅仅把数据放进 `context` 并不代表 LLM 自动看到这些业务对象。DeerFlow 默认动态上下文中间件主要处理日期和 Memory，因此本项目新增一层很薄的：

```text
TeacherBusinessContextMiddleware
```

完整链路：

```text
Teacher Page
↓
RunCreateRequest.context.teacher_business_context
↓
TeacherBusinessContextMiddleware【本项目】
↓
将当前页面业务对象作为隐藏业务 Context 注入模型
↓
Teacher Lead Agent
```

推荐代码位置：

```text
teacher_copilot/
└── agents/
    └── middlewares/
        └── teacher_business_context.py
            └── TeacherBusinessContextMiddleware
```

通过 DeerFlow 已有配置化 Middleware 扩展点接入：

```yaml
extensions:
  middlewares:
    - teacher_copilot.agents.middlewares.teacher_business_context:TeacherBusinessContextMiddleware
```

因此不修改 DeerFlow Lead Agent 主代码，不 fork `build_middlewares()`，只利用 DeerFlow 已提供的 extension middleware 机制。

边界固定为：

```text
Teacher Business Context
= 帮助 LLM 理解当前页面 / 当前作业 / 当前题

≠ 授权事实
```

即使前端传来的业务 Context 被篡改，Teacher Tool 仍然需要通过 Runtime 中的可信身份执行权限检查。

## 2.5 Business Object Resolution（业务对象解析）与 DeerFlow HITL

Teacher Agent 的正式业务 Tool 仍然使用明确的 `student_id / class_id / homework_id / question_id`。Teacher Lead Agent 在调用正式 Tool / Skill 前完成轻量解析。

解析顺序固定为：

```text
Teacher Query
        ↓
Teacher Business Context
        ↓
当前 Context 能否直接确定？
├── Yes → 使用真实业务 ID
└── No
     ↓
必要时调用对象发现 Tool
├── list_class_students
└── list_class_homeworks
     ↓
能否唯一确定？
├── Yes → 使用真实业务 ID
└── No  → DeerFlow ask_clarification
             ↓
           教师选择
             ↓
           使用确认后的业务 ID
```

例如：

```text
教师：
“分析一下张三最近数学情况。”

current_class_id = class_03
↓
list_class_students(class_03)
↓
匹配 name = 张三
↓
唯一结果 → student-diagnosis
多个候选 → ask_clarification
```

“第 8 题”优先使用：

```text
current_homework_id
+
current_question_refs(question_no = 8)
→ question_id
```

HITL 直接复用 DeerFlow：

```text
Teacher Lead Agent
        ↓
ask_clarification【DeerFlow builtin Tool】
        ↓
ClarificationMiddleware【DeerFlow】
        ↓
Human Input Request / Interrupt
        ↓
DeerFlow Human Input UI / Card
        ↓
教师选择
        ↓
Resume 当前 Thread / Run
        ↓
继续正式 Tool / Skill
```

因此当前不新增：

```text
TeacherClarificationModal
TeacherHITLService
TeacherInterruptProtocol
Entity Resolution Agent / Skill / Tool
```

对象解析遵循：

```text
Context First（上下文优先）
Unique Match First（唯一匹配直接继续）
Clarify on Ambiguity（存在歧义才询问）
Never Guess ID（禁止猜测业务 ID）
```

# 3. 业务复杂度驱动的执行层级

Teacher Lead Agent 不把所有请求都套进固定 Workflow。

| 层级 | 典型业务 | 执行方式 |
|---|---|---|
| L1 | 查询一个明确事实 / 业务对象列表 | Direct Tool（直接工具） |
| L2 | 一个已有标准教学任务 | Single Skill（单技能） |
| L3 | 没有现成 Skill，但多个 Tool 可以完成 | Adaptive Multi-Tool（自主多工具） |
| L4 | 一个 Skill 完成主体，额外需要 Tool | Skill + Tool（技能 + 工具组合） |
| L5 | 一个请求包含多个串行教学任务 | Multi-Skill（多技能组合，仍是单 Agent） |
| L6 | 大量独立对象需要批量分析 / 生成 | DeerFlow `task` → Parallel Sub-Agents |
| L7 | 大型高价值结果需要独立复核 | `task(subagent_type="reviewer")` |

核心原则：

```text
L1–L5
默认由 Teacher Lead Agent 完成

L6–L7
只有真实存在并行、上下文隔离、专业能力或独立审核价值时
才通过 DeerFlow task 升级为 Multi-Agent
```

业务对象解析为了补齐参数而额外调用列表 Tool / `ask_clarification`，不参与 L1–L7 的复杂度升级判断。

# 4. 场景一：明确事实 / 对象查询 → Direct Tool

## 4.1 真实业务

```text
“八三班这次数学作业完成率是多少？”
“张三现在最薄弱的三个知识点是什么？”
“第 8 题错误率是多少？”
“八三班有哪些学生？”
“八三班这周有哪些数学作业？”
```

## 4.2 执行方式

```text
Teacher
↓
Teacher Lead Agent
↓
解析必要业务对象
↓
对应 Tool
↓
Answer
```

例如：

```text
完成率 → get_homework_analysis
学生薄弱知识点 → get_student_profile
第 8 题错误率 → get_question_analysis
班级学生名单 → list_class_students
时间范围作业 → list_class_homeworks
```

## 4.3 为什么不需要 Skill / Multi-Agent

一个正式业务 Tool 已经能够返回完整事实，因此遵循：

> **Single Tool First（单工具优先）。**

即使为了把“张三”解析成 `student_id` 先调用了 `list_class_students`，教师真正要求的仍是一个画像事实查询，仍属于 L1，而不是因为出现两个 Tool Call 就机械升级 L3。

# 5. 场景二：标准教学任务 → Single Skill

## 5.1 真实业务

```text
“帮我分析一下张三最近数学学习情况，看看主要问题是什么。”
```

这个任务需要长期画像 + 历史作答证据 + 诊断解释。

## 5.2 执行方式

```text
Teacher
↓
Teacher Lead Agent
↓
student-diagnosis
↓
get_student_profile
+
get_student_grading_history
↓
诊断结果
```

同类业务：

```text
“分析一下八三班长期学情。”
→ class-learning-analysis

“分析一下这次作业应该怎么讲评。”
→ homework-review

“给班里不同水平学生安排练习。”
→ differentiated-practice
```

## 5.3 为什么仍然只需要一个 Agent

一个稳定 Skill 已经能够完整完成业务任务，所以：

```text
Teacher Lead Agent + 一个 Skill
```

比新增专业 Agent 更简单、更便宜，也更容易评测。

# 6. 场景三：Skill 未命中 → Adaptive Multi-Tool

## 6.1 真实业务

```text
“张三和李四在数学上的主要差异是什么？谁现在更需要重点关注？”
```

当前没有 `compare-two-students` 固定 Skill，也不应该为所有问法都创建 Skill。

## 6.2 执行方式

```text
Teacher Lead Agent
        ↓
get_student_profile（张三）
        ↓
get_student_profile（李四）
        ↓
根据中间结果判断证据是否足够
        ↓
必要时继续：
get_student_grading_history（张三）
get_student_grading_history（李四）
        ↓
综合比较
        ↓
Answer
```

Skill 未命中不等于 Agent 无法完成任务；Teacher Lead Agent 保留自主 Tool Calling 能力。

# 7. 场景四：Skill + Tool 灵活组合

## 7.1 真实业务

```text
“分析一下这次作业应该重点讲哪些问题，
再给最需要讲的三个知识点各找几道类似题。”
```

前半部分属于 `homework-review`，后半部分属于 `search_question_bank`。

## 7.2 执行方式

```text
Teacher Lead Agent
        ↓
homework-review
        ↓
得到高错题 / 本次低表现 / 长期薄弱 / 讲评优先级
        ↓
search_question_bank
        ↓
最终回答
```

Skill 是稳定业务能力块，不锁死 Agent 后续流程。

# 8. 场景五：多个 Skill 串行组合 → 仍然 Single-Agent

## 8.1 真实业务

```text
“分析这次作业的问题，然后根据班级情况给学生安排分层练习。”
```

包含：

```text
Task A = homework-review
Task B = differentiated-practice
```

## 8.2 执行方式

```text
Teacher Lead Agent
        ↓
homework-review
        ↓
differentiated-practice
        ↓
Answer
```

## 8.3 为什么这里不使用 Multi-Agent

这是明显线性依赖 `A → B`。拆成两个 Agent 没有并行收益，只增加上下文交接、延迟、成本和错误传播。

因此采用：

> **Multi-Skill Composition（多技能组合），而不是 Multi-Agent。**

DeerFlow `task` 的真实设计同样明确：不能仅因为任务复杂、多步骤或内容较长就委派 Sub-Agent。

# 9. 场景六：班级周度学情复盘 → Parallel Diagnosis Sub-Agents

这是当前阶段最核心、最自然的 Multi-Agent 业务之一。

## 9.1 真实业务

```text
“帮我做一下八三班这周数学的整体复盘。
看看全班主要薄弱点，重点关注哪些学生，
每个重点学生具体是什么问题，
最后形成下周教学重点。”
```

如果全班学生都由 Lead Agent 串行深入分析，会出现执行时间长、主 Agent 上下文过大、不同学生历史互相挤占上下文的问题；而不同学生的诊断基本独立。

## 9.2 Lead Agent 先完成全局筛选

```text
Teacher Lead Agent
        ↓
list_class_homeworks
        ↓
得到本周 homework_id 列表
        ↓
逐份 get_homework_analysis
+
get_class_profile
        ↓
获得：
A. ClassProfile.attention_students（长期）
B. 各 HomeworkAnalysis.attention_students（本周即时）
        ↓
综合长期 + 本周多份作业异常的一致性 / 严重程度
        ↓
weekly_attention_students
        ↓
只选择真正需要深度诊断的学生
```

三层对象必须保持区分：

```text
ClassProfile.attention_students
= 长期画像关注学生

HomeworkAnalysis.attention_students
= 单次作业即时异常候选

weekly_attention_students
= Lead Agent 综合长期画像 + 本周多份作业后形成的周度业务结果
```

不是一开始就把全班所有学生全部交给 Sub-Agent。

## 9.3 DeerFlow 实际执行：并行 task 调用

假设筛选出 12 个重点学生，按照每个 Worker 4 人分成 3 个独立批次：

```text
Teacher Lead Agent
        ↓
同一轮产生 3 个独立 task Tool Call
        │
        ├── task(
        │     description="诊断重点学生 A-D",
        │     prompt="...",
        │     subagent_type="diagnosis-worker"
        │   )
        │
        ├── task(... diagnosis-worker ...)
        │
        └── task(... diagnosis-worker ...)
        ↓
DeerFlow SubagentLimitMiddleware / Sub-Agent Runtime
        ↓
并行执行 Diagnosis Workers
        ↓
每个 Worker 执行 student-diagnosis
        ↓
返回结构化结果
        ↓
Teacher Lead Agent Fan-in
        ↓
班级周度学情复盘
```

当前不自己实现：

```text
asyncio.gather Worker 调度层
自定义 Semaphore
自定义 Agent WorkerPool
自定义 Sub-Agent 生命周期管理
```

这些 Harness 能力直接复用 DeerFlow `task` + Subagent Runtime。

## 9.4 为什么这里值得 Multi-Agent

```text
Parallelism
= 学生 A 的诊断不依赖学生 B

Context Isolation
= 每个 Diagnosis Worker 只处理自己的学生和历史

Specialization
= diagnosis-worker 有更窄的 Tool / Skill / Prompt 边界
```

这里的 Multi-Agent 是由真实班级规模和上下文压力自然产生，而不是为了展示架构人工拆角色。

# 10. 场景七：班级诊断 + 分层练习包 → 两阶段 Fan-out / Fan-in

## 10.1 真实业务

```text
“帮我把八三班这周数学学习情况完整复盘一下，
找出主要问题和重点学生，
并根据学生水平生成下周分层练习。”
```

业务目标包括班级整体分析、重点学生深度诊断、学生分层和不同层级练习生成。

## 10.2 数据准备

```text

        ↓

        ↓
get_homework_analysis（逐份）
+
get_class_profile
        ↓

        ↓
筛选重点学生
```

```text

        ↓
多个并行 task(subagent_type="diagnosis-worker")
```

# 11. 场景八：全班个性化练习生成 → Practice Workers

## 11.1 真实业务

# 12. 场景九：大型教学方案 → Reviewer Agent 独立审核

Multi-Agent 的价值不只来自并行，也可以来自 Independent Perspective（独立视角）。

## 12.1 真实业务

系统完成：

```text
班级诊断
+
重点学生判断
+
学生分层
+
分层 / 个性化练习
```

这类大型方案影响实际教学安排，可以按需独立审核。

## 12.2 Reviewer 不重新生成方案

Reviewer 只负责检查：

```text
重点学生是否有数据依据
长期薄弱判断是否有足够历史证据
练习知识点是否对应真实薄弱知识点
题目难度是否与学生层级匹配
是否存在结论与 Profile / Analysis 事实冲突
是否遗漏明显需要关注的学生
```

## 12.3 DeerFlow 实际执行

```text
Teacher Lead Agent
        ↓
生成完整教学方案
        ↓
task(
  description="审核教学方案",
  prompt="...",
  subagent_type="reviewer"
)
        ↓
Reviewer 独立读取必要事实
        ↓
返回 pass / warnings / issues
        ↓
Teacher Lead Agent
        ↓
必要时修正
        ↓
最终方案
```

Reviewer 默认不用于普通事实查询、单学生简单诊断和普通作业分析。

# 13. 场景十：教师长期偏好 → DeerFlow Memory

Memory 同样从真实业务产生，而不是为了 Agent 架构单独建设。

## 13.1 真实业务

教师明确表达：

```text
“以后给我做作业分析的时候，
先告诉我最值得课堂讲的三个问题，
不用写太长。”
```

这是稳定教师偏好，不是学生业务事实。

下次教师只说：

```text
“帮我看看今天这次作业。”
```

系统可以读取 Teacher Memory，然后仍然通过 Tool 获取最新业务事实，最后按照教师偏好组织回答。

## 13.2 Memory 当前保存内容

当前阶段保留三类：

```text
Teacher Preference（教师偏好）
├── 回答长短偏好
├── 分析粒度偏好
└── 结果展示方式偏好

Teaching Style（教学风格）
├── 偏重基础讲解
├── 偏重启发式教学
├── 偏重错题复盘
└── 偏重分层训练

Teaching Decision Context（教学决策上下文）
├── “近期重点关注张三”这类持续关注意图
├── “近期把某知识点作为重点”这类教学策略倾向
└── “这个班近期多安排基础练习”这类策略上下文
```

这里将原来的 `Teaching Decision` 明确限定成 `Teaching Decision Context`：它是长期策略上下文，不是正式可审计的业务记录。

如果未来需要保存：

```text
已正式布置某个干预方案
已执行某个教学决策
某学生已加入正式干预计划
```

则应新增 MySQL 业务对象 / 表，而不是只保存在 Memory。

## 13.3 Memory 不能作为哪些事实的来源

```text
学生成绩
知识点掌握度
薄弱知识点
重复错误统计
作业完成率
题目错误率
GradingResult
Student Profile
Class Profile
Homework Analysis
Question Analysis
```

都必须通过 Tool 从 MySQL / Profile 中读取。

核心边界：

```text
MySQL / Profile
= 客观业务事实与可重算学习状态

Tool
= 访问业务事实

Skill
= 完成稳定教学任务的方法

DeerFlow Memory
= 教师长期上下文
```

> **Memory 可以改变回答方式和教学策略偏好，但不能改变业务事实。**

# 15. Sub-Agent 类型与 DeerFlow Config

当前不按照“学生 A Agent / 学生 B Agent”创建大量 Agent 类型，只定义少量稳定 Worker 类型，再按任务动态启动多个实例。

DeerFlow `CustomSubagentConfig` 已支持：

```text
description
system_prompt
tools
disallowed_tools
skills
model
max_turns
timeout_seconds
```

因此 Worker 的能力边界直接通过 DeerFlow Config 限制，而不是只靠 Prompt 约定。

## 15.1 Diagnosis Worker

逻辑配置：

```yaml
subagents:
  custom_agents:
    diagnosis-worker:
      description: 对分配的学生集合执行深度学习诊断
      system_prompt: 你是学习诊断子智能体，只处理分配给你的学生诊断任务。
      tools:
        - get_student_profile
        - get_student_grading_history
      skills:
        - student-diagnosis
      disallowed_tools:
        - task
        - ask_clarification
        - present_files
```

职责：读取 ProfileAlgorithmV1 已确定的长期画像、使用 Grading History 举证薄弱 / 重复错误 / 趋势；不负责班级整体决策、练习生成、最终教师回答，也不继续创建 Sub-Agent。

## 15.2 Practice Worker

```yaml
subagents:
  custom_agents:
    practice-worker:
      description: 对分配的学生组或学生批次生成针对性练习
      system_prompt: 你是分层与个性化练习设计子智能体。
      tools:
        - get_student_profile
        - get_class_profile
        - search_question_bank
      skills:
        - differentiated-practice
      disallowed_tools:
        - task
        - ask_clarification
        - present_files
```

Practice Worker 接收 Lead Agent 已经分配好的学生组 / 学生批次，因此不需要自己再次调用 `list_class_students`。

## 15.3 Reviewer Agent

```yaml
subagents:
  custom_agents:
    reviewer:
      description: 独立审核大型教学方案的事实一致性和练习匹配合理性
      system_prompt: 你是教学方案审核智能体，只做独立检查，不重新生成整个方案。
      tools:
        - get_class_profile
        - get_student_profile
        - get_student_grading_history
        - get_homework_analysis
        - get_question_analysis
        - search_question_bank
      disallowed_tools:
        - task
        - ask_clarification
        - present_files
```

Reviewer 只读取必要事实，不修改业务数据，也不继续委派新的 Agent。

当前 DeerFlow 自定义 Sub-Agent 的默认 deny 本身已经包含 `task / ask_clarification / present_files`；本项目在配置示例中继续显式写出，是为了让文档中的业务边界一眼可见。

# 16. Agent / Skill / Tool 最终关系

```text
Agent（智能体）
= 理解目标、动态决策、调用能力或执行专业任务

Skill（技能）
= 已验证、可复用的教学任务 SOP

Tool（工具）
= 真正查询、计算或检索业务数据的原子能力
```

Teacher Lead Agent 可以自主选择 Tool / Skill、根据中间结果继续追加 Tool、组合多个 Skill、决定是否 `task` 委派 Sub-Agent。

Sub-Agent 任务范围更窄、上下文更隔离、Tool / Skill 权限更受限，只完成 Lead Agent 分配的边界清晰任务。

稳定教学任务优先走 Skill；不存在匹配 Skill 时，Lead Agent 可以自主组合 Tool。

# 18. Multi-Agent 触发规则

Teacher Lead Agent 默认不启用 Multi-Agent。只有出现以下任一**真实收益**时才考虑 DeerFlow `task`：

```text
A. Independent Parallelism
= 存在多个彼此独立、可真正并行的对象 / 子任务

B. Specialist Capability
= 某个专门 Sub-Agent 拥有明显更合适的 Tool / Skill / Prompt / Model 能力

C. Context Isolation
= 单任务上下文很重，拆分后可以明显保护主 Agent Context

D. Independent Review
= 高价值结果需要独立 Reviewer 第二视角
```

明确不是触发条件：

```text
“任务步骤很多”
“任务很复杂”
“回答会很长”
“涉及多个 Tool”
```

业务示例：

```text
单学生诊断
→ Lead Agent + student-diagnosis

普通作业讲评
→ Lead Agent + homework-review

作业分析 + 分层练习
→ Lead Agent 串行两个 Skill
→ 不使用 Multi-Agent

10+ 个重点学生深度诊断
→ 并行 task(diagnosis-worker)

全班个性化练习
→ list_class_students
→ 并行 task(practice-worker)

大型班级教学方案
→ 按需 task(reviewer)
```

# 19. Multi-Agent 成本控制原则

## 19.1 先筛选再 Fan-out

不要：

```text
40 个学生
↓
直接启动 40 个 Agent
```

应该：

```text
Lead Agent
↓
list_class_homeworks + get_homework_analysis + get_class_profile
↓
先识别真正需要深度诊断的重点学生
↓
再 task Fan-out
```

## 19.2 Worker 处理批次，而不是默认一人一个 Agent

例如 12 个重点学生：

```text
3 个 Diagnosis Worker × 每个 4 人
```

全班个性化练习也先通过 `list_class_students` 获取成员，再按批次分配多个 Practice Worker。

## 19.3 Sub-Agent 不递归委派

当前通过 `CustomSubagentConfig.disallowed_tools` 禁止 Worker 使用 `task`，从运行时约束而不是只靠 Prompt 防止递归 Agent 树。

## 19.4 Reviewer 按需启动

Reviewer 只用于大型、高价值或教师明确要求审核的任务。

## 19.5 当前 MVP 使用 task，Durable Batch 留作后续扩展

当前 30～40 人班级的周度诊断和个性化练习，默认使用 DeerFlow 普通并行 `task`：

```text
当前 MVP
→ parallel task calls
→ SubagentLimitMiddleware 控制并发 / 总委派量
→ Sub-Agent Runtime 执行
```

当前不把 DeerFlow `batch_task` 设为主路径，因为 durable batch 会引入当前比赛规模不需要的持久化批任务复杂度。

未来满足以下情况时再评估：

```text
100+ 独立对象
任务需要 Gateway 重启后继续
教师不需要一直在线等待
需要真正 durable batch 生命周期
```

此时可以：

```text
parallel task
→ 升级为 DeerFlow batch_task
```

而不改变 Tool / Skill / Worker 的业务 Contract。

# 20. Memory 的读写责任与 DeerFlow 实现

当前阶段直接复用 DeerFlow Memory Runtime，不新增 `remember_teacher_preference` / `save_memory` 等 Teacher 专属 Memory Tool。

当前 MVP 决策：

```text
memory.mode = middleware
```

运行链路：

```text
Teacher Conversation
        ↓
DeerFlow MemoryMiddleware
        ↓
本轮结束后 enqueue conversation
        ↓
MemoryManager
        ↓
长期 Teacher Memory
        ↓
后续会话由 DeerFlow Dynamic Context / Memory Runtime 注入相关记忆
```

因此不再写成“Teacher Lead Agent 自己在每轮结束后决定是否写 Memory”。长期记忆的抽取与持久化使用 DeerFlow Memory Runtime；Teacher Copilot 负责通过 Prompt / Memory 规则限制什么信息值得长期保存。

Sub-Agent 默认不直接管理长期 Memory。如果 Sub-Agent 需要教师偏好或教学风格，由 Lead Agent 把当前任务必要的 Memory Context 一起放入 `task.prompt` / 子任务上下文；Worker 不直接写长期 Memory。

这样避免多个 Worker 重复写 Memory、偏好冲突以及业务分析结论被错误沉淀成事实。
