# AI Teacher Copilot：06–07 业务驱动的 Teacher Agent 设计

## 1. 设计目标

Step 1–5 已经确定 Teacher Copilot 的业务事实、学习画像、Tools（工具）和 Skills（技能）。

Step 6–7 不再从“Memory 怎么设计”“Intent Router 怎么设计”“需要几个 Agent”出发，而是从真实教师业务出发：

> **教师提出不同复杂度的任务时，Teacher Agent 应该采用什么最低成本、最低复杂度、但能够完整完成任务的执行方式。**

本阶段采用四个核心原则：

```text
Business-Driven（业务驱动）
= 先有真实教学任务，再决定需要什么 Agent 能力

Single-Agent First（单智能体优先）
= 能由一个 Teacher Lead Agent 完成，就不升级为 Multi-Agent

Harness Reuse First（Harness 复用优先）
= Agent 执行框架优先复用 DeerFlow
= 不重新实现第二套 LangGraph Agent Runtime

Screening Before Delegation（先筛查，再委派）
= 全班学生状态的第一轮发现
  由 ProfileAlgorithmV1 / AnalysisCalculationV1
  的确定性结果完成

= 不使用 Sub-Agent 判断“谁可能有问题”

= 只有已经明确存在多个需要
  Deep Diagnosis 的 student_id，才升级 Diagnosis Workers
```

Multi-Agent（多智能体）只在真实业务满足以下条件时启用：

```text
① Parallelism（任务可并行）
   多个子任务之间基本没有前后依赖，可以同时执行

② Context Isolation（上下文隔离）
   单次任务需要处理大量学生 / 历史数据，拆开后能显著降低主 Agent 上下文压力

③ Independent Perspective（独立专业视角）
   需要独立审核、验证或不同专业角色，而不是同一个 Agent 连续完成线性任务
```

如果以上条件都不满足，则不使用 Multi-Agent。

# 2. Teacher Agent 总体架构

Teacher Agent Runtime 只有一个统一的教师侧 AI 执行入口 `teacher-copilot`，但教师产品 UI 不是单页面。Teacher Dashboard、Class Detail、Student Profile、Homework Authoring、Homework Analysis 等页面负责直接展示和操作教育业务数据；这些页面需要 AI 对话、分析或教学规划能力时，统一进入 Teacher Copilot / DeerFlow Thread，而不是为每个业务页面创建独立 Agent。

```text
Teacher Business Page / Teacher Copilot Chat
        │
        │ 发起 AI 请求时
        ↓
DeerFlow Thread / Run
    ↓
assistant_id = Lead Agent
context.agent_name = teacher-copilot
    ↓
DeerFlow Lead Agent Runtime
    ↓
加载 teacher-copilot AgentConfig + SOUL.md
    ↓
Teacher Lead Agent（教师主智能体）
```

Teacher Lead Agent 负责：

```text
理解教师请求
+
解析请求中的业务对象
+
读取必要 Memory（记忆）
+
判断任务复杂度
+
选择 Tool / Skill
+
必要时自主组合多个 Tool / Skill
+
复杂任务时通过 DeerFlow task 委派 Sub-Agent
+
汇总结果并生成最终回答
```

整体关系：

```text
                         Teacher
                           ↓
                     DeerFlow Thread
                           ↓
                  teacher-copilot
                  Teacher Lead Agent
                           │
          ┌────────────────┼────────────────┐
          ↓                ↓                ↓
       Memory            Skills           Tools
   DeerFlow Memory    DeerFlow Skills   DeerFlow Tools
          │                │                │
          └────────────────┼────────────────┘
                           │
                    根据业务复杂度
                           │
        ┌──────────────────┼──────────────────┐
        ↓                  ↓                  ↓
   Direct Tool        Tool / Skill       DeerFlow task
   （直接工具）         灵活编排          Sub-Agent Delegation
                                                │
                                     ┌──────────┴──────────┐
                                     ↓                     ↓
                                Diagnosis          Consistency
                                 Worker              Reviewer
                                     │                     │
                                     └──────────┬──────────┘
                                                ↓
                                       Teacher Lead Agent
                                                ↓
                                           Final Answer
```

这里不存在一个独立的 `Intent Router Agent（意图路由智能体）`。Intent Routing（意图与任务路由）是 Teacher Lead Agent 的职责：判断当前请求应该直接调用 Tool、执行 Skill、灵活组合多个 Tool / Skill，还是通过 DeerFlow `task` 委派 Sub-Agent。

Multi-Agent 也不是 Lead Agent 后面的另一套系统：

```text
DeerFlow Teacher Lead Agent
+
按需 task 启动的 Sub-Agents
=
Teacher Multi-Agent System（教师多智能体系统）
```

## 2.1 Teacher Copilot Custom Agent 配置

当前 MVP 固定创建一个名为：

```text
teacher-copilot
```

的 DeerFlow Custom Agent。逻辑配置如下：

```yaml
name: teacher-copilot
description: AI Teacher Copilot 教师主智能体
model: deepseek-v4-flash

tool_groups:
  - teacher:data
  - teacher:resource

skills:
  - student-diagnosis
  - class-learning-analysis
  - homework-review

allowed_subagents:
  - diagnosis-worker
  - consistency-reviewer
```

`AgentConfig` 负责声明这个 Custom Agent 可以使用的模型、Tool Groups、Skills 和 Sub-Agent 类型；`SOUL.md` 负责 Teacher Copilot 的长期角色和执行规则。

`SOUL.md` 至少固定以下规则：

```text
教师助理角色
事实优先
Business Object Resolution 规则
Single-Agent First
已有稳定 Skill 优先
Skill 未命中时允许自主 Tool Calling
只有真实收益时才能 task 委派 Sub-Agent
Memory 不能覆盖业务事实
Sub-Agent 结果需要由 Lead Agent 汇总
```

因此当前不新增：

```text
teacher_agent_graph.py
TeacherSupervisorGraph
TeacherIntentRouterGraph
```

Teacher Copilot 的 Agent Runtime 直接复用 DeerFlow `backend/packages/harness/deerflow/agents/lead_agent/agent.py` 和 Custom Agent 配置系统。

## 2.2 业务事实、画像算法与 LLM 的边界

教师侧所有学习状态统一遵守：

```text
MySQL
= 原始业务事实
        ↓
ProfileAlgorithmV1（profile_v1）
= 确定性计算 mastery / trend / weak_point / recurring_error 等画像事实
        ↓
Profile Tools
= 返回结构化派生学习事实
        ↓
Teacher Lead Agent / Skill / Sub-Agent
= 解释、比较、下钻证据、制定教学计划
```

因此 LLM 不负责重新计算 `mastery`，也不允许自行改变 `< 0.60`、`attempt_count >= 3`、最近 14/28 天等画像阈值。需要修改画像判断，只修改 Step 3–5 中的 `ProfileAlgorithmV1`。

对于某次 Homework / Question 的即时分析，同样遵循：

```text
MySQL 当前有效 Grading Facts
        ↓
AnalysisCalculationV1
= 确定性计算成绩、错误率、知识点即时表现、
  成绩分布和 Homework 即时异常候选
        ↓
Analysis Tools
├── get_homework_analysis
└── get_question_analysis
        ↓
Teacher Lead Agent / Skill / Sub-Agent
= 解释、比较、下钻、形成教学判断
```

因此 LLM 同样不负责重新计算：

```text
avg_score_rate
error_rate
avg_performance
score_distribution
HomeworkAnalysis.attention_students
```

同时：

```text
Homework / Question low_performance
≠
ProfileAlgorithmV1 weak_point
```

一次作业问题是否同时属于长期问题，必须通过 Class / Student Profile 对照判断。

## 2.5 Business Object Resolution（业务对象解析）与 DeerFlow HITL

Teacher Agent 的正式业务 Tool 仍然使用明确的 `student_id / class_id / homework_id / question_id`。Teacher Lead Agent 在调用正式 Tool / Skill 前完成轻量解析。

解析顺序固定为：

```text
Teacher Query
        ↓
必要时调用对象发现 Tool
├── list_classes
├── list_class_students
└── list_class_homeworks
     ↓
能否唯一确定？
├── Yes → 使用真实业务 ID
└── No  → DeerFlow ask_clarification
             ↓
           教师选择
             ↓
           使用确认后的业务 ID
```

例如：

```text
教师：
“分析一下八三班张三最近数学情况。”

list_classes(“八三班”)
↓
class_03
↓
list_class_students(class_03)
↓
匹配 name = 张三
↓
唯一结果 → student-diagnosis
多个候选 → ask_clarification
```

“第 8 题”需要教师说明是哪份作业：

```text
“八三班最近这次数学作业的第 8 题错误率是多少？”
↓
list_class_homeworks(class_03, math)
↓
确定 homework_id
↓
question_no = 8
→ question_id
```

学科同样属于“调用工具前要先确定”的参数：查学生画像、班级画像与搜题库都必须给出学科。

```text
教师提问里说明了学科
→ 按教师说的

提问里提到具体某份作业 / 题目
→ 按该作业自带的学科（Homework.subject）

两者都没有
→ 按数学处理，并在回答里写明“按数学看”
```

HITL 直接复用 DeerFlow：

```text
Teacher Lead Agent
        ↓
ask_clarification【DeerFlow builtin Tool】
        ↓
ClarificationMiddleware【DeerFlow】
        ↓
Human Input Request / Interrupt
        ↓
DeerFlow Human Input UI / Card
        ↓
教师选择
        ↓
Resume 当前 Thread / Run
        ↓
继续正式 Tool / Skill
```

因此当前不新增：

```text
TeacherClarificationModal
TeacherHITLService
TeacherInterruptProtocol
Entity Resolution Agent / Skill / Tool
```

Figma 中的 Clarification Card 只表示 DeerFlow Human Input UI / Card 在 Teacher Copilot 产品中的视觉与交互形态。实现时仍直接复用 DeerFlow Human Input / Interrupt / Resume 链路，不因为 Figma 中出现该卡片而新增 `TeacherClarificationModal`。

对象解析遵循：

```text
Unique Match First（唯一匹配直接继续）
Clarify on Ambiguity（存在歧义才询问）
Never Guess ID（禁止猜测业务 ID）
```

## 2.6 Teacher UI / DeerFlow Frontend 复用边界

Teacher 产品前端分为两类：

```text
A. Teacher Business Pages
- 01 · Teacher Dashboard
- 02 · Class Detail
- 03 · Student Profile
- 04 · Homework Authoring
- 05 · Homework Analysis
- 09 · Class Overview

B. Teacher Agent Chat
- 06 · Teacher Copilot Chat

C. Student Pages
- 07 · Student Homework
- 08 · Student Grading

D. 通用
- 10 · Login & Demo
```

A 类页面：

```text
→ 复用 DeerFlow Workspace Shell / Sidebar / 通用 UI primitives
→ 教育业务内容由 Teacher Copilot 实现
→ 通过普通 Business API 访问 Service
```

这些页面不是为了“复用 DeerFlow”而强行变成 Chat；ClassProfile、StudentProfile、HomeworkAnalysis 等仍然通过普通业务 API 读取。

B 类页面：

```text
→ 高度复用 DeerFlow ChatPage / Message Timeline / InputBox / Thread / Streaming
→ HITL 复用 DeerFlow Human Input UI
→ Sub-Agent 执行过程优先复用 DeerFlow 已有 Sub-Agent / Background Task 展示能力
```

Teacher Copilot 的历史会话继续属于 DeerFlow Thread 生命周期。教师可以通过 Workspace Sidebar 中的“最近聊天”重新进入此前的 Teacher Copilot Thread，并继续已有对话。“最近聊天”是已有 Thread History 在教师产品中的入口和展示形式，不改变当前 Teacher Agent 的 Runtime 结构；具体历史列表查询、导航和恢复方式在实现阶段优先基于 DeerFlow 当时已有能力确定。

当前不建设以下独立产品页面：

```text
Agent Management
Sub-Agent Management
Memory Management
Skill Management
```

这些属于 Agent Runtime / Harness 能力，不是当前教师业务产品的信息架构。

# 3. 业务复杂度驱动的执行层级

Teacher Lead Agent 不把所有请求都套进固定 Workflow。

| 层级 | 典型业务 | 执行方式 |
|---|---|---|
| L1 | 查询一个明确事实 / 业务对象列表 | Direct Tool（直接工具） |
| L2 | 一个已有标准教学任务 | Single Skill（单技能） |
| L3 | 没有现成 Skill，但多个 Tool 可以完成 | Adaptive Multi-Tool（自主多工具） |
| L4 | 一个 Skill 完成主体，额外需要 Tool | Skill + Tool（技能 + 工具组合） |
| L5 | 一个请求包含多个串行教学任务 | Multi-Skill（多技能组合，仍是单 Agent） |
| L6 | 多个学生需要分别进行 Deep Diagnosis | DeerFlow `task` → Parallel Diagnosis Workers |
| L7 | 完整班级周度复盘需要独立一致性审核 | `task(subagent_type="consistency-reviewer")` |

核心原则：

```text
L1–L5
默认由 Teacher Lead Agent 完成

L6–L7
只有真实存在并行、上下文隔离、专业能力或独立审核价值时
才通过 DeerFlow task 升级为 Multi-Agent
```

业务对象解析为了补齐参数而额外调用列表 Tool / `ask_clarification`，不参与 L1–L7 的复杂度升级判断。

# 4. 场景一：明确事实 / 对象查询 → Direct Tool

## 4.1 真实业务

```text
“八三班这次数学作业完成率是多少？”
“张三现在最薄弱的三个知识点是什么？”
“第 8 题错误率是多少？”
“八三班有哪些学生？”
“八三班这周有哪些数学作业？”
```

## 4.2 执行方式

```text
Teacher
↓
Teacher Lead Agent
↓
解析必要业务对象
↓
对应 Tool
↓
Answer
```

例如：

```text
完成率 → get_homework_analysis
学生薄弱知识点 → get_student_profile
第 8 题错误率 → get_question_analysis
班级学生名单 → list_class_students
时间范围作业 → list_class_homeworks
```

## 4.3 为什么不需要 Skill / Multi-Agent

一个正式业务 Tool 已经能够返回完整事实，因此遵循：

> **Single Tool First（单工具优先）。**

即使为了把“张三”解析成 `student_id` 先调用了 `list_class_students`，教师真正要求的仍是一个画像事实查询，仍属于 L1，而不是因为出现两个 Tool Call 就机械升级 L3。

---

# 5. 场景二：标准教学任务 → Single Skill

## 5.1 真实业务

```text
“帮我分析一下张三最近数学学习情况，看看主要问题是什么。”
```

这个任务需要长期画像 + 历史作答证据 + 诊断解释。

## 5.2 执行方式

```text
Teacher
↓
Teacher Lead Agent
↓
student-diagnosis
↓
get_student_profile
+
get_student_grading_history
↓
诊断结果
```

同类业务：

```text
“分析一下八三班长期学情。”
→ class-learning-analysis

“分析一下这次作业应该怎么讲评。”
→ homework-review
```

## 5.3 为什么仍然只需要一个 Agent

一个稳定 Skill 已经能够完整完成业务任务，所以：

```text
Teacher Lead Agent + 一个 Skill
```

比新增专业 Agent 更简单、更便宜，也更容易评测。

---

# 6. 场景三：Skill 未命中 → Adaptive Multi-Tool

## 6.1 真实业务

```text
“张三和李四在数学上的主要差异是什么？谁现在更需要重点关注？”
```

当前没有 `compare-two-students` 固定 Skill，也不应该为所有问法都创建 Skill。

## 6.2 执行方式

```text
Teacher Lead Agent
        ↓
get_student_profile（张三）
        ↓
get_student_profile（李四）
        ↓
根据中间结果判断证据是否足够
        ↓
必要时继续：
get_student_grading_history（张三）
get_student_grading_history（李四）
        ↓
综合比较
        ↓
Answer
```

Skill 未命中不等于 Agent 无法完成任务；Teacher Lead Agent 保留自主 Tool Calling 能力。

---

# 7. 场景四：Skill + Tool 灵活组合

## 7.1 真实业务

```text
“分析一下这次作业应该重点讲哪些问题，
再给最需要讲的三个知识点各找几道类似题。”
```

前半部分属于 `homework-review`，后半部分属于 `search_question_bank`。

## 7.2 执行方式

```text
Teacher Lead Agent
        ↓
homework-review
        ↓
得到高错题 / 本次低表现 / 长期薄弱 / 讲评优先级
        ↓
search_question_bank
        ↓
最终回答
```

Skill 是稳定业务能力块，不锁死 Agent 后续流程。

---

# 8. 场景五：多个 Skill 串行组合 → 仍然 Single-Agent

## 8.1 真实业务

```text
“先分析一下这次作业整体有什么问题，
再深入看看张三最近数学为什么一直有问题。”
```

包含：

```text
Task A = homework-review
Task B = student-diagnosis
```

## 8.2 执行方式

```text
Teacher Lead Agent
        ↓
homework-review
        ↓
student-diagnosis（张三）
        ↓
Final Answer
```

## 8.3 为什么这里不使用 Multi-Agent

两个任务可以由 Teacher Lead Agent 依次完成，当前只有一个学生需要 Deep Diagnosis。

因此采用：

> **Multi-Skill Composition（多技能组合），而不是 Multi-Agent。**

# 9. 场景六：班级周度学情复盘 → Screening → 按需 Diagnosis Workers

这是当前阶段最核心的 Multi-Agent 业务场景。

## 9.1 真实业务

教师可能只要求整体复盘：

```text
“帮我复盘一下八三班这周数学情况，
看看班级主要问题和哪些学生需要关注。”
```

也可能进一步要求：

```text
“帮我复盘八三班这周数学，
并把持续异常的学生分别具体分析一下。”
```

第一种请求不因为出现多个重点学生就自动启动 Sub-Agent；第二种请求才需要继续进行学生 Deep Diagnosis。

## 9.2 Lead Agent 先完成全班 Screening

```text
Teacher Lead Agent
        ↓
list_class_homeworks
        ↓
得到本周 homework_id 列表
        ↓
逐份 get_homework_analysis
+
get_class_profile
        ↓
获得：
A. ClassProfile.attention_students（长期）
B. 各 HomeworkAnalysis.attention_students（本周即时）
```

这里的两个 `attention_students` 都已经由 `ProfileAlgorithmV1 / AnalysisCalculationV1` 基于全班数据确定性计算，不需要 Sub-Agent 对全班逐个学生做第一轮诊断。

Teacher Lead Agent 直接基于这些结构化结果综合长期状态和本周多份作业信号，判断本轮真正需要进一步 Deep Diagnosis 的学生，并形成：

```text
weekly_attention_students
```

三层语义继续保持：

```text
ClassProfile.attention_students
= 长期画像关注学生

HomeworkAnalysis.attention_students
= 单次作业即时异常候选

weekly_attention_students
= Teacher Lead Agent 综合长期画像
  + 本周多份 Homework Analysis
  后形成的周度业务判断
```

Lead Agent 只能基于 Tool 已返回的结构化事实进行判断，不重新计算或覆盖 `ProfileAlgorithmV1 / AnalysisCalculationV1` 的阈值与字段语义。

如果教师只要求整体复盘，Lead 到这里即可继续形成班级周度总结，不启动 Diagnosis Worker。

## 9.3 Diagnosis Workers

当教师还要求对多个学生继续做 Deep Diagnosis 时：

```text
weekly_attention_students
        ↓
需要 Deep Diagnosis 的 student_ids
        ↓
一个或多个 task(subagent_type="diagnosis-worker")
        ↓
Diagnosis Workers
        ↓
Fan-in
        ↓
Teacher Lead Agent
```

一个 Diagnosis Worker 可以接收一个或多个明确 `student_id`。如果一次需要分析 10 个学生，不要求创建 10 个 Agent；Teacher Lead 可以根据当前运行时并发和上下文规模，把这些 `student_id` 分配给一个或多个 Diagnosis Worker。

每个 Worker 内部必须严格逐个处理学生：

```text
student_id A
↓
完整执行 student-diagnosis SOP
↓
形成 A 的 StudentDiagnosisResult
↓
再处理 student_id B
↓
完整执行 student-diagnosis SOP
↓
形成 B 的 StudentDiagnosisResult
↓
……
```

禁止把多个学生的 Profile / History 混在一起形成一份模糊诊断结果。

这里不规定固定：

```text
3 个 Worker × 每个 4 人
6～8 人一个批次
```

每个 task 分配多少 `student_id` 属于运行时调度问题，不是教育业务规则。

当前不自己实现：

```text
asyncio.gather Worker 调度层
自定义 Semaphore
自定义 Agent WorkerPool
自定义 Sub-Agent 生命周期管理
```

这些 Harness 能力直接复用 DeerFlow `task` + Subagent Runtime。

## 9.4 教师主动指定多个学生

如果教师已经明确指定需要分别深度分析的学生，例如：

```text
“张三、王五、赵六下午我要分别谈一下，
帮我逐个深入分析。”
```

则 Teacher Lead 直接解析这些学生对应的真实 `student_id`，不需要重新判断他们是否应该进入 `weekly_attention_students`，随后按同样方式委派 Diagnosis Worker。

## 9.5 为什么这里使用 Multi-Agent

不同学生的深度诊断彼此独立，且每个学生都需要读取自己的 Profile 和 Grading History。Diagnosis Worker 提供独立上下文，并允许 DeerFlow 并行执行多个子任务。

# 10. 场景七：完整班级周度复盘 → Consistency Reviewer

Multi-Agent 的另一类价值来自 Independent Perspective（独立审核视角）。

## 10.1 审核对象

场景六最终可以形成一份结构化的班级周度复盘：

```text
WeeklyClassReview
├── class_id
├── subject
├── period
├── homework_ids[]
│
├── class_findings
│   ├── key_weak_knowledge_points[]
│   └── common_errors[]
│
├── students_to_watch[]
│
├── deep_diagnoses[]       可选
│
└── next_week_teaching_focus[]
```

`WeeklyClassReview` 是当前 Run 的业务分析结果，不新增 MySQL 表，也不作为新的业务事实源。

当前不在该对象中加入：

```text
学生分层
练习分组
练习包
QuestionBankItem[]
Homework 创建 / 发布
```

## 10.2 Consistency Reviewer 职责

Consistency Reviewer 只做事实与语义一致性审核，不重新生成整份周度复盘。

检查范围：

```text
本周 Homework 范围是否完整

class_findings
是否与 ClassProfile / HomeworkAnalysis 一致

长期 weak_point / recurring_error
是否真的来自 Profile

是否把一次 Homework 即时异常
错误写成长期问题

students_to_watch / deep_diagnoses
是否有对应的结构化事实依据

StudentDiagnosisResult
是否与 StudentProfile / GradingHistory 一致

next_week_teaching_focus
是否对应本周发现的知识点 / 错误
```

Consistency Reviewer 不负责：

```text
判断哪一种教学法最优
重新生成整份 WeeklyClassReview
查询题库生成练习
发布 Homework
```

## 10.3 DeerFlow 实际执行

```text
Teacher Lead Agent
        ↓
形成完整 WeeklyClassReview
        ↓
task(
  description="审核班级周度复盘",
  prompt="...",
  subagent_type="consistency-reviewer"
)
        ↓
Consistency Reviewer
独立读取必要事实
        ↓
ReviewResult
        ↓
Teacher Lead Agent
        ↓
必要时修正
        ↓
Final Answer
```

Reviewer 默认不用于普通事实查询、单学生诊断和普通作业分析。

# 12. Sub-Agent 类型与 DeerFlow Config

当前只定义两个稳定 Sub-Agent 类型，由 Teacher Lead Agent 在需要时通过 DeerFlow `task` 动态启动实例。

DeerFlow `CustomSubagentConfig` 已支持：

```text
description
system_prompt
tools
disallowed_tools
skills
model
max_turns
timeout_seconds
```

因此 Worker 的能力边界直接通过 DeerFlow Config 限制，而不是只靠 Prompt 约定。

## 12.1 Diagnosis Worker

逻辑配置：

```yaml
subagents:
  custom_agents:
    diagnosis-worker:
      description: 对分配的学生执行深度学习诊断
      system_prompt: >
        你是学习诊断子智能体，只处理分配给你的明确 student_id。
        如果一次分配多个 student_id，必须一个一个地按照 student-diagnosis SOP 独立分析：
        完成一个学生并形成该学生独立的 StudentDiagnosisResult 后，再处理下一个学生。
        不得把多个学生的 Profile、History 或诊断结论混在一起。
        不负责筛选学生或班级整体决策。
      tools:
        - get_student_profile
        - get_student_grading_history
      skills:
        - student-diagnosis
      disallowed_tools:
        - task
        - ask_clarification
        - present_files
```

职责：读取 ProfileAlgorithmV1 已确定的长期画像、使用 Grading History 举证薄弱 / 重复错误 / 趋势；按 student_id 分别输出诊断结果，不负责班级整体决策、练习生成、最终教师回答，也不继续创建 Sub-Agent。

## 12.2 Consistency Reviewer

```yaml
subagents:
  custom_agents:
    consistency-reviewer:
      description: 独立审核完整班级周度复盘的事实与语义一致性
      system_prompt: >
        你是班级周度复盘一致性审核子智能体。
        只检查已有 WeeklyClassReview 是否与正式 Profile、Analysis
        和学生历史证据一致，不重新生成整份周度复盘，
        不判断教学法是否最优。
      tools:
        - list_class_homeworks
        - get_class_profile
        - get_homework_analysis
        - get_student_profile
        - get_student_grading_history
      disallowed_tools:
        - task
        - ask_clarification
        - present_files
```

Consistency Reviewer 只读取必要事实，不修改业务数据，也不继续委派新的 Agent。

当前 DeerFlow 自定义 Sub-Agent 的默认 deny 本身已经包含 `task / ask_clarification / present_files`；本项目在配置示例中继续显式写出，是为了让文档中的业务边界一眼可见。

# 13. Agent / Skill / Tool 最终关系

```text
Agent（智能体）
= 理解目标、动态决策、调用能力或执行专业任务

Skill（技能）
= 已验证、可复用的教学任务 SOP

Tool（工具）
= 真正查询、计算或检索业务数据的原子能力
```

Teacher Lead Agent 可以自主选择 Tool / Skill、根据中间结果继续追加 Tool、组合多个 Skill、决定是否 `task` 委派 Sub-Agent。

Sub-Agent 任务范围更窄、上下文更隔离、Tool / Skill 权限更受限，只完成 Lead Agent 分配的边界清晰任务。

稳定教学任务优先走 Skill；不存在匹配 Skill 时，Lead Agent 可以自主组合 Tool。

# 14. Sub-Agent 任务与结果传递

Sub-Agent 之间不默认直接通信：

```text
Teacher Lead Agent
↓
task(description, prompt, subagent_type)
↓
Sub-Agent 独立 Context
↓
返回结构化结果
↓
Teacher Lead Agent
```

Diagnosis Worker 对每个 student_id 分别返回：

```text
StudentDiagnosisResult
├── student_id
├── weak_knowledge_points
├── recurring_errors
├── trend
├── diagnosis_type
└── evidence_summary
```

一次 Diagnosis Worker task 可以包含多个 `student_id`，但结果必须仍然是多份彼此独立的 `StudentDiagnosisResult`，不能合并成一份多人诊断。

Consistency Reviewer 返回：

```text
ReviewResult
├── status
│   ├── PASS
│   └── NEEDS_REVISION
└── issues[]
    ├── code
    ├── target
    ├── reason
    └── evidence
```

Lead Agent 负责 Fan-in、后续任务输入和最终回答。不要把前一个 Agent 的整段自然语言无结构地交给下一个 Agent。

# 15. Multi-Agent 触发规则

Teacher Lead Agent 默认不启用 Multi-Agent。只有出现以下任一**真实收益**时才考虑 DeerFlow `task`：

```text
A. Independent Parallelism
= 存在多个彼此独立、可真正并行的对象 / 子任务

B. Specialist Capability
= 某个专门 Sub-Agent 拥有明显更合适的 Tool / Skill / Prompt / Model 能力

C. Context Isolation
= 单任务上下文很重，拆分后可以明显保护主 Agent Context

D. Independent Review
= 高价值结果需要独立 Reviewer 第二视角
```

明确不是触发条件：

```text
“任务步骤很多”
“任务很复杂”
“回答会很长”
“涉及多个 Tool”
```

业务示例：

```text
单学生诊断
→ Lead Agent + student-diagnosis

普通作业讲评
→ Lead Agent + homework-review

作业讲评 + 单学生诊断
→ Lead Agent 串行两个 Skill
→ 不使用 Multi-Agent

普通班级周度复盘
→ Lead Agent 完成 Screening 和周度总结
→ 不自动使用 Multi-Agent

班级周度复盘 + 多个学生 Deep Diagnosis
→ task(diagnosis-worker)

教师明确指定多个学生分别 Deep Diagnosis
→ task(diagnosis-worker)

完整 WeeklyClassReview 需要独立审核
→ 按需 task(consistency-reviewer)
```

# 16. Multi-Agent 成本控制原则

## 16.1 先 Screening 再 Fan-out

不要：

```text
40 个学生
↓
直接启动大量 Diagnosis Worker
```

应该：

```text
Lead Agent
↓
list_class_homeworks + get_homework_analysis + get_class_profile
↓
基于长期 / 本周 attention_students
判断本轮需要 Deep Diagnosis 的学生
↓
再 task Fan-out
```

## 16.2 Diagnosis Worker 顺序处理被分配的学生

当前不规定“一个学生必须一个 Agent”，也不规定固定批次数量。

```text
一个 Diagnosis Worker
→ 可以接收一个或多个 student_id
→ 对每个 student_id 逐个完整执行 student-diagnosis SOP
→ 分别输出 StudentDiagnosisResult
```

Teacher Lead 根据当前任务规模、上下文容量以及 DeerFlow Sub-Agent 限制决定启动多少个 Diagnosis Worker；该数量属于运行时调度，不属于教育业务规则。

## 16.3 Sub-Agent 不递归委派

当前通过 `CustomSubagentConfig.disallowed_tools` 禁止 Worker 使用 `task`，从运行时约束而不是只靠 Prompt 防止递归 Agent 树。

## 16.4 Consistency Reviewer 按需启动

Consistency Reviewer 只用于完整班级周度复盘或教师明确要求审核的任务。

## 16.5 当前 MVP 使用 task，Durable Batch 留作后续扩展

当前班级规模默认使用 DeerFlow 普通 `task`：

```text
当前 MVP
→ parallel task calls
→ SubagentLimitMiddleware 控制并发 / 总委派量
→ Sub-Agent Runtime 执行
```

当前不把 DeerFlow `batch_task` 设为主路径，因为 durable batch 会引入当前比赛规模不需要的持久化批任务复杂度。

未来满足以下情况时再评估：

```text
100+ 独立对象
任务需要 Gateway 重启后继续
教师不需要一直在线等待
需要真正 durable batch 生命周期
```

此时可以：

```text
parallel task
→ 升级为 DeerFlow batch_task
```

而不改变 Tool / Skill / Worker 的业务 Contract。

# 17. Memory 的读写责任与 DeerFlow 实现

当前阶段直接复用 DeerFlow Memory Runtime，不新增 `remember_teacher_preference` / `save_memory` 等 Teacher 专属 Memory Tool。

当前 MVP 决策：

```text
memory.mode = middleware
```

运行链路：

```text
Teacher Conversation
        ↓
DeerFlow MemoryMiddleware
        ↓
本轮结束后 enqueue conversation
        ↓
MemoryManager
        ↓
长期 Teacher Memory
        ↓
后续会话由 DeerFlow Dynamic Context / Memory Runtime 注入相关记忆
```

长期记忆的抽取与持久化使用 DeerFlow Memory Runtime；Teacher Copilot 负责通过 Prompt / Memory 规则限制什么信息值得长期保存。

当前长期 Teacher Memory 仅允许保存：

```text
Teacher Preference（教师偏好）
├── 回答长短偏好
├── 分析粒度偏好
└── 结果展示方式偏好

Teaching Style（教学风格）
├── 偏重基础讲解
├── 偏重启发式教学
├── 偏重错题复盘
└── 偏重针对性练习

Teaching Decision Context（教学决策上下文）
├── “近期重点关注张三”这类持续关注意图
├── “近期把某知识点作为重点”这类教学策略倾向
└── “这个班近期多安排基础练习”这类策略上下文
```

以下业务事实不能从 Memory 读取后直接作为当前事实：

```text
学生成绩
知识点掌握度
薄弱知识点
重复错误统计
作业完成率
题目错误率
GradingResult
Student Profile
Class Profile
Homework Analysis
Question Analysis
```

都必须通过 Tool 从 MySQL / Profile / Analysis 中读取。

Sub-Agent 默认不直接管理长期 Memory。如果 Sub-Agent 需要教师偏好或教学风格，由 Lead Agent 把当前任务必要的 Memory Context 一起放入 `task.prompt` / 子任务上下文；Worker 不直接写长期 Memory。
