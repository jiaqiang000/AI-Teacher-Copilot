# AI Teacher Copilot：06–07 业务驱动的 Teacher Agent 设计

## 1. 设计目标

Step 1–5 已经确定 Teacher Copilot 的业务事实、学习画像、Tools（工具）和 Skills（技能）。

Step 6–7 不再从“Memory 怎么设计”“Intent Router 怎么设计”“需要几个 Agent”出发，而是从真实教师业务出发：

> **教师提出不同复杂度的任务时，Teacher Agent 应该采用什么最低成本、最低复杂度、但能够完整完成任务的执行方式。**

因此本阶段采用两个核心原则：

```text
Business-Driven（业务驱动）
= 先有真实教学任务，再决定需要什么 Agent 能力

Single-Agent First（单智能体优先）
= 能由一个 Teacher Lead Agent 完成，就不升级为 Multi-Agent
```

Multi-Agent（多智能体）只在真实业务满足以下条件时启用：

```text
① Parallelism（任务可并行）
   多个子任务之间基本没有前后依赖，可以同时执行

② Context Isolation（上下文隔离）
   单次任务需要处理大量学生 / 历史数据，拆开后能显著降低主 Agent 上下文压力

③ Independent Perspective（独立专业视角）
   需要独立审核、验证或不同专业角色，而不是同一个 Agent 连续完成线性任务
```

如果以上条件都不满足，则不使用 Multi-Agent。

# 2. Teacher Agent 总体架构

整个教师侧只有一个统一入口：

```text
Teacher（教师）
      ↓
Teacher Lead Agent（教师主智能体）
```

Teacher Lead Agent 是教师侧真正的主控 Agent，负责：

```text
理解教师请求
+
解析请求中的业务对象
+
读取必要 Memory（记忆）
+
判断任务复杂度
+
选择 Tool / Skill
+
必要时自主组合多个 Tool / Skill
+
复杂任务时委派 Sub-Agent（子智能体）
+
汇总结果并生成最终回答
```

整体关系：

```text
                         Teacher
                           ↓
                  Teacher Lead Agent
                   （教师主智能体）
                           │
          ┌────────────────┼────────────────┐
          ↓                ↓                ↓
       Memory            Skills           Tools
      （记忆）           （技能）          （工具）
          │                │                │
          └────────────────┼────────────────┘
                           │
                    根据业务复杂度
                           │
        ┌──────────────────┼──────────────────┐
        ↓                  ↓                  ↓
   Direct Tool        Tool / Skill       Sub-Agent
   （直接工具）         灵活编排           Delegation
                                           （子智能体委派）
                                                │
                                   ┌────────────┼────────────┐
                                   ↓            ↓            ↓
                              Diagnosis     Practice      Reviewer
                               Worker        Worker        Agent
                            （诊断子智能体） （练习子智能体） （审核智能体）
                                                │
                                                ↓
                                       Teacher Lead Agent
                                                ↓
                                           Final Answer
                                           （最终回答）
```

这里不存在一个独立的 `Intent Router Agent（意图路由智能体）`。

Intent Routing（意图与任务路由）是 Teacher Lead Agent 的一个职责：

> **根据当前教师业务请求，判断应该直接调用 Tool、执行 Skill、灵活组合多个 Tool / Skill，还是委派 Sub-Agent。**

Multi-Agent 也不是 Lead Agent 后面的另一套系统：

```text
Teacher Lead Agent
+
按需启动的 Sub-Agents
=
Teacher Multi-Agent System（教师多智能体系统）
```

## 2.1 业务事实、画像算法与 LLM 的边界

教师侧所有学习状态统一遵守以下链路：

```text
MySQL
= 原始业务事实
        ↓
ProfileAlgorithmV1（profile_v1）
= 确定性计算 mastery / trend / weak_point / recurring_error 等画像事实
        ↓
Profile Tools
= 返回结构化派生学习事实
        ↓
Teacher Lead Agent / Skill / Sub-Agent
= 解释、比较、下钻证据、制定教学计划
```

因此 LLM 不负责重新计算 `mastery`，也不允许自行改变 `< 0.60`、`attempt_count >= 3`、最近 14/28 天等画像阈值。需要修改画像判断，只修改 Step 3–5 中的 `ProfileAlgorithmV1`。

## 2.2 Teacher Business Context（教师业务上下文）

教师进入 Teacher Copilot 时，运行时可以携带当前页面已经明确的业务对象。第一版只保留真正有助于参数解析的轻量信息：

```text
TeacherBusinessContext
├── teacher_id
├── class_refs[]
│   ├── class_id
│   └── class_name
│
├── current_class_id        可选
├── current_homework_id     可选
├── current_question_id     可选
│
└── current_question_refs[] 可选
    ├── question_id
    └── question_no
```

其中：

```text
class_refs
= 当前教师可访问的少量班级引用
= 用于把“八三班”等名称映射到 class_id

current_class_id / current_homework_id / current_question_id
= 当前页面已经明确的业务对象

current_question_refs
= 当前作业中的题号与 question_id 对应关系
= 用于解析“第 8 题”等表达
```

Teacher Business Context 只是运行时参数，不新增数据库业务对象，也不要求单独持久化。页面已经明确的对象直接复用，不再让 Agent 重复查询或再次询问教师。

## 2.3 Business Object Resolution（业务对象解析）

Teacher Agent 的正式业务 Tool 仍然使用明确的 `student_id / class_id / homework_id / question_id`。教师不需要感知这些内部 ID，Teacher Lead Agent 在调用正式 Tool / Skill 前完成轻量解析。

解析顺序固定为：

```text
Teacher Query（教师请求）
        ↓
Teacher Business Context
        ↓
当前 Context 能否直接确定？
├── Yes → 使用真实业务 ID
└── No
     ↓
必要时调用对象发现 Tool
├── list_class_students
└── list_class_homeworks
     ↓
能否唯一确定？
├── Yes → 使用真实业务 ID
└── No  → DeerFlow ask_clarification
             ↓
           教师选择
             ↓
           使用确认后的业务 ID
```

例如教师说：

```text
“分析一下张三最近数学情况。”
```

当前：

```text
current_class_id = class_03
```

执行：

```text
Teacher Lead Agent
        ↓
list_class_students(class_03)
        ↓
匹配 name = 张三
        ↓
只有一个结果？
├── Yes
│    ↓
│ student_id = stu_003
│    ↓
│ student-diagnosis
│
└── No
     ↓
  ask_clarification
     ↓
  教师选择
     ↓
  student_id
     ↓
  student-diagnosis
```

“第 8 题”优先使用当前作业上下文中的题号映射：

```text
教师：
“第 8 题错误率是多少？”

current_homework_id = hw_004
current_question_refs:
question_no = 8
question_id = q008

↓
得到 question_id = q008
↓
get_question_analysis
```

对象解析遵循：

```text
Context First（上下文优先）
Unique Match First（唯一匹配直接继续）
Clarify on Ambiguity（存在歧义才询问）
Never Guess ID（禁止猜测业务 ID）
```

存在多个候选或无法唯一确定时，直接复用 DeerFlow 内置 `ask_clarification` Human-in-the-Loop 能力，不新增 Entity Resolution Tool / Skill / Agent，也不单独建设 HITL 系统。

# 3. 业务复杂度驱动的执行层级

Teacher Lead Agent 不把所有请求都套进固定 Workflow（工作流）。

根据真实业务复杂度，从低到高采用以下执行方式：

| 层级 | 典型业务 | 执行方式 |
|---|---|---|
| L1 | 查询一个明确事实 / 业务对象列表 | Direct Tool（直接工具） |
| L2 | 一个已有标准教学任务 | Single Skill（单技能） |
| L3 | 没有现成 Skill，但多个 Tool 可以完成 | Adaptive Multi-Tool（自主多工具） |
| L4 | 一个 Skill 完成主体，额外需要 Tool | Skill + Tool（技能 + 工具组合） |
| L5 | 一个请求包含多个串行教学任务 | Multi-Skill（多技能组合，仍是单 Agent） |
| L6 | 大量独立对象需要批量分析 / 生成 | Parallel Sub-Agents（并行子智能体） |
| L7 | 大型高价值结果需要独立复核 | Reviewer Agent（独立审核智能体） |

核心原则：

```text
L1–L5
默认由 Teacher Lead Agent 完成

L6–L7
只有真实存在并行、上下文隔离或独立审核价值时
才升级为 Multi-Agent
```

# 4. 场景一：明确事实 / 对象查询 → Direct Tool

## 4.1 真实业务

教师会频繁询问明确的数据问题，例如：

```text
“八三班这次数学作业完成率是多少？”

“张三现在最薄弱的三个知识点是什么？”

“第 8 题错误率是多少？”

“八三班有哪些学生？”

“八三班这周有哪些数学作业？”
```

这些问题的答案已经存在于 Step 3–5 建设的数据能力中。

## 4.2 执行方式

```text
Teacher
↓
Teacher Lead Agent
↓
识别为明确事实 / 对象查询
↓
解析必要的业务对象
↓
对应 Tool
↓
Answer
```

例如：

```text
完成率
→ get_homework_analysis

学生薄弱知识点
→ get_student_profile

第 8 题错误率
→ get_question_analysis

班级完整学生名单
→ list_class_students

指定时间范围的班级作业
→ list_class_homeworks
```

其中两个列表 Tool 只负责发现业务对象：

```text
list_class_students
= 谁在这个班级里

list_class_homeworks
= 这个时间范围有哪些作业
```

它们不负责学情分析。

## 4.3 为什么不需要 Skill / Multi-Agent

```text
目标明确
+
一个正式业务 Tool 已经能够返回完整事实 / 对象列表
```

因此遵循：

> **Single Tool First（单工具优先）。**

业务对象解析不参与 L1–L7 复杂度升级判断。复杂度层级描述的是教师真正要求完成的教学任务，而不是为了补齐 Tool 参数实际调用了多少次对象发现能力。

例如：

```text
教师：
“张三有哪些薄弱知识点？”

实际执行：
list_class_students
↓
唯一确定 student_id
↓
get_student_profile
```

教师真正要求的仍然只是一次学生画像事实查询，因此仍属于 `L1 Direct Tool`，不能因为实际出现两个 Tool Call 就机械升级为 `L3 Adaptive Multi-Tool`。

同理：

```text
ask_clarification
= 补齐正式 Tool 参数所需的 Human-in-the-Loop
≠ 一个新的教学任务
≠ L1–L7 升级条件
```

# 5. 场景二：标准教学任务 → Single Skill

## 5.1 真实业务

教师提出的是一个完整教学任务，而不是简单字段查询：

```text
“帮我分析一下张三最近数学学习情况，看看主要问题是什么。”
```

这个任务需要：

```text
ProfileAlgorithmV1 已生成的学生长期画像
+
历史作答证据
+
解释长期薄弱 / 近期退步 / 偶发错误的区别
+
形成诊断结论
```

其中“是否长期薄弱、是否重复错误、趋势是否下降”已经由 `ProfileAlgorithmV1` 确定：

```text
长期薄弱
→ profile.weak_points

重复错误
→ profile.recurring_errors

近期退步
→ profile.trend = declining

偶发错误
→ 历史事实中出现错误，但未进入 weak_points / recurring_errors
```

`student-diagnosis` 不重新定义这些阈值，只使用 Grading History 下钻“为什么得到这个画像结论”。

## 5.2 执行方式

现有 `student-diagnosis（学生学习诊断）` Skill 已经完整覆盖：

```text
Teacher
↓
Teacher Lead Agent
↓
student-diagnosis
↓
get_student_profile
+
get_student_grading_history
↓
诊断结果
```

同类业务包括：

```text
“分析一下八三班长期学情。”
→ class-learning-analysis（班级学情分析）

“分析一下这次作业应该怎么讲评。”
→ homework-review（作业讲评分析）

“给班里不同水平学生安排练习。”
→ differentiated-practice（分层练习设计）
```

其中 `differentiated-practice` 在数据准备阶段会通过 `list_class_students（查询班级学生列表）` 枚举完整班级成员，再按需读取学生画像完成分层。

## 5.3 为什么仍然只需要一个 Agent

一个稳定 Skill 已经能够完整完成业务任务。

因此：

```text
Teacher Lead Agent
+
一个 Skill
```

比新增一个专业 Agent 更简单、更便宜，也更容易评测。

# 6. 场景三：Skill 未命中 → Adaptive Multi-Tool

## 6.1 真实业务

真实教师提问不可能全部落在预定义 Skill 中。

例如：

```text
“张三和李四在数学上的主要差异是什么？谁现在更需要重点关注？”
```

当前系统并没有：

```text
compare-two-students
```

这样的固定 Skill。

也不应该为教师所有可能问法都提前创建 Skill。

## 6.2 执行方式

Teacher Lead Agent 自主安排 Tool Calling（工具调用）：

```text
Teacher Lead Agent
        ↓
get_student_profile（张三）
        ↓
get_student_profile（李四）
        ↓
根据中间结果判断证据是否足够
        ↓
必要时继续：
get_student_grading_history（张三）
get_student_grading_history（李四）
        ↓
综合比较
        ↓
Answer
```

## 6.3 设计意义

这类业务说明：

> **Skill 未命中，不等于 Agent 无法完成任务。**

Teacher Lead Agent 必须保留自主 Tool Calling 能力：

```text
理解当前任务
↓
选择 Tool
↓
读取结果
↓
根据中间结果继续决定下一个 Tool
↓
直到获得足够事实
```

否则 Teacher Copilot 会退化成只能执行固定 Skill 的 Workflow 系统，而不是 Agent。

# 7. 场景四：Skill + Tool 灵活组合

## 7.1 真实业务

```text
“分析一下这次作业应该重点讲哪些问题，
再给最需要讲的三个知识点各找几道类似题。”
```

前半部分属于：

```text
homework-review（作业讲评分析）
```

后半部分属于：

```text
search_question_bank（检索题库）
```

但 `homework-review` 本身并不负责题库检索。

## 7.2 执行方式

```text
Teacher Lead Agent
        ↓
homework-review
        ↓
得到：
高错题
薄弱知识点
共性错误
讲评优先级
        ↓
发现教师还要求“找类似题”
        ↓
search_question_bank
        ↓
最终回答
```

## 7.3 设计意义

Skill 是稳定的业务能力块，而不是强制锁死 Agent 后续执行流程。

因此 Teacher Lead Agent 可以：

```text
Skill
+
额外 Tool
```

完成比单个 Skill 更丰富、但仍然不需要 Multi-Agent 的教师请求。

# 8. 场景五：多个 Skill 串行组合 → 仍然 Single-Agent

## 8.1 真实业务

```text
“分析这次作业的问题，然后根据班级情况给学生安排分层练习。”
```

实际上包含两个稳定任务：

```text
Task A
homework-review（作业讲评分析）

Task B
differentiated-practice（分层练习设计）
```

## 8.2 执行方式

```text
Teacher Lead Agent
        ↓
homework-review
        ↓
得到本次作业问题
        ↓
differentiated-practice
        ↓
生成分层练习
        ↓
Answer
```

## 8.3 为什么这里不使用 Multi-Agent

因为这是明显的线性依赖：

```text
A
↓
B
```

第二个任务需要使用第一个任务的结果。

拆成：

```text
Analysis Agent
↓
Practice Agent
```

不会带来真正并行收益，反而增加：

```text
额外 LLM 调用
上下文交接
延迟
成本
错误传播
调试复杂度
```

因此这里采用：

> **Multi-Skill Composition（多技能组合），而不是 Multi-Agent。**

这也是本项目避免 Multi-Agent 过度设计的重要边界。

# 9. 场景六：班级周度学情复盘 → Parallel Diagnosis Sub-Agents

这是当前阶段最核心、最自然的 Multi-Agent 业务之一。

## 9.1 真实业务

教师每周需要对班级进行一次整体复盘：

```text
“帮我做一下八三班这周数学的整体复盘。
看看全班主要薄弱点，重点关注哪些学生，
每个重点学生具体是什么问题，
最后形成下周教学重点。”
```

班级可能包含：

```text
40 个学生
+
本周多次作业
+
每个学生长期 Student Profile
+
每个学生近期 Grading History
```

如果所有学生都由 Lead Agent 串行深入分析，会出现：

```text
执行时间长
主 Agent 上下文过大
不同学生分析互相挤占上下文
```

而不同学生之间的深度诊断本身基本独立。

## 9.2 第一阶段：Lead Agent 发现本周作业并完成全局筛选

周度复盘不能直接假设系统已经知道“本周有哪些作业”，因此先使用对象发现 Tool：

```text
Teacher Lead Agent
        ↓
list_class_homeworks
（class_id + subject + 本周时间范围）
        ↓
得到本周 homework_id 列表
        ↓
对这些作业调用 get_homework_analysis
        +
get_class_profile
        ↓
获得两类关注信号：

A. ClassProfile.attention_students
= ProfileAlgorithmV1 产生的长期画像关注学生

B. 当前周 Homework Analysis 中暴露出的近期异常学生
= 本周完成率 / 成绩 / 高错题等即时作业事实
        ↓
Teacher Lead Agent 综合 A + B
        ↓
得到 weekly_attention_students（本周重点学生）
        ↓
确定真正需要深度诊断的学生
```

这里必须区分：

```text
ClassProfile.attention_students
≠ weekly_attention_students
```

前者只表示长期画像关注对象；后者是周度业务场景的最终筛选结果，可以因为“本周刚出现一次明显异常”而包含尚未达到长期 weak / recurring 阈值的学生。

同时：

```text
list_class_homeworks
= 发现本周有哪些作业

get_homework_analysis
= 分析每一份具体作业

get_class_profile
= 提供班级长期状态
```

三者边界清晰。

不是一开始就把全班所有学生全部交给 Sub-Agent。Lead Agent 先通过班级与近期作业数据完成筛选，控制 Multi-Agent 成本。

## 9.3 第二阶段：Diagnosis Worker 并行诊断

假设最终识别出 12 个重点关注学生：

```text
                     Teacher Lead Agent
                            ↓
                    12 个重点学生
                            ↓
          ┌─────────────────┼─────────────────┐
          ↓                 ↓                 ↓
Diagnosis Worker 1   Diagnosis Worker 2   Diagnosis Worker 3
   学生 A-D             学生 E-H             学生 I-L
          ↓                 ↓                 ↓
 student-diagnosis    student-diagnosis    student-diagnosis
          ↓                 ↓                 ↓
          └─────────────────┼─────────────────┘
                            ↓
                       Lead Agent 汇总
                            ↓
                    班级周度学情复盘
```

## 9.4 为什么这里值得 Multi-Agent

### Parallelism（任务可并行）

```text
学生 A 的诊断
不依赖
学生 B 的诊断
```

可以并行运行。

### Context Isolation（上下文隔离）

每个 Diagnosis Worker 只处理自己负责的学生及其历史记录。

不需要把所有重点学生的完整历史数据都塞入 Teacher Lead Agent 上下文。

### Specialization（专业能力）

Diagnosis Worker 专门执行学习诊断任务，拥有明确边界。

因此这里的 Multi-Agent 是由：

```text
真实班级规模
+
大量独立学生诊断
+
上下文压力
```

自然产生，而不是为了展示 Multi-Agent 人工拆角色。

# 10. 场景七：班级诊断 + 分层练习包 → 两阶段 Fan-out / Fan-in

这是当前最适合作为完整 Demo 的 Multi-Agent 业务闭环。

## 10.1 真实业务

```text
“帮我把八三班这周数学学习情况完整复盘一下，
找出主要问题和重点学生，
并根据学生水平生成下周分层练习。”
```

业务目标包括：

```text
班级整体分析
+
重点学生深度诊断
+
学生分层
+
不同层级练习生成
```

## 10.2 数据准备：先发现本周作业

```text
Teacher Lead Agent
        ↓
list_class_homeworks
        ↓
获得本周数学 homework_id 列表
        ↓
get_homework_analysis（逐份分析）
+
get_class_profile
        ↓
班级整体分析
        ↓
筛选重点学生
```

## 10.3 第一轮 Fan-out（并行扇出）：重点学生诊断

```text
Teacher Lead Agent
        ↓
筛选重点学生
        ↓
────────────────────────────
第一轮 Fan-out（并行扇出）
────────────────────────────
        │
        ├── Diagnosis Worker 1
        ├── Diagnosis Worker 2
        └── Diagnosis Worker 3
        │
        ↓
并行执行 student-diagnosis
        ↓
Fan-in（结果汇总）
        ↓
Teacher Lead Agent
```

Lead Agent 汇总得到：

```text
班级主要问题
重点学生问题
薄弱知识点
重复错误
学生学习层次
```

## 10.4 第二轮 Fan-out（并行扇出）：分层练习生成

学生分层完成之后：

```text
基础组
巩固组
提升组
```

三组练习之间不需要互相等待，因此可以再次并行：

```text
                   Teacher Lead Agent
                          ↓
                     学生分层结果
                          ↓
        ┌─────────────────┼─────────────────┐
        ↓                 ↓                 ↓
Practice Worker 1  Practice Worker 2  Practice Worker 3
     基础组              巩固组              提升组
        ↓                 ↓                 ↓
differentiated-     differentiated-     differentiated-
practice            practice            practice
        ↓                 ↓                 ↓
search_question_bank  search_question_bank  search_question_bank
        ↓                 ↓                 ↓
        └─────────────────┼─────────────────┘
                          ↓
                     Fan-in（汇总）
                          ↓
                  Teacher Lead Agent
                          ↓
           班级诊断 + 分层练习完整方案
```

## 10.5 业务闭环

最终形成：

```text
发现本周作业
↓
分析班级整体问题
↓
批量诊断重点学生
↓
形成学生分层
↓
并行生成不同层级练习
↓
教师获得完整下周教学方案
```

这个场景同时具备：

```text
真实教师需求
真并行
上下文隔离
已有 Profile / Tool / Skill 可直接复用
```

因此是当前阶段 Teacher Multi-Agent 的核心业务场景。

# 11. 场景八：全班个性化练习生成 → 大规模 Practice Workers

## 11.1 真实业务

教师进一步提出：

```text
“根据八三班每个学生最近的学习情况，
给每个人安排 10 道针对性练习。”
```

这不是简单的三组分层练习，而是 40 个学生的 Personalized Practice（个性化练习）。

## 11.2 第一步：先拿到真实班级成员

不能因为 Class Profile 中有 `student_count = 40` 就假设知道 40 个学生是谁。

因此 Lead Agent 先调用：

```text
Teacher Lead Agent
        ↓
list_class_students
        ↓
得到完整 student_id 列表
        ↓
按批次切分给 Practice Workers
```

`get_class_profile` 负责班级学情，`list_class_students` 负责真实成员枚举，两者不混用。

## 11.3 单 Agent 的问题

如果 Teacher Lead Agent 串行执行：

```text
学生 1
→ Profile
→ 选择薄弱知识点
→ 搜题

学生 2
→ Profile
→ 选择薄弱知识点
→ 搜题

...

学生 40
```

整体执行时间和上下文规模都会明显增加。

而每个学生的练习生成相互独立。

## 11.4 Multi-Agent 执行

```text
                     Teacher Lead Agent
                            ↓
                    list_class_students
                            ↓
                        40 个学生
                            ↓
          ┌─────────────────┼─────────────────┐
          ↓                 ↓                 ↓
Practice Worker 1   Practice Worker 2   Practice Worker N
   学生 1–5            学生 6–10             ...
          ↓                 ↓                 ↓
get_student_profile  get_student_profile  get_student_profile
          ↓                 ↓                 ↓
选择薄弱知识点        选择薄弱知识点        选择薄弱知识点
          ↓                 ↓                 ↓
search_question_bank search_question_bank search_question_bank
          ↓                 ↓                 ↓
          └─────────────────┼─────────────────┘
                            ↓
                       Lead Agent 汇总
                            ↓
                     全班个性化练习包
```

这里满足：

```text
高度可并行
+
每个学生上下文独立
+
单 Agent 串行成本明显
```

因此属于非常自然的 Multi-Agent 场景。

# 12. 场景九：大型教学方案 → Reviewer Agent 独立审核

Multi-Agent 的价值不只来自并行，也可以来自 Independent Perspective（独立视角）。

## 12.1 真实业务

系统完成一次大型班级教学方案：

```text
班级诊断
+
重点学生判断
+
学生分层
+
分层 / 个性化练习
```

这类输出影响后续实际教学安排，价值较高。

可以按需启动：

```text
Reviewer Agent（审核智能体）
```

## 12.2 Reviewer 不重新生成方案

Reviewer 只负责独立检查：

```text
重点学生是否有数据依据？

长期薄弱判断是否有足够历史证据？

练习知识点是否对应真实薄弱知识点？

题目难度是否与学生层级匹配？

是否存在 Agent 结论与 Profile / Analysis 事实冲突？

是否遗漏明显需要关注的学生？
```

## 12.3 执行方式

```text
Teacher Lead Agent
        ↓
生成完整教学方案
        ↓
仅大型 / 高价值任务触发 Reviewer
        ↓
Reviewer Agent
        ↓
独立读取必要事实
        ↓
返回：
pass（通过）
warnings（警告）
issues（问题）
        ↓
Teacher Lead Agent
        ↓
必要时修正
        ↓
最终方案
```

Reviewer 默认不用于：

```text
普通事实查询
单学生简单诊断
普通作业分析
```

避免所有请求无意义地增加一次 LLM 调用。

# 13. 场景十：教师长期偏好 → Agent Memory

Memory（记忆）同样从真实业务产生，而不是为了 Agent 架构单独建设。

## 13.1 真实业务

教师明确表达长期偏好：

```text
“以后给我做作业分析的时候，
先告诉我最值得课堂讲的三个问题，
不用写太长。”
```

这个信息不是学生业务事实，而是稳定的教师偏好。

应该写入：

```text
Teacher Preference（教师偏好）
```

下次教师只说：

```text
“帮我看看今天这次作业。”
```

系统可以：

```text
Teacher Lead Agent
        ↓
读取相关 Teacher Memory
        ↓
homework-review
        ↓
业务事实仍来自 Tool
        ↓
按照教师偏好：
优先给三个课堂重点
+
保持简洁
```

## 13.2 Memory 当前保存内容

当前阶段只保留真正具有长期价值的三类：

```text
Teacher Preference（教师偏好）
├── 回答长短偏好
├── 分析粒度偏好
└── 结果展示方式偏好

Teaching Style（教学风格）
├── 偏重基础讲解
├── 偏重启发式教学
├── 偏重错题复盘
└── 偏重分层训练

Teaching Decision（教学决策）
├── 某学生需要持续关注
├── 某知识点近期作为重点
└── 某班级采用某种练习策略
```

## 13.3 Memory 不能保存什么

以下数据不能由 Memory 作为事实源：

```text
学生成绩
知识点掌握度
薄弱知识点
重复错误统计
作业完成率
题目错误率
GradingResult（批改结果）
Student Profile（学生画像）
Class Profile（班级画像）
Homework Analysis（作业分析）
Question Analysis（题目分析）
```

它们必须通过 Step 3–5 已确定的 Tool 从 MySQL / Profile 中读取。

核心边界：

```text
MySQL / Profile
= 客观业务事实与可重算学习状态

Tool
= 访问业务事实

Skill
= 完成稳定教学任务的方法

Memory
= 教师长期上下文
```

因此：

> **Memory 可以改变回答方式和教学策略偏好，但不能改变业务事实。**

# 15. Sub-Agent 类型与能力边界

当前不按照“学生 A Agent / 学生 B Agent”创建大量 Agent 类型。

只定义少量稳定 Worker 类型，再按任务动态启动多个实例。

---

## 15.1 Diagnosis Worker（学习诊断子智能体）

定位：

> **对分配给自己的学生集合执行深度学习诊断。**

内置能力：

```text
Diagnosis Worker
│
├── 专属 System Prompt
│   └── 学习诊断专家
│
├── Skill
│   └── student-diagnosis
│
└── Tools
    ├── get_student_profile
    └── get_student_grading_history
```

业务边界：

```text
负责：
读取 ProfileAlgorithmV1 已确定的学生长期画像
解释薄弱知识点 / 重复错误 / 学习趋势
使用 Grading History 区分并举证长期薄弱 / 近期退步 / 偶发错误
历史事实验证

不负责：
自行重算 mastery / weak / recurring 阈值
班级整体决策
最终教师回答
练习生成
继续创建其他 Sub-Agent
```

同一个大任务可以动态启动：

```text
Diagnosis Worker #1
Diagnosis Worker #2
Diagnosis Worker #3
...
```

它们是同一种 Agent 的多个并行实例。

---

## 15.2 Practice Worker（练习设计子智能体）

定位：

> **对分配给自己的学生组 / 学生集合生成针对性练习。**

内置能力：

```text
Practice Worker
│
├── 专属 System Prompt
│   └── 分层 / 个性化练习设计专家
│
├── Skill
│   └── differentiated-practice
│
└── Tools
    ├── get_student_profile
    ├── get_class_profile
    └── search_question_bank
```

业务边界：

```text
负责：
确定训练目标
确定知识点
确定难度
确定题型
题库检索
形成练习方案

不负责：
重新完成整个班级学情分析
修改学生业务事实
最终汇总多个 Worker 结果
继续创建其他 Sub-Agent
```

Practice Worker 接收 Lead Agent 已分配好的学生组 / 学生批次，因此不需要自己再次调用 `list_class_students`。

可以按：

```text
基础组 / 巩固组 / 提升组
```

或：

```text
学生批次
```

并行启动多个实例。

---

## 15.3 Reviewer Agent（审核智能体）

定位：

> **对大型高价值教学方案进行独立事实一致性与合理性审核。**

Reviewer 与 Diagnosis / Practice Worker 不同：

```text
Diagnosis / Practice
= 执行业务任务

Reviewer
= 独立验证已有结果
```

Reviewer 默认只读取必要的事实 Tool，不直接修改业务数据，也不继续委派新的 Agent。

# 16. Agent / Skill / Tool 最终关系

三者边界固定为：

```text
Agent（智能体）
= 负责理解目标、动态决策、调用能力或执行专业任务

Skill（技能）
= 已验证、可复用的教学任务 SOP（标准流程）

Tool（工具）
= 真正查询、计算或检索业务数据的原子能力
```

Teacher Lead Agent 的特点是：

```text
可以自主选择 Tool / Skill
可以根据中间结果继续追加 Tool
可以组合多个 Skill
可以决定是否委派 Sub-Agent
```

Sub-Agent 的特点是：

```text
任务范围更窄
上下文更隔离
Tool / Skill 权限更受限
只完成 Lead Agent 分配的边界清晰任务
```

稳定教学任务优先走 Skill：

```text
存在匹配 Skill
→ 优先执行 Skill SOP

不存在匹配 Skill
→ Lead Agent 可以自主组合 Tool
```

Agent 不应为了“更自主”而无视已经稳定验证的 Skill SOP。

---

# 17. Sub-Agent 任务与结果传递

Sub-Agent 之间不默认直接通信。

主要通信模式：

```text
Teacher Lead Agent
↓
委派边界清晰的子任务
↓
Sub-Agent
↓
返回结构化结果
↓
Teacher Lead Agent
```

Sub-Agent 返回结果应优先结构化，而不是只返回大段自然语言。

例如 Diagnosis Worker 返回：

```text
StudentDiagnosisResult
├── student_id
├── weak_knowledge_points
├── recurring_errors
├── trend
├── diagnosis_type
└── evidence_summary
```

Practice Worker 返回：

```text
PracticeResult
├── target_students
├── knowledge_points
├── difficulty
├── question_type
└── selected_questions
```

这样 Lead Agent 可以稳定完成：

```text
Fan-in（结果汇总）
+
后续任务输入
+
最终回答
+
Agent 级评测
```

避免把前一个 Agent 的整段自然语言直接交给下一个 Agent，减少信息丢失和误差传播。

---

# 18. Multi-Agent 触发规则

Teacher Lead Agent 默认不启用 Multi-Agent。

满足以下任一真实收益条件时才考虑委派：

```text
A. 有多个彼此独立的对象 / 子任务，可以并行

B. 单任务需要读取大量历史上下文，拆分后可以明显隔离 Context

C. 最终结果价值高，需要独立 Reviewer 提供第二视角
```

业务判断示例：

```text
单个学生诊断
→ Teacher Lead Agent + student-diagnosis

一次普通作业讲评
→ Teacher Lead Agent + homework-review

作业分析 + 分层练习
→ Teacher Lead Agent 串行执行两个 Skill
→ 不使用 Multi-Agent

10+ 个重点学生深度诊断
→ Diagnosis Workers 并行

全班学生个性化练习
→ list_class_students
→ Practice Workers 并行

大型班级教学方案
→ 可选 Reviewer Agent
```

因此：

> **是否使用 Multi-Agent 由业务规模和执行收益决定，而不是由“一个请求包含几个教学动作”决定。**

---

# 19. Multi-Agent 成本控制原则

Multi-Agent 必须显式控制成本和复杂度。

## 19.1 先筛选再 Fan-out

不要：

```text
40 个学生
↓
直接启动 40 个 Agent
```

而应该：

```text
Lead Agent
↓
list_class_homeworks + get_homework_analysis + get_class_profile
↓
先识别班级近期问题与真正需要深度诊断的重点学生
↓
再 Fan-out
```

## 19.2 Worker 处理批次，而不是默认一人一个 Agent

例如 12 个重点学生可以：

```text
3 个 Diagnosis Worker
×
每个处理 4 个学生
```

而不是机械创建 12 个 Agent。

全班个性化练习同样先通过 `list_class_students` 获取成员，再按批次分配给多个 Practice Worker。

## 19.3 Sub-Agent 不继续递归委派

当前阶段：

```text
Teacher Lead Agent
可以委派 Sub-Agent

Sub-Agent
默认不能继续创建新的 Sub-Agent
```

避免 Agent 树无限扩展和执行不可控。

## 19.4 Reviewer 按需启动

Reviewer 不作为所有回答的默认步骤，只用于大型、高价值或教师明确要求审核的任务。

# 20. Memory 的读写责任

当前阶段 Long-Term Memory（长期记忆）主要服务 Teacher Lead Agent。

```text
Memory
↓
Teacher Lead Agent
```

Sub-Agent 默认不直接管理长期 Memory。

如果某个 Sub-Agent 需要教师偏好或教学风格：

```text
Teacher Lead Agent
↓
将与当前任务相关的必要 Memory Context（记忆上下文）
一起传给 Sub-Agent
```

Sub-Agent 不直接写入长期 Memory。

最终是否产生新的长期记忆，由 Teacher Lead Agent 在本轮任务结束后统一判断。

这样可以避免：

```text
多个 Sub-Agent 重复写 Memory
不同 Agent 写入相互冲突的教师偏好
业务分析结论被错误沉淀为长期事实
```

---

# 21. 当前阶段不实现的能力

继续沿用 Step 3–5 已确定的边界：

```text
暂不建设：
RAG / Teaching Knowledge Base（教学知识库）

因此暂缓：
search_teaching_materials（教学资料检索）
personalized-intervention（个性化教学干预）
Teaching Intervention Agent（教学干预智能体）
```

同时当前不提前建设：

```text
复杂 Intent Classification（意图标签体系）
独立 Intent Router Agent
独立 Entity Resolution Agent / Skill / Tool
独立 HITL 系统
固定 Supervisor → Analysis Agent → Practice Agent 串行架构
Sub-Agent 递归委派
所有请求默认 Reviewer
复杂 Memory Reflection（记忆反思）
复杂 Memory Compression（记忆压缩）
```

这些能力只有在真实业务出现明确需求时再扩展。
