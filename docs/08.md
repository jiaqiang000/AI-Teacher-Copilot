# AI Teacher Copilot：08 评测驱动开发设计

## 1. 这份文档解决什么问题

01–07 已经定义了业务边界、GradingResult、学习画像、Teacher Agent Tools / Skills、Single-Agent First（单智能体优先）、Multi-Agent（多智能体）、Reviewer（审核智能体）和 Memory（记忆）边界。

08 不再重复解释这些能力，而是把 01–07 中的重要设计决策转换成**可以执行、可以判定、可以回归的 Eval Case（评测用例）**。

核心关系固定为：

```text
01–07 Design Decision（设计决策）
        ↓
Eval Case（评测用例）
        ↓
Implementation（功能实现）
        ↓
Run Evaluation（运行评测）
        ↓
Result Pass + Behavior Pass（结果通过 + 行为通过）
        ↓
Failed / Unstable Case（失败 / 不稳定用例）
        ↓
Trace + Diagnosis Agent（执行链路 + 诊断智能体）
        ↓
Fix + Regression（修复 + 回归）
```

因此当前阶段的评测重点不是“学生上传图片到数据库的整条工程链路”，而是：

```text
Teacher Agent（教师智能体）
├── Tool Calling（工具调用）
├── Skill Routing（技能路由）
├── Adaptive Tool Use（自适应工具使用）
├── Multi-Skill（多技能组合）
├── Sub-Agent Delegation（子智能体委派）
├── Fan-out / Fan-in（并行扇出 / 结果汇总）
├── Reviewer（审核智能体）
└── Memory Boundary（记忆边界）
```

学生侧 Grading Workflow（批改工作流）只保留必要的 Smoke Evaluation（冒烟评测），确保 Teacher Agent 读取到的 `GradingResult` 基本可信，同时对已经固定的 `GradingTask` 异步执行、提交版本保护和实时进度契约做最小回归。

## 2. 评测执行闭环

每个 Teacher Eval Case（教师评测用例）固定执行 5 次，用于同时衡量正确性和稳定性。

```text
Evaluation Case（评测用例）
        ↓
Teacher Agent 独立运行 5 次
        ↓
┌────────────────────┬────────────────────┐
↓                    ↓                    ↓
Result Judge       Behavior Check       Quality Judge
结果评判             行为检查              质量评判
↓                    ↓                    ↓
Result Pass        Behavior Pass        Quality Score
结果是否正确          架构行为是否正确        回答质量
└────────────────────┴────────────────────┘
                     ↓
              Case Evaluation Result
                     ↓
          Failed / Unstable Case
                     ↓
             Trace + Diagnosis
```

每次 Run（运行）必须保存：

```text
User Query（用户问题）
Gold Facts（标准业务事实）
Expected Behavior（期望执行行为）
Forbidden Behavior（禁止行为）
Final Answer（最终回答）
Complete Trace（完整执行链路）
Judge Result（裁判结果）
```

### 2.1 为什么区分 Result Pass 和 Behavior Pass

Teacher Agent 既要验证“最终有没有完成教师任务”，也要验证 06–07 中的 Agent 架构设计有没有真正执行。

例如 L5 Multi-Skill（多技能串行）任务：

```text
最终答案完全正确
但是错误启动了 5 个 Sub-Agent
```

应该得到：

```text
Result Pass（结果通过）   = PASS
Behavior Pass（行为通过） = FAIL

原因：
违反 Single-Agent First（单智能体优先）
出现 Unnecessary Multi-Agent（不必要的多智能体升级）
```

反过来：

```text
Tool / Skill 调用全部符合预期
但是最终把第 8 题错误率写错
```

应该得到：

```text
Result Pass（结果通过）   = FAIL
Behavior Pass（行为通过） = PASS
```

因此：

```text
Result Evaluation（结果评测）
= 产品效果是否正确

Behavior Evaluation（行为评测）
= Agent 架构和执行方式是否正确

Trace / Diagnosis（链路 / 诊断）
= 为什么失败
```

三者不混在一起。

## 3. Teacher Evaluation Snapshot：先构造一个固定的教师评测世界

Teacher Agent 的 Tool、Skill、Multi-Agent 和 Judge 都依赖业务事实。如果底层数据一直变化，就无法稳定判断 Agent 是否真正进步。

因此第一版固定构造：

```text
teacher_eval_v1（教师智能体冻结评测快照）
```

### 3.1 评测世界

第一版统一使用：

```text
Teacher（教师）
├── teacher_id: teacher_01
└── name: 王老师

Class（班级）
├── class_id: class_03
├── name: 八三班
├── subject: math
└── student_count: 30

时间范围
└── 最近 4 周

Homework（作业）
├── hw_001
├── hw_002
├── hw_003
└── hw_004
```

评测数据库中真实保存完整的 30 名学生、4 周作业、Question（题目）、Submission（提交）和 GradingResult（批改结果）。

08 文档只固定最关键、会被多个 Eval Case 复用的 Gold Facts（标准业务事实）。

### 3.2 第一批固定 Gold Facts

#### 班级事实

```text
class_id（班级 ID） = class_03
student_count（学生人数） = 30

长期主要薄弱知识点：
1. math.linear_equation.transposition（移项）
2. math.function.graph（函数图像）

主要共性错误：
1. SIGN_ERROR（符号错误）
2. GRAPH_READING_ERROR（函数图像读取错误）
```

#### 本周作业事实

```text
本周作业：
hw_003
hw_004

hw_004：
assigned_student_count（布置人数） = 30
submitted_student_count（提交人数） = 27
completion_rate（完成率） = 0.90

hw_004 最高错题：
question_id（题目 ID） = q008
attempt_count（作答人数） = 27
wrong_student_count（错误人数） = 18
error_rate（错误率） = 0.667

q008 主要错误：
SIGN_ERROR（符号错误）
```

#### 重点学生事实

```text
attention_students（重点关注学生）
├── stu_003 张三
├── stu_011 李四
├── stu_018 王五
└── stu_024 赵六
```

其中第一版重点固定两个有明显对照关系的学生：

```text
stu_003 张三
├── weak_point（长期薄弱点）
│   └── math.linear_equation.transposition（移项）
├── recurring_error（重复错误）
│   └── SIGN_ERROR（符号错误）
├── occurrence_count（近 4 周出现次数） = 5
└── trend（趋势） = declining（下降）

stu_011 李四
├── long_term_mastery（长期掌握） = normal（正常）
├── hw_004 中出现一次 SIGN_ERROR
├── recurring_error（重复错误） = false
└── trend（趋势） = stable（稳定）
```

这里故意构造：

```text
张三
= 长期薄弱 + 重复错误

李四
= 单次偶发错误
```

用于验证 Teacher Agent 是否真正遵守 03–05 的业务规则：

> 单次错误不能直接推导为长期薄弱知识点。

### 3.3 Snapshot Gate：跑 Agent 之前先验证事实底座

Teacher Agent Benchmark（教师智能体评测）运行前，必须先通过 Snapshot Gate（快照事实门禁）。

至少验证：

```text
get_class_profile(class_03, math)
→ 返回固定 Class Profile Gold

get_homework_analysis(class_03, hw_004)
→ completion_rate = 0.90
→ q008 为最高错题

get_question_analysis(class_03, hw_004, q008)
→ error_rate = 0.667
→ common_error = SIGN_ERROR

get_student_profile(stu_003, math)
→ weak_point = 移项
→ recurring_error = SIGN_ERROR
→ trend = declining

get_student_profile(stu_011, math)
→ 不得把本次单次 SIGN_ERROR 直接标记为长期 recurring_error
```

如果 Snapshot Gate 不通过：

```text
停止 Teacher Agent Evaluation
```

因为此时 Agent 后续错误无法和数据层错误区分。

## 4. Teacher Eval Case 的统一结构

所有 Teacher Agent Case 使用统一结构：

```jsonc
{
  "case_id": "T-L5-001",                // case_id（评测用例 ID）
  "level": "L5",                        // level（业务复杂度等级）
  "query": "...",                       // query（教师请求）
  "snapshot_id": "teacher_eval_v1",     // snapshot_id（冻结评测快照 ID）

  "gold_facts": {                        // gold_facts（最终回答依据的标准业务事实）
    "...": "..."
  },

  "expected_behavior": {                 // expected_behavior（期望执行行为）
    "execution_level": "L5",
    "skills": [],
    "required_tools": [],
    "required_subagents": []
  },

  "forbidden_behavior": [],              // forbidden_behavior（禁止出现的行为）

  "result_requirements": []              // result_requirements（最终回答必须完成的内容）
}
```

四部分职责必须分开：

```text
Gold Facts（标准事实）
= 最终答案应该基于什么事实

Expected Behavior（期望行为）
= Agent 正常情况下应该怎么执行

Forbidden Behavior（禁止行为）
= 绝对不希望出现的架构行为

Result Requirements（结果要求）
= 用户真正要求完成什么
```

自然语言最终答案不要求和 Gold 文本完全一致。

## 5. Teacher Agent Core Evaluation Cases

第一阶段先建设一组小而明确的 Core Set（核心评测集），直接驱动 Tool、Skill 和 Agent 开发。

后续可以扩充表达方式、边界数据和异常 Case，但每新增一个重要设计能力，必须先补对应 Eval Case。

### 5.1 L1：Direct Tool（直接工具调用）

#### T-L1-001：查询本次作业完成率

```text
教师：
“八三班这次数学作业完成率是多少？”

上下文已确定：
homework_id = hw_004
```

Gold Facts：

```text
completion_rate（完成率） = 0.90
submitted_student_count（提交人数） = 27
assigned_student_count（布置人数） = 30
```

Expected Behavior：

```text
execution_level（执行层级） = L1
required_tool（必须调用工具） = get_homework_analysis

arguments（参数）
├── class_id = class_03
└── homework_id = hw_004
```

Forbidden Behavior：

```text
get_class_profile
spawn_sub_agent
invoke_reviewer
```

Result Requirements：

```text
必须明确回答完成率 90%
不得根据 Memory 或模型自行计算不存在的数据
```

---

#### T-L1-002：查询第 8 题错误率

```text
教师：
“这次作业第 8 题错误率多少？主要是什么错误？”
```

Gold Facts：

```text
question_id（题目 ID） = q008
error_rate（错误率） = 0.667
common_error（主要错误） = SIGN_ERROR（符号错误）
```

Expected Behavior：

```text
required_tool = get_question_analysis
```

Result Requirements：

```text
回答约 66.7%
指出主要错误为 SIGN_ERROR（符号错误）
```

---

#### T-L1-003：查询本周数学作业

```text
教师：
“八三班这周有哪些数学作业？”
```

Gold Facts：

```text
homeworks（作业）
├── hw_003
└── hw_004
```

Expected Behavior：

```text
required_tool = list_class_homeworks

arguments（参数）至少包含：
class_id = class_03
```

```text
get_homework_analysis
```

```text
list_class_homeworks
= 发现“有哪些作业”

```

#### T-L1-004：查询班级学生列表

```text
教师：
“八三班现在有哪些学生？”
```

Expected Behavior：

```text

```

Result Requirements：

```text
返回完整 30 名学生
不能用 Class Profile 中的 student_count 猜学生身份
```

### 5.3 L3：Adaptive Multi-Tool（自适应多工具）

#### T-L3-001：比较两个学生

```text
教师：
“张三和李四在数学上的主要差异是什么？谁现在更需要重点关注？”
```

Gold Facts：

```text
张三：
长期移项薄弱

trend = declining

李四：
长期状态正常
hw_004 偶发一次 SIGN_ERROR
```


这里重点评测：


### 5.5 L5：Multi-Skill，但仍然 Single-Agent

#### T-L5-001：作业分析 + 分层练习

```text
教师：
“分析这次作业的问题，然后根据班级情况给学生安排分层练习。”
```

Expected Behavior：

```text
execution_level = L5

homework-review
        ↓
differentiated-practice
        ↓
Final Answer
```

Required Tools：

```text
get_homework_analysis
get_question_analysis
get_class_profile
list_class_students
get_student_profile（按需）
search_question_bank
```

Forbidden Behavior：

```text
spawn_sub_agent
invoke_reviewer
```

Result Requirements：

```text
必须包含：
本次作业主要问题
重点学生 / 分层依据
基础组 / 巩固组 / 提升组

```

核心评测点：

```text

A → B

所以应该 Multi-Skill（多技能）

```

#### T-L5-002：错误升级 Multi-Agent 的反例

使用与 T-L5-001 相同的问题和 Gold。

如果运行结果出现：

```text
Analysis Agent
↓
Practice Agent
```

但没有真实并行或上下文隔离收益，则：

```text
Result Pass
→ 按最终回答判断

Behavior Pass
→ FAIL

reason（原因）
= Unnecessary Multi-Agent（不必要的多智能体升级）
```

### 5.6 L6：Parallel Sub-Agents（并行子智能体）

这是当前 Teacher Copilot 最核心的 Multi-Agent 评测。

#### T-L6-001：班级周度学情复盘

```text
教师：
“帮我做一下八三班这周数学的整体复盘。
看看全班主要薄弱点，重点关注哪些学生，
每个重点学生具体是什么问题，最后形成下周教学重点。”
```

Gold Facts：

```text
本周作业：
hw_003
hw_004

attention_students：
stu_003
stu_011
stu_018
stu_024
```

Expected Behavior：

```text
Teacher Lead Agent
        ↓
list_class_homeworks
        ↓
得到 hw_003 / hw_004
        ↓
逐份 get_homework_analysis
+
get_class_profile
        ↓
先筛选 attention_students
        ↓
只对重点学生 Fan-out
        ↓
Diagnosis Workers（诊断子智能体）
        ↓
每个 Worker 执行 student-diagnosis
        ↓
Fan-in
        ↓
Teacher Lead Agent 汇总
```

Behavior Assertions：

```text
必须：
先做全局筛选
再启动 Sub-Agent

必须覆盖：
stu_003
stu_011
stu_018
stu_024

禁止：
一开始对全班 30 人全部启动 Diagnosis Worker
```

核心指标：

```text
Sub-Agent Delegation Accuracy（子智能体委派准确率）
Fan-out Correctness（并行扇出正确性）
Fan-in Completeness（结果汇总完整率）
Unnecessary Agent Count（不必要 Agent 数量）
```

#### T-L6-002：全班个性化练习

```text
教师：
“根据八三班每个学生最近的学习情况，给每个人安排 10 道针对性练习。”
```

Expected Behavior：

```text
list_class_students
        ↓
真实获取 30 个 student_id
        ↓
按批次 Fan-out Practice Workers
        ↓
每个 Worker：
get_student_profile
        ↓
识别薄弱点
        ↓
search_question_bank
        ↓
生成个人练习
        ↓
Fan-in
```

Behavior Assertions：

```text
不能根据 student_count = 30 猜学生身份
必须调用 list_class_students

最终必须覆盖完整 30 名学生
不能丢学生
不能重复学生
```

核心指标：

```text
Student Coverage（学生覆盖率）
Fan-in Completeness（结果汇总完整率）
Parallel Speedup（并行加速比）
Max Context Size（最大上下文规模）
```

---

### 5.7 L7：Reviewer Agent（审核智能体）

Reviewer 评测必须同时包含正样本和负样本，否则无法判断是否过度调用。

#### T-L7-001：大型教学方案应该触发 Reviewer

```text
教师：
“完整复盘八三班本周数学学习情况，
诊断重点学生，并生成下周分层教学与练习方案。”
```

Expected Behavior：

```text
完成班级分析
+
重点学生诊断
+
练习方案
        ↓
invoke_reviewer
        ↓
Reviewer 独立复核
        ↓
必要时修正
        ↓
Final Answer
```

Reviewer 至少检查：

```text
重点学生是否有数据依据
长期薄弱是否有足够历史证据
练习知识点是否对应真实薄弱点
题目难度是否和学生层级匹配
最终结论是否与 Profile / Analysis 冲突
是否遗漏明显需要关注的学生
```

---

#### T-L7-002：普通任务不应该触发 Reviewer

```text
教师：
“分析一下张三最近数学学习情况。”
```

Expected Behavior：

```text
student-diagnosis
```

Forbidden Behavior：

```text
invoke_reviewer
```

由 T-L7-001 和 T-L7-002 共同计算：

```text
Reviewer Trigger Precision（Reviewer 触发精确率）
Reviewer Trigger Recall（Reviewer 触发召回率）
Unnecessary Review Rate（不必要审核率）
```

### 5.8 Memory Evaluation（记忆边界评测）

#### T-MEM-001：Memory 影响表达，不改变业务事实

Memory：

```text
Teacher Preference（教师偏好）
“以后做作业分析时先告诉我最值得课堂讲的三个问题，不用写太长。”
```

教师：

```text
“帮我看看 hw_004 这次作业。”
```

Expected Behavior：

```text
业务事实
→ 仍然通过 Tool 获取

Memory
→ 只影响最终回答组织方式
```

Result Requirements：

```text
优先输出三个课堂重点
保持相对简洁
但数据必须来自 get_homework_analysis / get_question_analysis 等 Tool
```

---

#### T-MEM-002：Memory 不能覆盖当前业务事实

Memory 中存在旧信息：

```text
“李四数学一直比较差。”
```

当前 Snapshot Gold：

```text
李四长期状态正常
trend = stable
本次只有一次偶发 SIGN_ERROR
```

教师：

```text
“分析一下李四最近数学学习情况。”
```

Expected Behavior：

```text
Memory 可以作为历史上下文线索
但最终事实必须以：
get_student_profile
+
get_student_grading_history
为准
```

Forbidden Result：

```text
仅因为 Memory 旧信息
直接得出“李四当前长期数学薄弱”
```

这是：

```text
Memory ≠ Business Fact Source（记忆不是业务事实源）
```

的核心回归 Case。

## 6. Result Judge：最终结果怎么判

Teacher Agent 最终输出是自然语言，不能使用字符串完全匹配。

Judge 输入：

```text
User Query（用户问题）
+
Gold Facts（标准业务事实）
+
Result Requirements（结果要求）
+
Agent Final Answer（Agent 最终回答）
+
Evaluation Rubric（评分标准）
```

### 6.1 Result Pass

客观 Teacher Task（教师任务）的核心硬指标是：

```text
Result Pass（结果通过）
```

满足：

```text
核心业务事实正确
+
核心结论正确
+
完成用户明确要求的主要任务
+
不存在明显业务事实编造
```

则：

```text
Result Pass = PASS
```

以下直接：

```text
Result Pass = FAIL
```

情况包括：

```text
核心数值错误
核心业务对象错误
核心结论错误
明显编造不存在的学生 / 作业 / 分数 / 知识点
遗漏用户要求的核心任务
最终回答与 Gold Facts 发生关键冲突
```

### 6.2 Quality Score

Result Pass 解决“对不对”，但无法完整表达“答得好不好”。

统一采用 0–5 档位 Rubric（评分标准）：

| 维度 | 权重 | 评什么 |
|---|---:|---|
| Correctness（正确性） | 40% | 数据、事实和核心结论是否正确，有没有编造 |
| Completeness（完整性） | 25% | 用户要求的内容是否完整覆盖 |
| Relevance（相关性） | 15% | 是否跑题、是否存在大量无关内容 |
| Analysis / Teaching Quality（分析 / 教学质量） | 20% | 诊断、解释和教学建议是否合理 |

Judge 每个维度只允许输出：

```text
0 / 1 / 2 / 3 / 4 / 5
```

不允许直接自由输出 83、87、91 这类连续分。

Correctness（正确性）档位固定为：

| 分数 | 标准 |
|---:|---|
| 5 | 核心和次要业务事实、核心结论全部正确，无编造 |
| 4 | 核心事实和结论正确，仅有轻微非关键偏差 |
| 3 | 主体正确，但部分次要事实或结论有明显偏差 |
| 2 | 存在明显错误，但仍有部分主要结果正确 |
| 1 | 核心业务事实或核心结论错误 |
| 0 | 明显编造不存在的业务事实 |

程序计算：

```text
Quality Score（质量分）
=
Correctness × 40%
+
Completeness × 25%
+
Relevance × 15%
+
Analysis / Teaching Quality × 20%
```

## 7. Behavior Check：执行行为怎么判

Behavior Pass 直接基于 Trace 程序化检查，不交给 LLM 自由判断。

检查内容来自 Case 中的：

```text
Expected Behavior（期望行为）
+
Forbidden Behavior（禁止行为）
```

### 7.1 主要过程指标

```text
Execution Level Accuracy（执行层级准确率）
Tool Selection Accuracy（工具选择准确率）
Argument Generation Accuracy（参数生成准确率）
Tool Execution Success Rate（工具执行成功率）
Skill Routing Accuracy（Skill 路由准确率）
Required Tool Coverage（必需 Tool 覆盖率）
Tool Sequence Correctness（Tool 调用顺序正确率）
Adaptive Decision Correctness（自适应决策正确率）
Unnecessary Tool Call Rate（不必要 Tool 调用率）
Unnecessary Multi-Agent Rate（不必要多智能体升级率）
Sub-Agent Delegation Accuracy（子智能体委派准确率）
Fan-out Correctness（并行扇出正确性）
Fan-in Completeness（结果汇总完整率）
Reviewer Trigger Precision（Reviewer 触发精确率）
Reviewer Trigger Recall（Reviewer 触发召回率）
Memory Boundary Correctness（Memory 边界正确率）
```

### 7.2 Behavior Pass 规则

单次 Run 满足：

```text
required Tool / Skill / Sub-Agent 全部满足
+
关键参数正确
+
关键执行顺序正确
+
forbidden behavior 未出现
```

则：

```text
Behavior Pass = PASS
```

注意：

```text
Behavior Pass
不覆盖 Result Pass

Result Pass
也不覆盖 Behavior Pass
```

最终报告同时展示两者。

## 8. 多次运行后的核心指标

每个 Core Case 默认独立运行 5 次。

例如：

```text
Run 1 → PASS
Run 2 → PASS
Run 3 → FAIL
Run 4 → PASS
Run 5 → PASS
```

则该 Case：

```text
Case Result Pass Rate（单题结果通过率） = 4 / 5 = 80%
```

### 8.1 一级指标

Teacher Agent 最终首先看：

```text
Result Pass Rate（结果通过率）
→ 对不对

Behavior Pass Rate（行为通过率）
→ 架构执行对不对

Average Quality Score（平均质量分）
→ 好不好

All-Pass Rate（全对率 / 稳定通过率）
→ 稳不稳
```

Result Pass Rate 先按每个 Case 计算，再跨 Case 平均：

```text
Case Result Pass Rate
= 该 Case 5 次中 Result PASS 的次数 / 5

Overall Result Pass Rate
= 所有 Case Result Pass Rate 的平均值
```

Behavior Pass Rate 同理。

All-Pass Rate：

```text
5 / 5 Result PASS 的 Case 数
÷
全部 Case 数
```

### 8.2 不稳定 Case

重点关注：

```text
5 / 5
→ 稳定通过

0 / 5
→ 系统性失败

2 / 5、3 / 5、4 / 5
→ 不稳定，高优先级分析
```

对于不稳定 Case，把成功 Run 和失败 Run 的 Trace 放在一起比较。

## 9. Trace 与失败诊断

每次 Teacher Agent Run 必须完整保存 Trace。

### 9.1 agent_trace

核心字段：

| 字段 | 含义 |
|---|---|
| `eval_run_id` | 评测运行 ID |
| `case_id` | 评测用例 ID |
| `session_id` | 会话 ID |
| `round` | 第几轮 |
| `agent_name` | Agent 名称 |
| `agent_instance_id` | Agent 实例 ID |
| `parent_agent_instance_id` | 父 Agent 实例 ID |
| `step_type` | 步骤类型 |
| `input_data` | 模型输入 |
| `output_data` | 模型输出 |
| `tool_name` | Tool 名称 |
| `tool_arguments` | Tool 参数 |
| `tool_result` | Tool 返回 |
| `skill_name` | Skill 名称 |
| `latency_ms` | 延迟 |
| `input_tokens` | 输入 Token |
| `output_tokens` | 输出 Token |
| `cost` | 成本 |
| `status` | 状态 |

`step_type` 固定：

```text
LLM（模型调用）
TOOL（工具调用）
SKILL_START（Skill 开始）
SKILL_END（Skill 结束）
SUB_AGENT_START（Sub-Agent 开始）
SUB_AGENT_END（Sub-Agent 结束）
MEMORY_READ（Memory 读取）
MEMORY_WRITE（Memory 写入）
FINAL（最终回答）
```

### 9.2 Diagnosis Agent

触发条件：

```text
Result Pass = FAIL

或

Behavior Pass = FAIL

或

同一 Case 5 次运行出现 2 / 5、3 / 5、4 / 5
```

Diagnosis Agent 输入：

```text
User Query（用户问题）
Gold Facts（标准事实）
Expected / Forbidden Behavior（期望 / 禁止行为）
Judge Result（裁判结果）
Final Answer（最终回答）
Complete Trace（完整执行链路）
```

诊断过程：

```text
从 Round 1 开始检查 Trace
        ↓
找到可疑决策
        ↓
必要时使用只读 Evaluation Snapshot Tool 查证事实
        ↓
定位第一次真正发生错误的位置
        ↓
确定 Root Error（根源错误点）
        ↓
归因 Root Cause（根因）
```

重点不是最后哪一步表现错误，而是：

```text
第一次从正确轨道偏离发生在哪里？
```

根因固定为四类：

```text
MODEL（模型能力问题）
PROMPT_SCHEMA（Prompt / Schema 问题）
TOOL_DATA（Tool / 数据问题）
AGENT_FRAMEWORK（Agent 框架问题）
```

输出：

```jsonc
{
  "root_error_round": 3,                          // root_error_round（首次错误轮次）
  "root_error_agent": "TeacherLeadAgent",         // root_error_agent（首次出错 Agent）
  "category": "PROMPT_SCHEMA",                    // category（根因类别）
  "component": "get_student_profile.description", // component（问题组件）
  "reason": "...",                                // reason（错误原因）
  "downstream_effect": "...",                     // downstream_effect（后续影响）
  "suggested_fix": "..."                          // suggested_fix（修复方向）
}
```

## 10. 评测驱动开发怎么执行

以后不是功能全部写完再补评测，而是：

```text
新增 / 修改一个 Teacher Agent 能力
        ↓
先确定对应业务场景
        ↓
先写 Eval Case
        ↓
固定 Gold Facts / Expected Behavior
        ↓
实现 Tool / Skill / Prompt / Agent
        ↓
运行目标 Case × 5
        ↓
通过后运行 Core Regression（核心回归）
        ↓
失败则看 Trace + Diagnosis
```

典型对应关系：

| 01–07 设计 | 08 必须存在的评测 |
|---|---|
| Tool Contract | L1 Tool Selection / Argument Case |
| `student-diagnosis` | T-L2-001 / T-L2-002 |
| `class-learning-analysis` | T-L2-003 |
| `homework-review` | T-L2-004 |
| Adaptive Tool Calling | T-L3-001 / T-L3-002 |
| Skill + Tool | T-L4 Cases |
| Single-Agent First | T-L5 Cases |
| Parallel Sub-Agents | T-L6 Cases |
| Reviewer | T-L7 正负 Case |
| Memory 不是业务事实源 | T-MEM-002 |

核心规则：

> **01–07 每增加一个重要设计约束，08 至少增加一个能够证明该约束真正实现的 Eval Case。**

## 11. 对照与消融实验

常规回归评测回答“有没有实现正确”，对照实验回答“为什么这样设计”。

当前 Teacher Agent 重点做 3 组实验。

### 11.1 L5：Single-Agent vs Forced Multi-Agent

```text
Teacher Lead Agent + Multi-Skill（主智能体 + 多技能）

vs

Forced Multi-Agent（强制多智能体）
```

比较：

```text
Result Pass Rate（结果通过率）
Behavior Pass Rate（行为通过率）
Average Quality Score（平均质量分）
All-Pass Rate（全对率）
Latency（延迟）
Token Usage（Token 消耗）
Cost（成本）
```

目的：验证有明确串行依赖的任务坚持 Single-Agent First 是否更合理。

### 11.2 L6：Single-Agent Serial vs Parallel Sub-Agents

```text
Single-Agent Serial Execution（单 Agent 串行执行）

vs

Parallel Sub-Agents（并行子智能体）
```

比较：

```text
Result Pass Rate（结果通过率）
Average Quality Score（平均质量分）
All-Pass Rate（全对率）
Latency（延迟）
Token Usage（Token 消耗）
Cost（成本）
Max Context Size（最大上下文规模）
Fan-in Completeness（结果汇总完整率）
```

目的：验证批量独立学生诊断和大规模练习生成场景下，Multi-Agent 的并行和上下文隔离价值。

### 11.3 Reviewer OFF vs ON

```text
Reviewer OFF（关闭审核）

vs

Reviewer ON（启用审核）
```

比较：

```text
Final Result Pass Rate（最终结果通过率）
Correction Rate（纠错率）
Added Latency（新增延迟）
Added Cost（新增成本）
```

目的：判断大型高价值教学任务中 Reviewer 的纠错收益是否覆盖额外成本。

## 附录 A：Grading Smoke Evaluation（批改冒烟评测）

学生侧不是当前 08 的主体，但 Teacher Agent 依赖 `GradingResult`，因此保留一组小规模固定 Smoke Case。

第一阶段：

```text
Math（数学）
10–15 Cases

English Essay（英语作文）
10–15 Cases
```

只验证 Teacher Agent 真正依赖的上游字段，以及已经固定的批改任务执行契约。

### A.1 GradingTask 工程契约 Smoke Cases

这些 Case 不做复杂性能 Benchmark，只验证 01 中已经固定的异步批改约束没有被实现破坏。

#### G-TASK-001：正常状态转换

```text
创建 GradingTask
↓
PENDING
↓
RUNNING
↓
SUCCEEDED
```

必须满足：

```text
SUCCEEDED 前已成功写入当前有效 GradingResult
```

#### G-TASK-002：失败状态

OCR、Parsing 或模型调用发生不可恢复异常：

```text
RUNNING
↓
FAILED
```

必须保存可追踪的：

```text
error_code
error_message
```

#### G-TASK-003：旧 Submission 版本不得覆盖新结果

构造：

```text
Submission.version = 2

Task A.submission_version = 1
Task B.submission_version = 2
```

即使 Task A 晚于 Task B 完成：

```text
Task A
→ 不得写入 / 覆盖当前 GradingResult

Task B
→ 可以写入当前 GradingResult
```

核心断言：

```text
GradingTask.submission_version
必须等于
Submission.version
才允许写入当前结果
```

#### G-TASK-004：数学 current_stage 顺序

正常数学任务阶段至少满足：

```text
OCR
↓
PARSING
↓
DIFFICULTY_CLASSIFICATION
↓
GRADING
↓
ASSEMBLING_RESULT
↓
COMPLETED
```

#### G-TASK-005：英语不得进入 Difficulty Classification

英语作文阶段必须为：

```text
OCR
↓
PARSING
↓
GRADING
↓
ASSEMBLING_RESULT
↓
COMPLETED
```

禁止：

```text
DIFFICULTY_CLASSIFICATION
```

英语两个评分阶段均使用：

```text
DeepSeek v4 Flash
```

#### G-TASK-006：实时进度事件

当阶段开始 / 完成时：

```text
grading.stage.started
→ 前端对应步骤 = active

grading.stage.completed
→ 前端对应步骤 = complete
```

未开始步骤保持：

```text
pending
```

#### G-TASK-007：页面刷新恢复

当持久化任务状态为：

```json
{
  "status": "RUNNING",
  "current_stage": "GRADING"
}
```

学生刷新页面后必须：

```text
先读取 GradingTask 当前状态
↓
恢复已完成 / active / pending 步骤
↓
重新订阅 SSE / Streaming
```

不得因为刷新页面把进度重新显示为 `QUEUED`，也不得要求重新启动一次批改任务。
