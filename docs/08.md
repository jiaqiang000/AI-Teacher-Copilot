# AI Teacher Copilot：08 评测体系设计

## 1. 整体评测设计

本项目的评测目标不是只得到一个“分数”，而是回答四个问题：

```text
拿什么评？
↓
怎么跑？
↓
结果到底对不对、好不好、稳不稳？
↓
如果失败，第一次错在哪里？
```

完整评测闭环固定为：

```text
Evaluation Dataset（评测数据集）
        ↓
Agent / Workflow Execution（Agent / 工作流执行）
        ↓
Judge Evaluation（裁判评判）
        ↓
Pass Rate / Quality / Stability（正确性 / 质量 / 稳定性）
        ↓
Failed / Unstable Cases（失败 / 不稳定用例）
        ↓
Trace + Diagnosis Agent（执行链路 + 诊断智能体）
        ↓
Root Error + Root Cause（首次错误点 + 根因）
```

项目评测分为两条业务主线：

```text
Grading Evaluation（学生批改评测）
→ 判断学生侧批改结果本身是否可靠

Teacher Agent Evaluation（教师智能体评测）
→ 判断 Teacher Agent 是否能够基于业务事实正确完成教师任务
```

两者必须分开。Teacher Agent 的输入事实来自前面的 GradingResult、Profile 和 Analysis，如果上游批改错误，不能错误归因到 Teacher Agent。

## 2. Evaluation Dataset：拿什么评

### 2.1 Grading Benchmark

Grading Benchmark 固定为 400 个 Case：

| 类型 | 数量 |
|---|---:|
| 数学 easy | 100 |
| 数学 medium | 100 |
| 数学 hard | 100 |
| 英语作文 | 100 |
| **总计** | **400** |

数据集版本固定为：

```text
grading_eval_v1（学生批改冻结评测集）
```

所有不同模型、Prompt 和 Workflow 版本均在同一份评测数据上运行。

#### Math Benchmark

数学 Case 使用 `Gold` 标准答案，由人工确认后冻结。

```jsonc
{
  "case_id": "math_001",             // case_id（评测用例 ID）
  "question": "...",                  // question（题目内容）
  "student_answer": "...",            // student_answer（学生作答）
  "gold": {                           // gold（人工标准结果）
    "difficulty": "medium",           // difficulty（题目难度）
    "correct": false,                 // correct（是否正确）
    "score": 6,                       // score（总得分）
    "step_scores": [],                // step_scores（过程分 / 分步得分）
    "error_types": [],                // error_types（错误类型）
    "knowledge_points": []            // knowledge_points（知识点）
  }
}
```

数学属于客观任务，不使用 LLM Judge 判断这些指标，程序直接比较预测结果和 Gold：

```text
Correctness Accuracy（对错判断准确率）
Score MAE（总分平均绝对误差）
Step Score MAE（过程分平均绝对误差）
Error Type F1（错误类型 F1）
Knowledge Point F1（知识点识别 F1）
Difficulty Accuracy（难度判断准确率）
Strong Model Upgrade Rate（强模型升级比例）
Average Latency（平均延迟）
Average Cost（平均成本）
```

数学模型路由重点比较：

```text
Always Strong Model（全部使用强模型）

vs

Small Model + Strong Model Fallback（小模型 + 强模型兜底）
```

最终回答：

```text
准确率是否明显下降？
强模型调用比例下降多少？
平均成本下降多少？
平均延迟变化多少？
```

#### English Essay Benchmark

英语作文 Case 保存作文、Rubric 和教师人工评分：

```jsonc
{
  "case_id": "essay_001",        // case_id（评测用例 ID）
  "question": "...",             // question（作文题目）
  "essay": "...",                // essay（学生作文）
  "rubric": {},                  // rubric（评分标准）
  "gold": {                      // gold（教师人工标准评分）
    "total_score": 16,           // total_score（总分）
    "content": 4,                // content（内容）
    "organization": 4,           // organization（组织结构）
    "grammar": 3,                // grammar（语法）
    "vocabulary": 5              // vocabulary（词汇）
  }
}
```

当前英语作文 Workflow：

```text
Essay + Rubric（学生作文 + 评分标准）
        ↓
Evidence Agent（评分证据提取智能体）
        ↓
evidence.json（结构化评分证据）
        ↓
Scoring Agent（评分智能体）
        ↓
GradingResult（最终批改结果）
```

Evidence Agent 评：

```text
Evidence Coverage（证据覆盖率）
Evidence Correctness（证据正确率）
Unsupported Evidence Rate（无依据证据率）
```

Scoring Agent 评：

```text
Total Score MAE（总分平均绝对误差）
Dimension Score MAE（评分维度平均绝对误差）
Evidence Grounding（证据支撑度）
Feedback Quality（反馈质量）
```

其中分数偏差由程序直接计算；`Evidence Grounding` 和 `Feedback Quality` 属于开放式质量判断，由 LLM Judge 按固定 Rubric 评分。

### 2.2 Teacher Agent Benchmark

Teacher Agent Benchmark 固定为 100 个 Case。

L1–L7 不再作为七套独立评测，而只是 **100 个 Teacher Agent Case 的业务复杂度分类**：

| Level | 场景 | Case 数 | 重点能力 |
|---|---|---:|---|
| L1 | Direct Tool（直接工具调用） | 20 | Tool 选择与参数 |
| L2 | Single Skill（单 Skill） | 15 | Skill 路由与 SOP |
| L3 | Adaptive Multi-Tool（自适应多 Tool） | 15 | 根据中间结果动态调用 |
| L4 | Skill + Tool | 15 | Skill 后继续完成额外需求 |
| L5 | Multi-Skill / Single-Agent（多 Skill / 单 Agent） | 15 | 串行任务、避免错误升级 Multi-Agent |
| L6 | Parallel Sub-Agents（并行子智能体） | 10 | Fan-out / Fan-in |
| L7 | Reviewer Agent（审核智能体） | 10 | Reviewer 是否正确启动 |
| | **总计** | **100** | |

每个 Case 固定保存：

```jsonc
{
  "case_id": "teacher_l5_001",       // case_id（评测用例 ID）
  "level": "L5",                     // level（业务复杂度等级）
  "query": "分析这次作业的问题，然后根据班级情况生成分层练习。", // query（教师请求）
  "snapshot_id": "teacher_eval_v1",  // snapshot_id（冻结业务快照 ID）

  "expected": {                      // expected（期望执行行为）
    "execution_level": "L5",         // execution_level（期望执行层级）
    "skills": [                      // skills（期望使用的 Skill）
      "homework-review",
      "differentiated-practice"
    ],
    "required_tools": [              // required_tools（必须调用的 Tool）
      "get_homework_analysis",
      "get_question_analysis",
      "get_class_profile"
    ],
    "forbidden_tools": [],           // forbidden_tools（禁止调用的 Tool）
    "required_subagents": [],        // required_subagents（必须启动的 Sub-Agent）
    "forbidden_behavior": [          // forbidden_behavior（禁止行为）
      "spawn_sub_agent",
      "invoke_reviewer"
    ]
  },

  "gold_facts": {                    // gold_facts（标准业务事实）
    "weak_points": [],               // weak_points（薄弱知识点）
    "attention_students": [],        // attention_students（重点关注学生）
    "common_errors": []              // common_errors（共性错误）
  }
}
```

Teacher Agent 的 Gold **不保存固定自然语言回答**，而保存：

```text
Gold Facts（正确业务事实）
Expected Task Requirements（必须完成的任务要求）
Expected Execution Hints（期望执行行为）
Forbidden Behaviors（禁止行为）
```

自然语言表达可以不同，最终判断的是数据、核心结论和任务完成情况。

### 2.3 Frozen Evaluation Snapshot

Teacher Agent 使用独立冻结业务快照：

```text
teacher_eval_v1（教师智能体冻结评测快照）
```

固定包含：

```text
Teacher（教师）
Student（学生）
Class（班级）
Homework（作业）
Question（题目）
Submission（学生提交）
GradingResult（批改结果）
Student Profile（学生画像）
Class Profile（班级画像）
Homework Analysis（作业分析）
Question Analysis（题目分析）
```

构建流程：

```text
构造 / 导入评测业务数据
↓
人工校验
↓
生成 Gold Facts（标准业务事实）
↓
冻结 teacher_eval_v1
↓
所有 Agent 版本使用完全相同的数据
```

客观任务一旦确定 Gold，底层评测数据也必须冻结，否则数据变化后 Gold 就会失效，无法做可靠版本对比。

本项目离线 Teacher Agent Benchmark 因此采用：

```text
Frozen Snapshot（冻结业务快照）
+
Gold Facts（标准事实）
+
LLM-as-Judge（大模型裁判）
```

不使用需要现场查询动态生产数据的 Agent-as-Judge。

## 3. Agent 执行与 Trace：怎么跑

### 3.1 每个 Teacher Case 独立运行 5 次

Teacher Agent 每个 Case 默认独立执行 5 次：

```text
100 Cases（100 个评测用例）
×
5 Runs（每题 5 次独立运行）
=
500 Teacher Agent Runs（500 次完整执行）
```

单个 Case：

```text
Run 1 → PASS（通过）
Run 2 → PASS（通过）
Run 3 → FAIL（失败）
Run 4 → PASS（通过）
Run 5 → PASS（通过）

Case Pass Rate（单题通过率）
= 4 / 5
= 80%
```

5 次是工程上的默认折中：既能观察模型随机性，又不会使评测成本无限放大。特别关注 2/5、3/5、4/5 这种“时对时错”的 Case，因为它们最容易暴露 Prompt、Tool 调用和上下文处理的不稳定性。

### 3.2 完整 Trace

每次 Run 都必须保存最终回答和完整执行 Trace。

统一建立：

```text
agent_trace（Agent 执行链路表）
```

核心字段：

| 字段 | 含义 |
|---|---|
| `eval_run_id` | 所属评测 Run |
| `case_id` | 评测 Case |
| `session_id` | Agent Session |
| `round` | 第几轮交互 |
| `agent_name` | 当前 Agent |
| `agent_instance_id` | Agent 实例 |
| `parent_agent_instance_id` | 父 Agent 实例 |
| `step_type` | 当前步骤类型 |
| `input_data` | 完整模型输入 |
| `output_data` | 完整模型输出 |
| `tool_name` | Tool 名称 |
| `tool_arguments` | Tool 参数 |
| `tool_result` | Tool 返回 |
| `skill_name` | Skill 名称 |
| `latency_ms` | 延迟 |
| `input_tokens` | 输入 Token |
| `output_tokens` | 输出 Token |
| `cost` | 成本 |
| `status` | 执行状态 |

`step_type` 固定：

```text
LLM（模型调用）
TOOL（工具调用）
SKILL_START（Skill 开始）
SKILL_END（Skill 结束）
SUB_AGENT_START（Sub-Agent 开始）
SUB_AGENT_END（Sub-Agent 结束）
MEMORY_READ（Memory 读取）
MEMORY_WRITE（Memory 写入）
FINAL（最终回答）
```

Trace 的职责不是决定最终答案是否正确，而是：

```text
记录执行过程
↓
计算 Process Metrics（过程指标）
↓
对比成功 Run / 失败 Run
↓
失败后定位第一次错误位置
```

评判关注最终结果，诊断关注执行过程；Trace 的核心价值就是让错误能够沿调用链向前追溯。

## 4. Judge 与评分规则：到底对不对、好不好

这是整个 Teacher Agent Evaluation 的核心。

Teacher Agent 最终交付的是自然语言分析报告，不能使用字符串完全匹配。

Judge 输入固定为：

```text
User Query（用户问题）
+
Gold Facts（标准业务事实）
+
Task Requirements（任务要求）
+
Agent Final Answer（Agent 最终回答）
+
Evaluation Rubric（评分标准）
```

评测结果分成两个维度：

```text
PASS / FAIL（对不对）
+
Quality Score（好不好）
```

客观任务必须保留硬性的 PASS / FAIL；仅有质量分不足以表示任务是否真正正确完成。

### 4.1 Teacher Agent Rubric

本项目固定使用四个维度：

| 维度 | 权重 | 判断内容 |
|---|---:|---|
| Correctness（正确性） | **40%** | 数据、事实和核心结论是否正确，有没有编造 |
| Completeness（完整性） | **25%** | 用户要求的主要任务是否完整完成 |
| Relevance（相关性） | **15%** | 是否围绕请求回答，是否存在大量无关内容 |
| Analysis / Teaching Quality（分析与教学质量） | **20%** | 分析、诊断和教学建议是否合理 |

不继续增加“简洁性”“可读性”“可用性”等维度，避免维度重叠导致 Judge 判断不稳定。Rubric 的作用就是提前规定“评什么、什么情况打几分”，而不是允许 Judge 自由发挥。

### 4.2 评分采用 0–5 档位

Judge 每个维度只能输出：

```text
0 分
1 分
2 分
3 分
4 分
5 分
```

不允许输出：

```text
83 分
87 分
91 分
```

使用带明确锚点的档位分，减少同一答案反复 Judge 时产生的随机波动。

其中最重要的 `Correctness（正确性）` 固定为：

| 分数 | 标准 |
|---:|---|
| **5** | 核心和次要业务事实、核心结论全部正确，没有编造 |
| **4** | 核心业务事实和结论正确，仅存在非常轻微的非关键偏差 |
| **3** | 主体正确，但部分次要事实或结论存在明显偏差 |
| **2** | 存在较明显错误，但部分主要结果仍正确 |
| **1** | 核心业务数据或核心结论错误 |
| **0** | 明显编造不存在的学生、成绩、作业、知识点等业务事实 |

### 4.3 PASS / FAIL 规则

Teacher Agent 的单次 Run：

```text
Correctness >= 4
+
用户核心任务已经完成
+
不存在明显编造
=
PASS（通过）
```

以下情况直接 `FAIL`：

```text
核心业务数据错误
核心业务结论错误
明显编造业务事实
遗漏用户明确要求的核心任务
回答与 Gold Facts 发生关键冲突
```

这里特别强调：

> **Tool 调错、Skill 路由错误、是否启动 Multi-Agent，本身不直接作为最终 PASS / FAIL 的唯一依据。**

最终结果优先。

如果 Agent 走了一条不理想的路径，但最终事实和结论完全正确：

```text
最终结果 → 可以 PASS

Process Metric（过程指标）
→ 会记录此次 Tool / Skill / Multi-Agent 行为存在问题
```

反过来，即使：

```text
Tool 调用全部正确
Skill 执行流程完整
```

只要最终核心业务事实写错：

```text
Run → FAIL
```

因此：

```text
Judge（裁判）
负责衡量最终结果

Process Metrics（过程指标）
负责拆解内部能力

Trace（执行链路）
负责解释为什么出错
```

三者职责不混合。

### 4.4 Quality Score

单次 Run 的质量分由程序加权：

```text
Quality Score（质量分）
=
Correctness（正确性） × 40%
+
Completeness（完整性） × 25%
+
Relevance（相关性） × 15%
+
Analysis / Teaching Quality（分析与教学质量） × 20%
```

Judge 只负责输出四个整数档位，最终小数分由程序计算。

### 4.5 Grading 的评分规则

Grading 不强行套 Teacher Agent 的 Rubric。

数学：

```text
程序直接比较预测值和 Gold
→ Accuracy / MAE / F1
```

英语作文：

```text
教师人工 Score Gold
→ Score MAE（分数偏差）

开放式 Evidence / Feedback
→ LLM Judge + Rubric（大模型裁判 + 评分标准）
```

这样保持：

```text
确定性问题 → 程序直接评

开放式质量问题 → Judge 评
```

## 5. 最终评测结果：对不对、好不好、稳不稳

Teacher Agent 最终只保留三个一级主指标。

### Pass Rate（通过率）—— 对不对

每个 Case 先独立计算：

```text
Case Pass Rate（单题通过率）
=
该 Case 的 PASS Runs（通过次数）
÷
该 Case 的全部 Runs（运行次数）
```

再对所有 Case 求平均：

```text
Overall Pass Rate（总体通过率）
=
所有 Case Pass Rate 的平均值
```

它是 Teacher Agent 最重要的主指标。

### Average Quality Score（平均质量分）—— 好不好

```text
Average Quality Score（平均质量分）
=
所有 Run 的 Quality Score
跨运行、跨 Case 求平均
```

它回答：

> 在正确与否之外，Teacher Agent 的分析到底完整不完整、相关不相关、教学建议质量怎么样。

### All-Pass Rate（全对率 / 稳定通过率）—— 稳不稳

只有：

```text
5 / 5 全部 PASS
```

才算一个 Case 稳定通过。

```text
All-Pass Rate（全对率）
=
5 / 5 全部通过的 Case 数
÷
全部 Case 数
```

因此最终报告固定展示：

| 主指标 | 回答的问题 |
|---|---|
| **Pass Rate** | 对不对 |
| **Average Quality Score** | 好不好 |
| **All-Pass Rate** | 稳不稳 |

### Process Metrics：内部能力拆解

Process Metrics 不作为唯一的最终正确性判据，而是通过 Trace 自动计算，用来回答：

> Agent 内部到底哪项能力强、哪项能力弱？

L1–L7 对应：

| Level | Process Metrics |
|---|---|
| L1 | Tool Selection Accuracy、Argument Generation Accuracy |
| L2 | Skill Routing Accuracy、Required Tool Coverage |
| L3 | Adaptive Decision Correctness、Unnecessary Tool Call Rate |
| L4 | Intermediate Result Usage、Additional Tool Correctness |
| L5 | Multi-Skill Routing Accuracy、Unnecessary Multi-Agent Rate |
| L6 | Sub-Agent Delegation Accuracy、Fan-in Completeness、Parallel Speedup |
| L7 | Reviewer Trigger Precision / Recall、Reviewer Correction Rate |

核心过程指标统一为：

```text
Execution Level Accuracy（执行层级选择准确率）
Tool Selection Accuracy（工具选择准确率）
Argument Generation Accuracy（参数生成准确率）
Skill Routing Accuracy（Skill 路由准确率）
Required Tool Coverage（必需 Tool 覆盖率）
Evidence Grounding Rate（证据支撑率）
Unnecessary Multi-Agent Rate（不必要 Multi-Agent 升级率）
Sub-Agent Delegation Accuracy（子智能体委派准确率）
Fan-in Completeness（结果汇总完整率）
Reviewer Trigger Precision / Recall（Reviewer 触发精确率 / 召回率）
Cost（成本）
Latency（延迟）
```

其中最能体现本项目设计思想的是：

```text
Unnecessary Multi-Agent Rate（不必要 Multi-Agent 升级率）
Sub-Agent Delegation Accuracy（子智能体委派准确率）
Fan-in Completeness（结果汇总完整率）
Single-Agent vs Multi-Agent Cost / Latency / Quality（单 Agent 与多 Agent 成本 / 延迟 / 质量）
```

## 6. 失败定位：为什么错

Judge 完成评判后：

```text
FAIL Case（失败用例）

或

2 / 5、3 / 5、4 / 5
Unstable Case（不稳定用例）
```

进入 Diagnosis。

Diagnosis Agent 输入：

```text
User Query（用户问题）
+
Gold Facts（标准业务事实）
+
Evaluation Result（评测结果）
+
Final Answer（最终回答）
+
Complete Trace（完整执行链路）
```

Diagnosis Agent 具备：

```text
Read Eval Snapshot Tool（读取冻结评测快照的只读 Tool）
+
Read Trace Tool（读取指定 Run Trace 的 Tool）
```

执行过程固定为：

```text
读取完整 Trace
↓
从 Round 1 开始向后检查
↓
发现可疑决策
↓
必要时读取评测库验证业务事实
↓
找到第一次真正发生错误的位置
↓
确定 Root Error
↓
归因 Root Cause
```

不是找：

```text
最终哪里表现错了
```

而是找：

```text
第一次哪里开始错了
```

因为 Agent 错误会级联，最终报告里的错误往往只是前面错误的传播结果。

Root Cause 一级分类固定为四类：

```text
MODEL（模型能力问题）
→ 理解、推理、判断、生成能力不足

PROMPT_SCHEMA（提示词 / Schema 问题）
→ System Prompt、Tool Description、Skill SOP、参数 Schema 设计问题

TOOL_DATA（工具 / 数据问题）
```

## 7. 对照与消融实验

评测体系最终必须支持 5 组核心实验。

### 实验一：数学模型路由

```text
Always Strong Model（全部使用强模型）

vs

Small Model + Strong Model Fallback（小模型 + 强模型兜底）
```

比较：

```text
Correctness Accuracy（对错判断准确率）
Score MAE（总分平均绝对误差）
Strong Model Rate（强模型调用比例）
Latency（延迟）
Cost（成本）
```

目标：证明模型级联是否能在基本保持批改效果的前提下降低成本和延迟。

### 实验二：英语作文两阶段评分

```text
Single LLM Scoring（单模型直接评分）

vs

Evidence Agent + Scoring Agent（评分证据提取智能体 + 评分智能体）
```

比较：

```text
Score MAE（分数平均绝对误差）
Evidence Grounding（证据支撑度）
Feedback Quality（反馈质量）
Latency（延迟）
Cost（成本）
```

目标：证明先提取评分证据再评分是否提高评分稳定性和证据支撑能力。

### 实验三：L5 Single-Agent vs Multi-Agent

```text
Teacher Lead Agent + Multi-Skill（主智能体 + 多 Skill）

vs

Forced Multi-Agent（强制拆分为多智能体）
```

比较：

```text
Pass Rate（通过率）
Average Quality Score（平均质量分）
All-Pass Rate（全对率）
Latency（延迟）
Token Usage（Token 消耗）
Cost（成本）
```

目标：验证具有明确串行依赖的任务是否应该坚持 Single-Agent First。

### 实验四：L6 Single-Agent vs Parallel Sub-Agents

```text
Single-Agent Serial Execution（单 Agent 串行执行）

vs

Parallel Sub-Agents（并行 Sub-Agent）
```

比较：

```text
Pass Rate（通过率）
Average Quality Score（平均质量分）
All-Pass Rate（全对率）
Latency（延迟）
Token Usage（Token 消耗）
Cost（成本）
Max Context Size（最大上下文规模）
```

目标：验证批量独立学生诊断、批量练习生成场景下 Multi-Agent 的并行与上下文隔离价值。

### 实验五：Reviewer Ablation

```text
Reviewer OFF（关闭 Reviewer）

vs

Reviewer ON（启用 Reviewer）
```

比较：

```text
Final Pass Rate（最终通过率）
Correction Rate（纠错率）
Added Latency（新增延迟）
Added Cost（新增成本）
```

目标：判断 Reviewer 在大型高价值教学任务中的纠错收益是否足以覆盖额外成本。

最终，整个项目的评测可以压缩成一条主线：

```text
400 Grading Cases（400 个学生批改用例）
+
100 Teacher Agent Cases（100 个教师 Agent 用例）
×
5 Runs（每题 5 次）
        ↓
Frozen Evaluation Snapshot（冻结评测快照）
        ↓
Agent / Workflow Execution（执行）
        ↓
Final Answer + Complete Trace（最终答案 + 完整执行链路）
        ↓
Judge Evaluation（裁判评判）
        ↓
Pass Rate（对不对）
+
Average Quality Score（好不好）
+
All-Pass Rate（稳不稳）
        ↓
Process Metrics（内部能力拆解）
        ↓
Failed / Unstable Cases（失败 / 不稳定用例）
        ↓
Diagnosis Agent（诊断智能体）
        ↓
First Root Error（第一次错误位置）
+
Root Cause（根因）
```

这套结构中，**最终结果评判始终处于中心位置；L1–L7 是 Benchmark 分类，Tool / Skill / Multi-Agent 指标是过程能力拆解，Trace 是诊断原料，Diagnosis Agent 只负责回答“为什么错”**。这样既保持了项目原有的批改、Tool、Skill、Single-Agent First、Multi-Agent、Reviewer 等内容，又不会再出现每个概念都独立占一个标题、主次关系混乱的问题。
