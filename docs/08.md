# AI Teacher Copilot：08 评测体系设计

## 1. 评测目标

本项目的评测不只判断“最终回答好不好”，而是覆盖从学生批改到 Teacher Agent 的完整链路，并能够在失败后定位问题根因。

整体采用三阶段体系：

```text
Agent / Workflow 执行
        ↓
Judge 评判
        ↓
失败 Case 定位
```

每个评测 Case 统一保留：

```text
问题
+
Gold / 标准事实
+
实际输出
+
完整 Trace
```

最终形成：

```text
固定评测集
↓
重复执行
↓
完整 Trace
↓
程序规则 + LLM Judge
↓
通过率 / 质量 / 稳定性
↓
失败 Case 自动诊断
↓
定位第一次出错的位置
```

评测分为两层：

```text
第一层：Grading Evaluation
确保学生侧批改事实本身可靠

第二层：Teacher Agent Evaluation
确保 Teacher Agent 正确使用业务事实完成教师任务
```

两层必须分开评测，避免上游批改错误被错误归因到 Teacher Agent。

---

# 2. 整体评测架构

```text
                Evaluation Dataset
                       │
       ┌───────────────┴──────────────┐
       ↓                              ↓
Grading Benchmark              Teacher Agent Benchmark
学生批改评测                    教师 Agent 评测
       │                              │
       ↓                              ↓
Grading Workflow                Teacher Lead Agent
       │                              │
       └──────────────┬───────────────┘
                      ↓
                    Trace
                      ↓
                   Judge
                      ↓
       ┌──────────────┴──────────────┐
       ↓                             ↓
   Metrics                       Failed Cases
                                     ↓
                              Diagnosis Agent
                                     ↓
                              Root Cause
```

核心原则：

```text
最终结果
= 衡量做得对不对

Trace
= 解释错在哪里
```

## 3.2 English Essay Benchmark（英语作文评测集）

英语作文每个 Case 保存：

```jsonc
{
  "case_id": "essay_001",        // case_id（评测用例 ID）
  "question": "...",             // question（作文题目）
  "essay": "...",                // essay（学生作文）
  "rubric": {},                   // rubric（评分标准）
  "gold": {                       // gold（人工标准评分）
    "total_score": 16,            // total_score（总分）
    "content": 4,                 // content（内容）
    "organization": 4,            // organization（组织结构）
    "grammar": 3,                 // grammar（语法）
    "vocabulary": 5               // vocabulary（词汇）
  }
}
```

其中评分维度为：

```text
content（内容）
organization（组织结构）
grammar（语法）
vocabulary（词汇）
```

英语作文当前 Workflow：

```text
作文原文 + Rubric（评分标准）
        ↓
Evidence Agent（评分证据提取智能体）
        ↓
evidence.json（结构化评分证据）
        ↓
Scoring Agent（评分智能体）
        ↓
GradingResult（最终批改结果）
```

### Evidence Agent（评分证据提取智能体）指标

```text
Evidence Coverage（证据覆盖率）
Evidence Correctness（证据正确率）
Unsupported Evidence Rate（无依据证据率）
```

### Scoring Agent（评分智能体）指标

```text
Total Score MAE（总分平均绝对误差）
Dimension Score MAE（评分维度平均绝对误差）
Evidence Grounding（证据支撑度）
Feedback Quality（反馈质量）
```

其中：

```text
分数偏差
→ 程序直接计算

Evidence Grounding（证据支撑度） / Feedback Quality（反馈质量）
→ LLM Judge（大模型裁判）按 Rubric（评分标准）评分
```

# 4. Teacher Agent Benchmark

Teacher Agent Benchmark 固定为 100 个 Case，并直接按照当前业务复杂度 L1–L7 划分。

| Level | 场景 | Case 数 |
|---|---|---:|
| L1 | Direct Tool | 20 |
| L2 | Single Skill | 15 |
| L3 | Adaptive Multi-Tool | 15 |
| L4 | Skill + Tool | 15 |
| L5 | Multi-Skill / Single-Agent | 15 |
| L6 | Parallel Sub-Agents | 10 |
| L7 | Reviewer Agent | 10 |
| | 总计 | 100 |

L1–L7 不再只是执行架构，同时作为 Teacher Agent Benchmark 的正式分类体系。

---

## 4.1 L1 Direct Tool

目标：验证 Teacher Lead Agent 对明确事实 / 对象查询能否直接选择正确 Tool。

评测内容：

```text
Tool Selection Accuracy
Argument Generation Accuracy
Tool Execution Success Rate
Unnecessary Tool Call Rate
```

Case Gold 需要明确：

```text
expected_level
expected_tools
forbidden_tools
```

---

## 4.2 L2 Single Skill

目标：验证已有标准教学任务能否正确路由到对应 Skill，并完整执行 Skill SOP。

评测内容：

```text
Skill Routing Accuracy
Required Tool Coverage
Tool Sequence Correctness
Evidence Grounding Rate
Task Completion Rate
```

---

## 4.3 L3 Adaptive Multi-Tool

目标：验证没有匹配 Skill 时，Teacher Lead Agent 是否能够根据任务和中间结果自主组合多个 Tool。

评测内容：

```text
Required Tool Coverage
Unnecessary Tool Call Rate
Adaptive Decision Correctness
Argument Generation Accuracy
Task Completion Rate
```

重点检查：

```text
是否根据中间结果继续调用必要 Tool
是否提前停止导致证据不足
是否调用无关 Tool
```

---

## 4.4 L4 Skill + Tool

目标：验证一个 Skill 完成主体任务后，Teacher Lead Agent 能否继续调用额外 Tool 完成剩余需求。

评测内容：

```text
Skill Routing Accuracy
Tool Sequence Correctness
Intermediate Result Usage
Additional Tool Correctness
Task Completion Rate
```

---

## 4.5 L5 Multi-Skill / Single-Agent

目标：验证多个串行教学任务能否由 Teacher Lead Agent 通过 Multi-Skill 完成，并且不会无意义升级 Multi-Agent。

重点指标：

```text
Multi-Skill Routing Accuracy
Tool / Skill Sequence Correctness
Intermediate Result Usage
Task Completion Rate
Unnecessary Multi-Agent Rate
```

其中：

```text
Unnecessary Multi-Agent Rate
=
本应由 L1-L5 Single-Agent 完成
却启动 Sub-Agent 的运行次数
÷
所有 L1-L5 运行次数
```

这是 Single-Agent First 原则的核心量化指标。

---

## 4.6 L6 Parallel Sub-Agents

目标：验证班级级批量诊断、批量练习生成等场景下，Teacher Lead Agent 能否正确 Fan-out / Fan-in。

评测内容：

```text
Sub-Agent Delegation Accuracy
Fan-out Correctness
Fan-in Completeness
Unnecessary Agent Count
Parallel Speedup
Task Completion Rate
```

执行行为要求：

```text
先读取班级整体事实
↓
筛选重点学生 / 确定任务范围
↓
再 Fan-out
```

禁止：

```text
未筛选业务对象
↓
直接对全班机械启动大量 Agent
```

---

## 4.7 L7 Reviewer Agent

目标：验证 Reviewer 只在大型高价值教学方案中按需启动。

评测内容：

```text
Reviewer Trigger Precision
Reviewer Trigger Recall
Reviewer Correction Rate
Unnecessary Review Rate
```

Reviewer 不只评是否执行，还要评：

```text
该启动时是否启动
不该启动时是否保持关闭
发现错误后是否真正产生纠错收益
```

```json

  "case_id": "teacher_l5_001",
  "level": "L5",
  "query": "分析这次作业的问题，然后根据班级情况生成分层练习。",
  "snapshot_id": "teacher_eval_v1",
  "expected": {
    "execution_level": "L5",
    "skills": [
      "homework-review",

    ],
    "required_tools": [
      "get_homework_analysis",
      "get_question_analysis",
      "get_class_profile",
      "list_class_students",

      "search_question_bank"

```

# 7. 多次运行与稳定性评测

Teacher Agent 每个 Case 默认独立运行 5 次。

```text
100 Cases
×
5 Runs
=
500 次完整 Teacher Agent Run
```

单个 Case：

```text
Run 1 PASS
Run 2 PASS
Run 3 FAIL
Run 4 PASS
Run 5 PASS

Case Pass Rate
= 4 / 5
= 80%
```

多次运行用于区分：

```text
5 / 5
→ 稳定正确

0 / 5
→ 稳定失败，通常存在明确能力或实现问题

2 / 5、3 / 5、4 / 5
→ 具备能力但不稳定
→ 优先分析
```

对于时对时错的 Case，直接对比成功 Run 和失败 Run 的 Trace，定位执行差异。

最终总体指标固定为：

```text
Pass Rate
Average Quality Score
All-Pass Rate
```

其中：

```text
All-Pass Rate
=
5 / 5 全部成功的 Case 数
÷
总 Case 数
```

# 8. Trace 设计

Trace 是 Agent 评测的核心基础设施。

只保存最终回答不够，必须保存 Teacher Agent 从输入到最终结果的完整执行过程。

统一建立：

```text
agent_trace
```

字段：

| 字段 | 含义 |
|---|---|
| `id` | Trace ID |
| `eval_run_id` | 所属评测 Run |
| `case_id` | Benchmark Case |
| `session_id` | 一次 Agent Session |
| `conversation_id` | 会话 ID |
| `round` | 第几轮 |
| `agent_name` | Lead / Diagnosis / Practice / Reviewer |
| `agent_instance_id` | Agent 实例 |
| `parent_agent_instance_id` | 父 Agent |
| `step_type` | 当前执行类型 |
| `input_data` | 完整模型入参 |
| `output_data` | 完整模型输出 |
| `tool_name` | Tool 名称 |
| `tool_arguments` | Tool 参数 |
| `tool_result` | Tool 返回 |
| `skill_name` | 当前 Skill |
| `latency_ms` | 延迟 |
| `input_tokens` | 输入 Token |
| `output_tokens` | 输出 Token |
| `cost` | 调用成本 |
| `status` | success / error |
| `created_at` | 时间 |

`step_type` 固定为：

```text
LLM
TOOL
SKILL_START
SKILL_END
SUB_AGENT_START
SUB_AGENT_END
MEMORY_READ
MEMORY_WRITE
FINAL
```

每次和 LLM 的完整输入、完整输出都保留。

Tool Call 同样保留原始结构：

```json
{
  "tool_calls": [
    {
      "name": "get_student_profile",
      "arguments": {
        "student_id": "stu_001",
        "subject": "math"
      }
    }
  ]
}
```

Trace 后续承担：

```text
Process Evaluation
失败定位
成功 / 失败 Run 对比
成本与延迟统计
Multi-Agent 分析
```

# 9. Process Evaluation

一次 Teacher Agent Run 不全部交给 LLM Judge。

可以确定判断的执行行为全部由程序根据 Trace 自动计算。

自动检查：

```text
Execution Level 是否正确

Tool Selection 是否正确

Arguments 是否正确

Required Tool 是否全部调用

是否调用 Forbidden Tool

Skill 是否正确

Tool / Skill Sequence 是否满足依赖关系

是否错误启动 Sub-Agent

Sub-Agent 类型是否正确

Fan-out 是否符合业务范围

Fan-in 是否完整

Reviewer 是否正确触发

Memory 是否被错误当成业务事实源
```

形成：

```text
Process Check
PASS / FAIL
```

Tool / Skill / Multi-Agent 不再建设相互独立的评测系统，而统一通过 Teacher Agent Trace 自动计算不同能力指标。

# 10. LLM-as-Judge

Teacher Agent 最终输出是自然语言，不使用字符串完全匹配。

Judge 只负责最终回答质量评判，不替代 Process Evaluation。

固定四个 Rubric 维度：

| 维度 | 权重 | 评测内容 |
|---|---:|---|
| Factual Grounding | 40% | 业务事实是否正确、是否有事实支撑、是否编造 |
| Completeness | 25% | 用户要求的主要任务是否完整覆盖 |
| Relevance | 15% | 是否围绕教师请求回答、是否存在大量无关内容 |
| Analysis / Teaching Quality | 20% | 分析、诊断和教学建议是否合理 |

Judge 每个维度只能输出：

```text
0
1
2
3
4
5
```

不允许直接自由打 83、87、91 等连续分。

总质量分由程序计算：

```text
Quality Score
=
Factual Grounding × 0.40
+
Completeness × 0.25
+
Relevance × 0.15
+
Analysis / Teaching Quality × 0.20
```

---

## 10.1 Factual Grounding 档位

```text
5
核心和次要业务事实全部正确，有明确事实依据，无编造

4
核心事实正确，仅存在轻微、不影响结论的问题

3
主体事实正确，但存在部分次要事实偏差或证据不足

2
存在明显事实错误，但仍有部分主要结论正确

1
核心业务事实错误

0
明显编造不存在的学生、成绩、作业、知识点或其他业务事实
```

---

## 10.2 硬性 FAIL 条件

出现以下任意情况，本次 Run 直接 FAIL：

```text
编造不存在的学生

编造成绩

编造作业

编造知识点事实

核心业务事实错误

没有完成用户要求的主要任务

L1-L5 错误升级 Multi-Agent

L6 应该进行必要并行处理却完全没有执行所需 Sub-Agent

Tool 参数导致读取错误业务对象

最终回答与 Tool 返回事实冲突

Memory 被错误当成学生 / 班级业务事实源
```

最终 PASS 条件：

```text
Process Check = PASS

且

Factual Grounding >= 4

且

Quality Score >= 4.0
```

# 12. Diagnosis Agent

当一次 Run 判定为 FAIL，或一个 Case 无法达到 5 / 5 稳定通过时，进入失败诊断。

Diagnosis Agent 输入：

```text
User Query
+
Gold Expected
+
Gold Facts
+
Final Answer
+
完整 Trace
```

Diagnosis Agent 具备两个核心能力：

```text
读取指定 Eval Snapshot 的只读业务 Tool

读取指定 Run 完整 Trace
```

诊断过程：

```text
读取 Trace
↓
从 Round 1 开始逐步检查
↓
找到第一个与 Gold / 业务事实冲突的位置
↓
必要时通过只读 Tool 验证事实
↓
确认 Root Error
↓
归因 Root Cause
```

核心原则：

```text
不是找最后哪里表现错了

而是找第一次真正出错的位置
```

因为后续错误很可能只是前面错误的级联传播。


Diagnosis 最终统一输出：

```json

  "component": "get_student_profile.description",
  "reason": "...",
  "downstream_effect": "...",
  "suggested_fix": "..."
}
```

# 15. 最终评测闭环

完整评测体系最终固定为：

```text
400 Grading Cases
+
100 Teacher Agent Cases
×
5 Runs

↓

Frozen Evaluation Snapshot

↓

完整 Trace

↓

确定性 Process Check
+
LLM Judge

↓

Pass Rate
Quality Score
All-Pass Rate

↓

失败 / 不稳定 Case

↓

Diagnosis Agent

↓

第一次错误位置
+
四类 Root Cause
```

一句话概括：

> **先通过独立 Grading Benchmark 保证批改事实可靠，再基于冻结业务快照构建覆盖 L1–L7 的 Teacher Agent Benchmark；每个 Case 多次运行并保存完整 Trace，确定性的 Tool / Skill / Multi-Agent 行为由程序自动评测，开放式最终回答由 LLM Judge 按固定 Rubric 评分；失败后由 Diagnosis Agent 沿 Trace 找到第一次真正出错的位置并完成根因归类，最终形成能够衡量能力、稳定性、成本收益并指导系统优化的完整评测闭环。**
