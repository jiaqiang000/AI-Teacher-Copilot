# AI Teacher Copilot：08 评测驱动开发设计

## 1. 这份文档解决什么问题

01–07 已经定义了业务边界、GradingResult、学习画像、Teacher Agent Tools / Skills、Single-Agent First（单智能体优先）、DeerFlow `task` Multi-Agent、Reviewer 和 Memory 边界。

08 不再重复解释这些能力，而是把 01–07 中的重要设计决策转换成**可以执行、可以判定、可以回归的 Eval Case（评测用例）**。

核心关系固定为：

```text
01–07 Design Decision
        ↓
Eval Case
        ↓
Implementation
        ↓
Run Evaluation
        ↓
Result Pass + Behavior Pass
        ↓
Failed / Unstable Case
        ↓
DeerFlow RunEventStore + Langfuse Trace
        ↓
Evaluation Diagnosis
        ↓
Fix + Regression
```

当前阶段评测重点仍然是 Teacher Agent，同时为教师题目创建 / 作业发布与学生侧 Grading Workflow 保留必要 Smoke Evaluation。

```text
Teacher Agent
├── Tool Calling
├── Skill Routing
├── Adaptive Tool Use
├── Multi-Skill
├── DeerFlow task / Sub-Agent Delegation
├── Fan-out / Fan-in
├── Reviewer
└── Memory Boundary
```

学生侧 Grading Workflow 只保留必要 Smoke Evaluation，确保 Teacher Agent 读取到的 `GradingResult` 基本可信，同时对 `Submission` 异步批改状态、重复提交限制、重新提交重置、SSE 实时聊天框进度和页面刷新恢复做最小回归。

教师侧 Question Authoring 增加最小 Smoke Evaluation，验证数学 difficulty 在 Question 创建阶段确定、题库题复制到 Homework Question、英语作文固定使用系统 `EnglishEssayRubricV1` 且 `max_score = 20`，以及 `DRAFT → PUBLISHED` 的作业发布契约。

## 2. 评测执行闭环

每个 Teacher Eval Case 固定执行 5 次，用于同时衡量正确性和稳定性。

```text
Evaluation Case
        ↓
Teacher Agent 独立运行 5 次
        ↓
┌────────────────────┬────────────────────┐
↓                    ↓                    ↓
Result Judge       Behavior Check       Quality Judge
↓                    ↓                    ↓
Result Pass        Behavior Pass        Quality Score
└────────────────────┴────────────────────┘
                     ↓
              Case Evaluation Result
                     ↓
          Failed / Unstable Case
                     ↓
             Trace + Diagnosis
```

每次 Run 必须能够关联：

```text
User Query
Gold Facts
Expected Behavior
Forbidden Behavior
Final Answer
DeerFlow thread_id / run_id
Langfuse trace_id
Judge Result
```

### 2.1 为什么区分 Result Pass 和 Behavior Pass

Teacher Agent 既要验证“最终有没有完成教师任务”，也要验证 06–07 中的 Agent 架构设计有没有真正执行。

例如 L5 Multi-Skill 任务：

```text
最终答案完全正确
但是错误调用 task 启动了多个 Sub-Agent
```

应该得到：

```text
Result Pass   = PASS
Behavior Pass = FAIL

原因：
违反 Single-Agent First
出现 Unnecessary Multi-Agent
```

反过来，如果 Tool / Skill 调用符合预期，但最终把第 8 题错误率写错：

```text
Result Pass   = FAIL
Behavior Pass = PASS
```

因此：

```text
Result Evaluation
= 产品效果是否正确

Behavior Evaluation
= Agent 架构和执行方式是否正确

Trace / Diagnosis
= 为什么失败
```

### 2.2 评测观测基础设施：RunEventStore + Langfuse

当前评测固定采用两层观测能力，不再自己建设第二套完整 Agent Trace Runtime。

```text
第一层：DeerFlow RunEventStore
= 程序化 Behavior Check 的主要执行证据
= 记录 Run / Tool / Middleware / Sub-Agent 等本地事件

第二层：Langfuse
= LLM / Tool / Agent Trace 可视化
= Token / Cost / Latency 分析
= 成功 / 失败 Run 对比与人工排查
```

当前 AI Teacher Copilot **固定接入 Langfuse，不同时维护 LangSmith**。

DeerFlow 已经在 Lead Agent graph invocation root 统一挂载 tracing callbacks，因此本项目不再给每个 Tool / Model 手工重复挂 Langfuse Callback。运行环境只启用 DeerFlow 已有 Langfuse 配置：

```text
LANGFUSE_TRACING=true
LANGFUSE_PUBLIC_KEY=...
LANGFUSE_SECRET_KEY=...
LANGFUSE_BASE_URL=...
```

两层职责不同：

```text
RunEventStore
= Behavior Checker 可程序化读取的执行证据

Langfuse
= 更完整的可视化 Trace / Token / Cost / Latency / 调试视图
```

评测数据库只保存它们的关联 ID，不复制一份完整 raw trace 作为第二事实源。

### 3.3 ProfileAlgorithmV1 Gate

在生成 Student / Class Profile 和运行 Teacher Agent Benchmark 之前，必须先对 `ProfileAlgorithmV1` 做确定性算法门禁，不依赖 LLM。

#### P-PROFILE-001：performance 映射

```text
correct   → 1.0
partial   → 0.5
incorrect → 0.0
```

#### P-PROFILE-002：加权 mastery

```text
最近 easy correct
p = 1.0
w = 1.0 × 0.8 = 0.8

20 天前 medium partial
p = 0.5
w = 0.8 × 1.0 = 0.8

40 天前 hard incorrect
p = 0.0
w = 0.6 × 1.2 = 0.72
```

断言：

```text
mastery
= (1.0×0.8 + 0.5×0.8 + 0×0.72) / (0.8+0.8+0.72)
= 0.5172
```

英语：

```text
English difficulty = null
→ difficulty_weight = 1.0
```

#### P-PROFILE-003：trend

```text
recent - previous >= 0.10 → improving
recent - previous <= -0.10 → declining
其他 → stable
```

任一窗口不足 2 条观察：

```text
trend = null
```

#### P-PROFILE-004：weak_point

```text
attempt_count = 3 AND mastery < 0.60
→ true

attempt_count = 2 AND mastery = 0.20
→ false

attempt_count >= 3 AND mastery >= 0.60
→ false
```

#### P-PROFILE-005：recurring_error

对相同 `(error_code, knowledge_point_key)`：

```text
最近 28 天出现 1 次 → false
最近 28 天出现 2 次 → true
```

不同 `knowledge_point_key` 不得合并。

#### P-PROFILE-006：class aggregation

验证班级均值按“每学生先算个人值，再对学生平均”，而不是按 GradingResult 条数直接平均；并验证班级 weak point 的参与学生和阈值规则。

只有全部 `P-PROFILE-*` 通过，才能继续生成 `teacher_eval_v1` Profile。

### 3.4 AnalysisCalculationV1 Gate

#### P-ANALYSIS-001：Question 基础统计

3 个成功结果：

```text
A score.rate=0.40 errors=[SIGN_ERROR]
B score.rate=1.00 errors=[]
C score.rate=0.70 errors=[SIGN_ERROR]
```

断言：

```text
attempt_count = 3
avg_score_rate = 0.7000
error_student_count = 2
error_rate = 0.6667
SIGN_ERROR affected_student_count = 2
```

#### P-ANALYSIS-002：Homework 成绩与分布

```text
A: 26/30 = 0.8667
B: 16/30 = 0.5333
C: 27/30 = 0.9000
```

断言：

```text
graded_student_count = 3
avg_score_rate = 0.7667
below_60 = 1
from_60_to_79 = 0
from_80_to_89 = 1
from_90_to_100 = 1
```

部分批改学生不得进入 `graded_student_count / score_distribution`。

#### P-ANALYSIS-003：Homework Knowledge Point

```text
A correct + partial → 0.75
B incorrect + partial → 0.25
C correct → 1.00
```

断言：

```text
participating_student_count = 3
avg_performance = 0.6667
low_performance_student_count = 1
```

本次 low performance 不自动产生长期 weak point。

#### P-ANALYSIS-004：Homework Attention Students

验证 `LOW_HOMEWORK_SCORE / HIGH_ERROR_QUESTION` 即时规则，并断言不得因此修改长期 Class / Student Profile。

#### P-ANALYSIS-005：空值与 Representative Errors

无有效作答：

```text
avg_score_rate = null
error_rate = null
```

Representative Errors 必须来自真实 MySQL Error 事实，不由 LLM 生成。

### 3.5 Snapshot Gate

执行顺序：

```text
ProfileAlgorithmV1 Gate
+
AnalysisCalculationV1 Gate
↓
生成 Student / Class Profile
↓
Snapshot Tool Gate
↓
Teacher Agent Evaluation
```

Student / Class Profile Gold 必须从 `grading_results.json + profile_v1` 推导，不手工维护独立 `profiles.json` 第二事实源。

至少验证：

```text
get_class_profile(class_03, math)
→ 固定 Class Profile Gold

get_homework_analysis(class_03, hw_004)
→ completion_rate = 0.90
→ q008.question_no = 8
→ q008.error_rate = 0.6667
→ stu_011 HIGH_ERROR_QUESTION / q008

get_question_analysis(class_03, hw_004, q008)
→ question_no = 8
→ error_rate = 0.6667
→ SIGN_ERROR

get_student_profile(stu_003, math)
→ weak_point / recurring_error / declining 正确

get_student_profile(stu_011, math)
→ 不得错误产生 weak_point / recurring_error

search_question_bank(... transposition, easy)
→ 只返回匹配的 QuestionBankItem
```

任一 Gate 不通过则停止 Teacher Agent Evaluation。

```jsonc
{
  "case_id": "T-L5-001",
  "level": "L5",
  "query": "...",
  "snapshot_id": "teacher_eval_v1",
  "gold_facts": {},
  "expected_behavior": {
    "execution_level": "L5",
    "skills": [],
    "required_tools": [],
    "required_subagents": []
  },
  "forbidden_behavior": [],
  "result_requirements": []
}
```

职责分开：

```text
Gold Facts
= 最终答案依据

Expected Behavior
= 正常应该如何执行

Forbidden Behavior
= 不能出现的架构行为

Result Requirements
= 用户真正要求完成什么
```

## 5. Teacher Agent Core Evaluation Cases

### 5.0 Business Object Resolution

#### T-OBJ-001：学生姓名唯一匹配

```text
教师：“张三有哪些薄弱知识点？”
current_class_id = class_03
```

Expected：

```text
list_class_students(class_03)
↓
唯一匹配 stu_003
↓
get_student_profile(stu_003, math)
```

Forbidden：

```text
ask_clarification
直接猜 student_id = stu_003
task Tool Call
```

#### T-OBJ-002：同名学生需要教师确认

```text
教师：“看看王强最近数学怎么样。”
current_class_id = class_03
```

Gold：`stu_026 / stu_027` 两个王强。

Expected：

```text

↓
发现两个候选
↓
ask_clarification
↓
教师选择
↓
才继续正式 Tool / Skill
```

Forbidden：自动选任一候选或跳过 HITL。

Gold：


```text

```

Forbidden：

```text

```

#### T-L1-002：查询第 8 题错误率


Expected：`list_class_homeworks(class_03, math, 本周范围)`；不得用 `get_homework_analysis` 代替对象发现。

Expected：`list_class_students(class_03)`；必须返回真实 30 名学生，不能根据 `student_count` 猜身份。

```text
必要时修正
```

Reviewer 至少检查重点学生依据、长期薄弱证据、练习知识点和难度、事实冲突与遗漏。

#### T-L7-002：普通任务不应该触发 Reviewer

“分析一下张三最近数学学习情况。”只执行 `student-diagnosis`，Forbidden：`task(subagent_type="reviewer")`。

共同计算 Reviewer Trigger Precision / Recall / Unnecessary Review Rate。

### 5.8 Memory Evaluation

#### T-MEM-001：Memory 影响表达，不改变业务事实

Memory：

```text
“以后做作业分析时先告诉我最值得课堂讲的三个问题，不用写太长。”
```

业务事实仍从 Tool 获取，Memory 只改变回答组织方式。

#### T-MEM-002：Memory 不能覆盖当前业务事实

即使 Memory 有“李四数学一直比较差”，当前 Tool Gold 表明李四未形成长期 weak / recurring，则最终事实必须以 `get_student_profile + get_student_grading_history` 为准。

## 6. Result Judge

最终输出是自然语言，不使用字符串完全匹配。

Judge 输入：

```text
User Query
Gold Facts
Result Requirements
Agent Final Answer
Evaluation Rubric
```

### 6.1 Result Pass

核心业务事实正确 + 核心结论正确 + 完成主要任务 + 无明显编造，则 PASS。

核心数值、业务对象、核心结论错误，明显编造或遗漏核心任务，则 FAIL。

### 6.2 Quality Score

| 维度 | 权重 |
|---|---:|
| Correctness | 40% |
| Completeness | 25% |
| Relevance | 15% |
| Analysis / Teaching Quality | 20% |

每个维度只允许 `0 / 1 / 2 / 3 / 4 / 5`。

```text
Quality Score
= Correctness × 40%
+ Completeness × 25%
+ Relevance × 15%
+ Analysis / Teaching Quality × 20%
```

## 7. Behavior Check：基于 DeerFlow 真实执行证据

Behavior Pass 不交给 LLM 自由判断，而是由 `EvalTraceAdapter` 把 DeerFlow RunEventStore 中的真实事件投影成 `EvalTraceView` 后程序化检查。

### 7.1 主要过程指标

```text
Execution Level Accuracy
Business Object Resolution Correctness
Tool Selection Accuracy
Argument Generation Accuracy
Tool Execution Success Rate
Skill Routing Accuracy
Required Tool Coverage
Tool Sequence Correctness
Adaptive Decision Correctness
Unnecessary Tool Call Rate
Unnecessary Multi-Agent Rate
Sub-Agent Delegation Accuracy
Fan-out Correctness
Fan-in Completeness
Reviewer Trigger Precision / Recall
Memory Boundary Correctness
```

### 7.2 真实行为如何识别

Tool：从 DeerFlow Tool call / result 事件和消息证据识别 Tool 名称、参数、返回。

Sub-Agent：

```text
task Tool Call
+
subagent.start / subagent.step / subagent.end
```

识别真实 `subagent_type / task_id / lifecycle`。因此 Eval Case 不再使用虚构的 `spawn_sub_agent / invoke_reviewer` 操作名。

Skill：

```text
显式 /skill
→ middleware:skill_activation

模型主动使用 Skill
→ 读取 .../<skill-name>/SKILL.md / skill_context
```

`EvalTraceAdapter` 统一投影成：

```text
skill_loaded = student-diagnosis
```

不额外发明 `SKILL_START / SKILL_END` 作为另一套 Source of Truth。

Memory：RunEventStore 的 `context:memory` 用于证明本轮存在 Memory Context；Memory 是否错误覆盖事实仍结合 Tool Trace + Gold + Final Answer 判断。

### 7.3 并行是否真的发生

L6 不能因为“调用了多个 Worker”就判定并行成功。

`EvalTraceAdapter` 根据不同 `task_id` 的：

```text
subagent.start.created_at
subagent.end.created_at
```

判断 Sub-Agent 生命周期是否发生重叠，得到：

```text
Parallelism Used
Max Concurrent Sub-Agents
```

真正存在生命周期重叠才算使用并行。

### 7.4 Behavior Pass 规则

满足 required Tool / Skill / Sub-Agent、关键参数、执行顺序和并行 / Reviewer 等断言，且 forbidden behavior 未出现，则 Behavior PASS。

Result Pass 和 Behavior Pass 始终独立展示。

## 8. 多次运行后的核心指标

每个 Core Case 默认独立运行 5 次。

```text
Case Result Pass Rate
= 该 Case 5 次 Result PASS 次数 / 5

Overall Result Pass Rate
= 所有 Case Result Pass Rate 平均
```

Behavior Pass Rate 同理。

一级指标：

```text
Result Pass Rate
Behavior Pass Rate
Average Quality Score
All-Pass Rate
```

`5/5` 稳定通过；`0/5` 系统性失败；`2/5、3/5、4/5` 视为不稳定，高优先级分析。成功和失败 Run 的 RunEventStore 投影与 Langfuse Trace 应一起比较。

## 9. Trace 与失败诊断

### 9.1 不再建立第二份 raw agent_trace Source of Truth

DeerFlow 已经维护 Run Event Stream，因此当前项目不再建立一张把 LLM / Tool / Skill / Sub-Agent / Memory 全部重复写一遍的 `agent_trace` 原始表。

执行证据链固定为：

```text
DeerFlow RunEventStore
        ↓
EvalTraceAdapter【本项目】
        ↓
EvalTraceView
        ↓
Behavior Checker
        ↓
Eval Judgement
```

本项目新增：

```text
evals/
└── runtime/
    └── eval_trace_adapter.py
```

`EvalTraceAdapter` 只做读模型转换，不成为新的 raw trace 存储。

至少统一抽取：

```text
run lifecycle
tool calls + arguments + results
skill activation / SKILL.md load
subagent task id / type / lifecycle
fan-out / fan-in evidence
memory context evidence
final answer
```

DeerFlow RunEventStore 已经包含 `run.start / run.end / llm.ai.response / llm.tool.result / context:memory / middleware:* / subagent.start / subagent.step / subagent.end` 等事件。Behavior Checker 读取这些真实证据，而不是要求业务 Agent 主动额外上报“我刚刚用了哪个 Skill”。

### 9.2 Langfuse Trace

Langfuse 与 RunEventStore 是并行观测管线，不从 RunEventStore 二次生成。

```text
DeerFlow Lead Agent graph invocation root
        ↓
build_tracing_callbacks()
        ↓
Langfuse CallbackHandler
        ↓
Langfuse Trace
```

主要用于：

```text
查看完整模型调用链
查看 Tool / Agent Span
Token Usage
Cost
Latency
成功 / 失败 Run 对比
人工排查 Prompt / Model 行为
```

评测代码不依赖 Langfuse 网络查询才能判 Behavior Pass；核心自动行为检查以 DeerFlow RunEventStore 为主，这样本地回归可稳定运行。

### 9.3 Evaluation Diagnosis Agent

触发条件：

```text
Result Pass = FAIL
OR Behavior Pass = FAIL
OR 同一 Case 5 次出现 2/5、3/5、4/5
```

Diagnosis Agent 保留，但实现为**评测专用 DeerFlow Custom Agent**：

```text
eval-diagnoser
```

它不加入：

```text
teacher-copilot.allowed_subagents
```

因此生产 Teacher Lead Agent 不会把正常教学任务委派给它；只由 Evaluation Runner 在失败 / 不稳定 Run 后单独调用。

输入：

```text
User Query
Gold Facts
Expected / Forbidden Behavior
Judge Result
Final Answer
EvalTraceView
Langfuse trace reference
```

必要时可使用只读 Evaluation Snapshot Tool 查证事实。

诊断目标是找到：

```text
第一次真正从正确轨道偏离的位置
```

根因固定为：

```text
MODEL
PROMPT_SCHEMA
TOOL_DATA
AGENT_FRAMEWORK
```

输出：

```jsonc
{
  "root_error_round": 3,
  "root_error_agent": "TeacherLeadAgent",
  "category": "PROMPT_SCHEMA",
  "component": "get_student_profile.description",
  "reason": "...",
  "downstream_effect": "...",
  "suggested_fix": "..."
}
```

## 附录 B：Grading Smoke Evaluation

### B.1 Submission 异步批改契约

#### G-SUB-001：第一次提交与正常状态转换

```text
不存在 Submission
→ PENDING / QUEUED
→ RUNNING
→ SUCCEEDED / COMPLETED
```

SUCCEEDED 前必须已写入当前有效 GradingResult；同一 `student_id + question_id` 仅一个当前 Submission。

#### G-SUB-002：失败状态

不可恢复异常：`RUNNING → FAILED`，保存 `error_code / error_message`；FAILED 后可复用同一 submission_id 重新提交。

#### G-SUB-003：批改中禁止重复提交

PENDING / RUNNING 时再次提交：HTTP 409 + `SUBMISSION_GRADING_IN_PROGRESS`；不得创建新 Submission / Workflow。

#### G-SUB-004：完成后复用 Submission 重交

SUCCEEDED / FAILED 后：保持 submission_id，更新 image_url，删除旧 OCRResult / GradingResult，重置状态和时间字段，重新执行完整 Workflow。

#### G-SUB-005：数学 current_stage 顺序

```text
QUEUED → OCR → PARSING → GRADING → ASSEMBLING_RESULT → COMPLETED
```

GRADING 直接读取已保存 Question.difficulty。

#### G-SUB-006：英语 current_stage 顺序

同一通用阶段；两个评分阶段均 DeepSeek v4 Flash。

#### G-SUB-007：SSE 实时进度事件

`grading.stage.started / completed` 必须包含 submission_id，前端正确更新 active / complete；未开始为 pending；Grading SSE 不依赖 task_id。

#### G-SUB-008：DeerFlow Chat 实时过程展示

```text
Student Image Message
↓
GradingProgressMessage
```

至少展示图片上传 / OCR / PARSING / GRADING / ASSEMBLING_RESULT。

必须由：

```text
grading.* Event
↓
gradingEventToProgressUpdate()
↓
complete / active / pending / failed
↓
GradingProgressMessage
↓
DeerFlow ChainOfThought UI primitives
```

不得把 OCR / PARSING / GRADING 伪装成 `AIMessage / reasoning / tool_calls`。

#### G-SUB-009：页面刷新恢复

```text

↓
status / current_stage
↓
恢复步骤
↓
重新订阅 events
```

不得刷新后回 QUEUED 或重新启动 Workflow。StreamBridge replay 是体验增强，不是状态事实源。

#### G-SUB-010：最终结果同一聊天上下文展示

`grading.completed` 后 Submission 必须 SUCCEEDED / COMPLETED，同一 Chat 时间线展示当前 GradingResultMessage，不能展示已删除旧结果。
