# AI Teacher Copilot：08 评测驱动开发设计

## 1. 这份文档解决什么问题

01–07 已经定义了业务边界、GradingResult、学习画像、Teacher Agent Tools / Skills、Single-Agent First（单智能体优先）、Multi-Agent（多智能体）、Reviewer（审核智能体）和 Memory（记忆）边界。

08 不再重复解释这些能力，而是把 01–07 中的重要设计决策转换成**可以执行、可以判定、可以回归的 Eval Case（评测用例）**。

核心关系固定为：

```text
01–07 Design Decision（设计决策）
        ↓
Eval Case（评测用例）
        ↓
Implementation（功能实现）
        ↓
Run Evaluation（运行评测）
        ↓
Result Pass + Behavior Pass（结果通过 + 行为通过）
        ↓
Failed / Unstable Case（失败 / 不稳定用例）
        ↓
Trace + Diagnosis Agent（执行链路 + 诊断智能体）
        ↓
Fix + Regression（修复 + 回归）
```

因此当前阶段的评测重点仍然是 Teacher Agent，同时为教师题目创建 / 作业发布与学生侧 Grading Workflow 保留必要 Smoke Evaluation（冒烟评测）。

```text
Teacher Agent（教师智能体）
├── Tool Calling（工具调用）
├── Skill Routing（技能路由）
├── Adaptive Tool Use（自适应工具使用）
├── Multi-Skill（多技能组合）
├── Sub-Agent Delegation（子智能体委派）
├── Fan-out / Fan-in（并行扇出 / 结果汇总）
├── Reviewer（审核智能体）
└── Memory Boundary（记忆边界）
```

学生侧 Grading Workflow（批改工作流）只保留必要的 Smoke Evaluation，确保 Teacher Agent 读取到的 `GradingResult` 基本可信，同时对已经固定的 `Submission` 异步批改状态、重复提交限制、重新提交重置、SSE 实时聊天框进度和页面刷新恢复做最小回归。

教师侧 Question Authoring（题目创建）则增加最小 Smoke Evaluation，验证：数学 difficulty 在 Question 创建阶段确定、题库题复制到 Homework Question、英语作文固定使用系统 `EnglishEssayRubricV1` 且 `max_score = 20`，以及 `DRAFT → PUBLISHED` 的作业发布契约。

## 2. 评测执行闭环

每个 Teacher Eval Case（教师评测用例）固定执行 5 次，用于同时衡量正确性和稳定性。

```text
Evaluation Case（评测用例）
        ↓
Teacher Agent 独立运行 5 次
        ↓
┌────────────────────┬────────────────────┐
↓                    ↓                    ↓
Result Judge       Behavior Check       Quality Judge
结果评判             行为检查              质量评判
↓                    ↓                    ↓
Result Pass        Behavior Pass        Quality Score
结果是否正确          架构行为是否正确        回答质量
└────────────────────┴────────────────────┘
                     ↓
              Case Evaluation Result
                     ↓
          Failed / Unstable Case
                     ↓
             Trace + Diagnosis
```

每次 Run（运行）必须保存：

```text
User Query（用户问题）
Gold Facts（标准业务事实）
Expected Behavior（期望执行行为）
Forbidden Behavior（禁止行为）
Final Answer（最终回答）
Complete Trace（完整执行链路）
Judge Result（裁判结果）
```

### 2.1 为什么区分 Result Pass 和 Behavior Pass

Teacher Agent 既要验证“最终有没有完成教师任务”，也要验证 06–07 中的 Agent 架构设计有没有真正执行。

例如 L5 Multi-Skill（多技能串行）任务：

```text
最终答案完全正确
但是错误启动了 5 个 Sub-Agent
```

应该得到：

```text
Result Pass（结果通过）   = PASS
Behavior Pass（行为通过） = FAIL

原因：
违反 Single-Agent First（单智能体优先）
出现 Unnecessary Multi-Agent（不必要的多智能体升级）
```

反过来：

```text
Tool / Skill 调用全部符合预期
但是最终把第 8 题错误率写错
```

应该得到：

```text
Result Pass（结果通过）   = FAIL
Behavior Pass（行为通过） = PASS
```

因此：

```text
Result Evaluation（结果评测）
= 产品效果是否正确

Behavior Evaluation（行为评测）
= Agent 架构和执行方式是否正确

Trace / Diagnosis（链路 / 诊断）
= 为什么失败
```

三者不混在一起。

## 3. Teacher Evaluation Snapshot：先构造一个固定的教师评测世界

Teacher Agent 的 Tool、Skill、Multi-Agent 和 Judge 都依赖业务事实。如果底层数据一直变化，就无法稳定判断 Agent 是否真正进步。

因此第一版固定构造：

```text
teacher_eval_v1（教师智能体冻结评测快照）
```

### 3.1 评测世界

第一版统一使用：

```text
Teacher（教师）
├── teacher_id: teacher_01
└── name: 王老师

Class（班级）
├── class_id: class_03
├── name: 八三班
├── subject: math
└── student_count: 30

时间范围
└── 最近 4 周

Homework（作业）
├── hw_001
├── hw_002
├── hw_003
└── hw_004
```

评测数据库中真实保存完整的 30 名学生、4 周作业、Question（题目）、Submission（提交）和 GradingResult（批改结果），并固定一组 Question Bank Fixture（题库评测数据）供练习检索相关 Case 使用。

08 文档只固定最关键、会被多个 Eval Case 复用的 Gold Facts（标准业务事实）。

### 3.2 第一批固定 Gold Facts

#### 班级事实

```text

student_count（学生人数） = 30

长期主要薄弱知识点：
1. math.linear_equation.transposition（移项）
2. math.function.graph（函数图像）

主要共性错误：
1. SIGN_ERROR（符号错误）
2. GRAPH_READING_ERROR（函数图像读取错误）
```

#### 本周作业事实

```text
本周作业：
hw_003
hw_004

submitted_student_count（提交人数） = 27
completion_rate（完成率） = 0.90

hw_004 最高错题：
question_id（题目 ID） = q008
question_no（题号） = 8

wrong_student_count（错误人数） = 18
error_rate（错误率） = 0.667

```

#### 重点学生事实

```text

├── stu_003 张三
├── stu_011 李四
├── stu_018 王五
└── stu_024 赵六
```

其中第一版重点固定两个有明显对照关系的学生：

```text

├── weak_point（长期薄弱点）
│   └── math.linear_equation.transposition（移项）

├── hw_004 中出现一次 SIGN_ERROR
├── recurring_error（重复错误） = false
└── trend（趋势） = stable（稳定）
```

这里故意构造：

```text

= 长期薄弱 + 重复错误

李四
= 单次偶发错误
```

用于验证 Teacher Agent 是否真正遵守 03–05 的业务规则：

> 单次错误不能直接推导为长期薄弱知识点。

#### 对象解析测试事实

为了验证教师自然语言中的业务对象能否稳定解析，固定增加以下对象关系：

```text
class_03 中：

stu_003 张三
= 姓名唯一

stu_026 王强
stu_027 王强
= 两个同名学生，用于验证 Human-in-the-Loop
```

这两个“王强”只是对象解析测试数据，不改变班级总人数 `student_count = 30`，也不参与前面的重点学生 Gold Facts。

### 3.3 Snapshot Gate：跑 Agent 之前先验证事实底座

Teacher Agent Benchmark（教师智能体评测）运行前，必须先通过 Snapshot Gate（快照事实门禁）。

至少验证：

```text
get_class_profile(class_03, math)
→ 返回固定 Class Profile Gold

get_homework_analysis(class_03, hw_004)
→ completion_rate = 0.90
→ q008 为最高错题
→ q008.question_no = 8

get_question_analysis(class_03, hw_004, q008)
→ question_no = 8
→ error_rate = 0.667
→ common_error = SIGN_ERROR

get_student_profile(stu_003, math)
→ weak_point = 移项
→ recurring_error = SIGN_ERROR
→ trend = declining

get_student_profile(stu_011, math)
→ 不得把本次单次 SIGN_ERROR 直接标记为长期 recurring_error

search_question_bank(math, [math.linear_equation.transposition], difficulty=easy)
→ 只返回 Question Bank Fixture 中符合条件的 QuestionBankItem
→ 不返回 Homework Question
```

如果 Snapshot Gate 不通过：

```text
停止 Teacher Agent Evaluation
```

因为此时 Agent 后续错误无法和数据层错误区分。

## 4. Teacher Eval Case 的统一结构

所有 Teacher Agent Case 使用统一结构：

```jsonc
{
  "case_id": "T-L5-001",                // case_id（评测用例 ID）
  "level": "L5",                        // level（业务复杂度等级）
  "query": "...",                       // query（教师请求）
  "snapshot_id": "teacher_eval_v1",     // snapshot_id（冻结评测快照 ID）

  "gold_facts": {                        // gold_facts（最终回答依据的标准业务事实）
    "...": "..."
  },

  "expected_behavior": {                 // expected_behavior（期望执行行为）
    "execution_level": "L5",
    "skills": [],
    "required_tools": [],
    "required_subagents": []
  },

  "forbidden_behavior": [],              // forbidden_behavior（禁止出现的行为）

  "result_requirements": []              // result_requirements（最终回答必须完成的内容）
}
```

四部分职责必须分开：

```text
Gold Facts（标准事实）
= 最终答案应该基于什么事实

Expected Behavior（期望行为）
= Agent 正常情况下应该怎么执行

Forbidden Behavior（禁止行为）
= 绝对不希望出现的架构行为

Result Requirements（结果要求）
= 用户真正要求完成什么
```

自然语言最终答案不要求和 Gold 文本完全一致。

## 5. Teacher Agent Core Evaluation Cases

第一阶段先建设一组小而明确的 Core Set（核心评测集），直接驱动 Tool、Skill 和 Agent 开发。

后续可以扩充表达方式、边界数据和异常 Case，但每新增一个重要设计能力，必须先补对应 Eval Case。

### 5.0 Business Object Resolution（业务对象解析）

对象解析 Case 只验证正式 Tool / Skill 调用前的参数准备，不把对象解析本身视为新的业务复杂度层级。

#### T-OBJ-001：学生姓名唯一匹配

```text
教师：
“张三有哪些薄弱知识点？”

Current Context（当前上下文）：
current_class_id = class_03
```

Gold Facts：

```text
class_03 中只有一个名为“张三”的学生：
stu_003 张三
```

Expected Behavior：

```text
execution_level = L1

list_class_students(class_03)
        ↓
唯一匹配 stu_003
        ↓
get_student_profile(stu_003, math)
```

Forbidden Behavior：

```text
ask_clarification
直接根据“张三”猜 student_id = stu_003
spawn_sub_agent
```

这个 Case 验证：

```text
能唯一确定
→ 自动继续
→ 不打扰教师
```

---

#### T-OBJ-002：同名学生需要教师确认

```text
教师：
“看看王强最近数学怎么样。”

Current Context（当前上下文）：
current_class_id = class_03
```

Gold Facts：

```text
class_03 中存在两个候选：
stu_026 王强
stu_027 王强
```

Expected Behavior：

```text
list_class_students(class_03)
        ↓
发现两个同名候选
        ↓
ask_clarification
        ↓
向教师展示候选并等待选择
        ↓
教师选择后才允许继续正式 Tool / Skill
```

Forbidden Behavior：

```text
自动选择 stu_026
自动选择 stu_027
编造其他 student_id
跳过教师确认直接继续
```

这个 Case 重点验证 DeerFlow Human-in-the-Loop 是否只在真正存在歧义时触发。

## 6. Result Judge：最终结果怎么判

Teacher Agent 最终输出是自然语言，不能使用字符串完全匹配。

Judge 输入：

```text
User Query（用户问题）
+
Gold Facts（标准业务事实）
+
Result Requirements（结果要求）
+
Agent Final Answer（Agent 最终回答）
+
Evaluation Rubric（评分标准）
```

### 6.1 Result Pass

客观 Teacher Task（教师任务）的核心硬指标是：

```text
Result Pass（结果通过）
```

满足：

```text
核心业务事实正确
+
核心结论正确
+
完成用户明确要求的主要任务
+
不存在明显业务事实编造
```

则：

```text
Result Pass = PASS
```

以下直接：

```text
Result Pass = FAIL
```

情况包括：

```text
核心数值错误
核心业务对象错误
核心结论错误
明显编造不存在的学生 / 作业 / 分数 / 知识点
遗漏用户要求的核心任务
最终回答与 Gold Facts 发生关键冲突
```

### 6.2 Quality Score

Result Pass 解决“对不对”，但无法完整表达“答得好不好”。

统一采用 0–5 档位 Rubric（评分标准）：

| 维度 | 权重 | 评什么 |
|---|---:|---|
| Correctness（正确性） | 40% | 数据、事实和核心结论是否正确，有没有编造 |
| Completeness（完整性） | 25% | 用户要求的内容是否完整覆盖 |
| Relevance（相关性） | 15% | 是否跑题、是否存在大量无关内容 |
| Analysis / Teaching Quality（分析 / 教学质量） | 20% | 诊断、解释和教学建议是否合理 |

Judge 每个维度只允许输出：

```text
0 / 1 / 2 / 3 / 4 / 5
```

不允许直接自由输出 83、87、91 这类连续分。

Correctness（正确性）档位固定为：

| 分数 | 标准 |
|---:|---|
| 5 | 核心和次要业务事实、核心结论全部正确，无编造 |
| 4 | 核心事实和结论正确，仅有轻微非关键偏差 |
| 3 | 主体正确，但部分次要事实或结论有明显偏差 |
| 2 | 存在明显错误，但仍有部分主要结果正确 |
| 1 | 核心业务事实或核心结论错误 |
| 0 | 明显编造不存在的业务事实 |

程序计算：

```text
Quality Score（质量分）
=
Correctness × 40%
+
Completeness × 25%
+
Relevance × 15%
+
Analysis / Teaching Quality × 20%
```

## 7. Behavior Check：执行行为怎么判

Behavior Pass 直接基于 Trace 程序化检查，不交给 LLM 自由判断。

检查内容来自 Case 中的：

```text
Expected Behavior（期望行为）
+
Forbidden Behavior（禁止行为）
```

### 7.1 主要过程指标

```text
Execution Level Accuracy（执行层级准确率）
Business Object Resolution Correctness（业务对象解析正确率）
Tool Selection Accuracy（工具选择准确率）
Argument Generation Accuracy（参数生成准确率）
Tool Execution Success Rate（工具执行成功率）
Skill Routing Accuracy（Skill 路由准确率）
Required Tool Coverage（必需 Tool 覆盖率）
Tool Sequence Correctness（Tool 调用顺序正确率）
Adaptive Decision Correctness（自适应决策正确率）
Unnecessary Tool Call Rate（不必要 Tool 调用率）
Unnecessary Multi-Agent Rate（不必要多智能体升级率）
Sub-Agent Delegation Accuracy（子智能体委派准确率）
Fan-out Correctness（并行扇出正确性）
Fan-in Completeness（结果汇总完整率）
Reviewer Trigger Precision（Reviewer 触发精确率）
Reviewer Trigger Recall（Reviewer 触发召回率）
Memory Boundary Correctness（Memory 边界正确率）
```

### 7.2 Behavior Pass 规则

单次 Run 满足：

```text
required Tool / Skill / Sub-Agent 全部满足
+
关键参数正确
+
关键执行顺序正确
+
forbidden behavior 未出现
```

则：

```text
Behavior Pass = PASS
```

注意：

```text
Behavior Pass
不覆盖 Result Pass

Result Pass
也不覆盖 Behavior Pass
```

最终报告同时展示两者。

## 8. 多次运行后的核心指标

每个 Core Case 默认独立运行 5 次。

例如：

```text
Run 1 → PASS
Run 2 → PASS
Run 3 → FAIL
Run 4 → PASS
Run 5 → PASS
```

则该 Case：

```text
Case Result Pass Rate（单题结果通过率） = 4 / 5 = 80%
```

### 8.1 一级指标

Teacher Agent 最终首先看：

```text
Result Pass Rate（结果通过率）
→ 对不对

Behavior Pass Rate（行为通过率）
→ 架构执行对不对

Average Quality Score（平均质量分）
→ 好不好

All-Pass Rate（全对率 / 稳定通过率）
→ 稳不稳
```

Result Pass Rate 先按每个 Case 计算，再跨 Case 平均：

```text
Case Result Pass Rate
= 该 Case 5 次中 Result PASS 的次数 / 5

Overall Result Pass Rate
= 所有 Case Result Pass Rate 的平均值
```

Behavior Pass Rate 同理。

All-Pass Rate：

```text
5 / 5 Result PASS 的 Case 数
÷
全部 Case 数
```

### 8.2 不稳定 Case

重点关注：

```text
5 / 5
→ 稳定通过

0 / 5
→ 系统性失败

2 / 5、3 / 5、4 / 5
→ 不稳定，高优先级分析
```

对于不稳定 Case，把成功 Run 和失败 Run 的 Trace 放在一起比较。

## 9. Trace 与失败诊断

每次 Teacher Agent Run 必须完整保存 Trace。

### 9.1 agent_trace

核心字段：

| 字段 | 含义 |
|---|---|
| `eval_run_id` | 评测运行 ID |
| `case_id` | 评测用例 ID |
| `session_id` | 会话 ID |
| `round` | 第几轮 |
| `agent_name` | Agent 名称 |
| `agent_instance_id` | Agent 实例 ID |
| `parent_agent_instance_id` | 父 Agent 实例 ID |
| `step_type` | 步骤类型 |
| `input_data` | 模型输入 |
| `output_data` | 模型输出 |
| `tool_name` | Tool 名称 |
| `tool_arguments` | Tool 参数 |
| `tool_result` | Tool 返回 |
| `skill_name` | Skill 名称 |
| `latency_ms` | 延迟 |
| `input_tokens` | 输入 Token |
| `output_tokens` | 输出 Token |
| `cost` | 成本 |
| `status` | 状态 |

`step_type` 固定：

```text
LLM（模型调用）
TOOL（工具调用）
SKILL_START（Skill 开始）
SKILL_END（Skill 结束）
SUB_AGENT_START（Sub-Agent 开始）
SUB_AGENT_END（Sub-Agent 结束）
MEMORY_READ（Memory 读取）
MEMORY_WRITE（Memory 写入）
FINAL（最终回答）
```

### 9.2 Diagnosis Agent

触发条件：

```text
Result Pass = FAIL

或

Behavior Pass = FAIL

或

同一 Case 5 次运行出现 2 / 5、3 / 5、4 / 5
```

Diagnosis Agent 输入：

```text
User Query（用户问题）
Gold Facts（标准事实）
Expected / Forbidden Behavior（期望 / 禁止行为）
Judge Result（裁判结果）
Final Answer（最终回答）
Complete Trace（完整执行链路）
```

诊断过程：

```text
从 Round 1 开始检查 Trace
        ↓
找到可疑决策
        ↓
必要时使用只读 Evaluation Snapshot Tool 查证事实
        ↓
定位第一次真正发生错误的位置
        ↓
确定 Root Error（根源错误点）
        ↓
归因 Root Cause（根因）
```

重点不是最后哪一步表现错误，而是：

```text
第一次从正确轨道偏离发生在哪里？
```

根因固定为四类：

```text
MODEL（模型能力问题）
PROMPT_SCHEMA（Prompt / Schema 问题）
TOOL_DATA（Tool / 数据问题）
AGENT_FRAMEWORK（Agent 框架问题）
```

输出：

```jsonc
{
  "root_error_round": 3,                          // root_error_round（首次错误轮次）
  "root_error_agent": "TeacherLeadAgent",         // root_error_agent（首次出错 Agent）
  "category": "PROMPT_SCHEMA",                    // category（根因类别）
  "component": "get_student_profile.description", // component（问题组件）
  "reason": "...",                                // reason（错误原因）
  "downstream_effect": "...",                     // downstream_effect（后续影响）
  "suggested_fix": "..."                          // suggested_fix（修复方向）
}
```

## 10. 评测驱动开发怎么执行

以后不是功能全部写完再补评测，而是：

```text
新增 / 修改一个 Teacher Agent 能力
        ↓
先确定对应业务场景
        ↓
先写 Eval Case
        ↓
固定 Gold Facts / Expected Behavior
        ↓
实现 Tool / Skill / Prompt / Agent
        ↓
运行目标 Case × 5
        ↓
通过后运行 Core Regression（核心回归）
        ↓
失败则看 Trace + Diagnosis
```

典型对应关系：

| 01–07 设计 | 08 必须存在的评测 |
|---|---|
| Teacher Homework Authoring + Question Bank | A-001 ～ A-005 + Question Bank Fixture |
| EnglishEssayRubricV1 | A-005 + G-ENG-001 |
| Business Object Resolution + HITL | T-OBJ-001 / T-OBJ-002 / T-L1-002 |
| Tool Contract | L1 Tool Selection / Argument Case |
| `student-diagnosis` | T-L2-001 / T-L2-002 |
| `class-learning-analysis` | T-L2-003 |
| `homework-review` | T-L2-004 |
| Adaptive Tool Calling | T-L3-001 / T-L3-002 |
| Skill + Tool | T-L4 Cases |
| Single-Agent First | T-L5 Cases |
| Parallel Sub-Agents | T-L6 Cases |
| Reviewer | T-L7 正负 Case |
| Memory 不是业务事实源 | T-MEM-002 |

核心规则：

> **01–07 每增加一个重要设计约束，08 至少增加一个能够证明该约束真正实现的 Eval Case。**

## 11. 对照与消融实验

常规回归评测回答“有没有实现正确”，对照实验回答“为什么这样设计”。

当前 Teacher Agent 重点做 3 组实验。

### 11.1 L5：Single-Agent vs Forced Multi-Agent

```text
Teacher Lead Agent + Multi-Skill（主智能体 + 多技能）

vs
```

### B.1 Submission 异步批改契约 Smoke Cases

这些 Case 不做复杂性能 Benchmark，只验证 01 中已经固定的 Submission 状态、重新提交和实时聊天框进度约束没有被实现破坏。

#### G-SUB-001：第一次提交与正常状态转换

第一次提交：

```text
不存在 Submission
↓
创建 Submission
↓
PENDING / QUEUED
↓
RUNNING
↓
SUCCEEDED / COMPLETED
```

必须满足：

```text
SUCCEEDED 前已成功写入当前有效 GradingResult
```

并且同一：

```text
student_id + question_id
```

只存在一个当前 Submission。

#### G-SUB-002：失败状态

OCR、Parsing 或模型调用发生不可恢复异常：

```text
RUNNING
↓
FAILED
```

必须保存可追踪的：

```text
error_code
error_message
```

FAILED 后允许学生重新提交，并复用同一 `submission_id`。

#### G-SUB-003：批改中禁止重复提交

构造：

```text

或
Submission.status = RUNNING
```

学生再次提交时必须：

```text
HTTP 409
code = SUBMISSION_GRADING_IN_PROGRESS
```

核心断言：

```text

不得启动新的 Grading Workflow
原 submission_id 保持不变
原 Workflow 继续执行
前端继续显示原批改进度
```

#### G-SUB-004：完成后复用同一 Submission 重新提交

构造：

```text
Submission.status = SUCCEEDED
submission_id = sub_10001
```

学生上传新图片后必须：

```text
submission_id 仍然 = sub_10001
image_url 更新
旧 OCRResult 删除
旧 GradingResult 删除
status → PENDING
current_stage → QUEUED
error_code / error_message → null
started_at / finished_at → null
```

然后重新启动一次完整 Workflow。

`FAILED` 后重新提交采用相同重置规则。

#### G-SUB-005：数学 current_stage 顺序

正常数学 Submission 阶段至少满足：

```text
↓

↓
PARSING
↓
GRADING
↓

↓
```

#### G-SUB-006：英语 current_stage 顺序

英语作文阶段同样为：

```text
↓
OCR
↓
PARSING
↓
GRADING
↓
ASSEMBLING_RESULT
↓
COMPLETED
```

#### G-SUB-007：SSE 实时进度事件

```text
grading.stage.completed
→ Event 必须包含 submission_id
```

```text
OCR

GRADING
ASSEMBLING_RESULT
```

```text
必须把 grading.* Event
```

同时禁止为了复用 DeerFlow 前端而把：

```text
PARSING
GRADING
```

伪装成 `AIMessage / reasoning / tool_calls`。

#### G-SUB-009：页面刷新恢复

当持久化 Submission 状态为：

```json
  "submission_id": "sub_10001",
  "status": "RUNNING",
```

```text
↓
读取 Submission.status / current_stage
↓
恢复已完成 / active / pending 步骤
↓
重新订阅 /api/submissions/sub_10001/events
```

不得因为刷新页面把进度重新显示为 `QUEUED`，也不得重新启动一次批改 Workflow。

后必须满足：

### English Essay

英语作文统一使用系统内置 `EnglishEssayRubricV1（英语作文评分标准 V1）`：

```text
Content（内容）                    0–5
Organization（组织结构与衔接）    0–5
Grammar（语法与句式）             0–5
Vocabulary（词汇）                0–5
Total（总分）                    20
```

需要评测：

```text
dimension_scores（多维评分）
evidence（按四维组织的评分证据）
feedback（反馈）
GradingResult Schema（批改结果结构）
```

#### G-ENG-001：固定 Rubric Contract

任意正常完成的英语作文 `GradingResult` 必须满足：

```text
dimension_scores
必须且只能包含：
content
organization
grammar
vocabulary

每项 max_score = 5
每项 score ∈ {0, 1, 2, 3, 4, 5}

score.max = 20

score.earned
=
content.score
+ organization.score
+ grammar.score
+ vocabulary.score

score.rate
=
score.earned / 20
```

`english_essay_detail.evidence` 必须按四个固定维度组织：

```text
content[]
organization[]
grammar[]
vocabulary[]
```

同时断言：

```text
Agent 1 使用 EnglishEssayRubricV1 提取四维证据
Agent 1 不直接打分
Agent 2 使用同一 EnglishEssayRubricV1 正式评分
不得从 Question 读取自定义 rubric
不得出现第五个自定义评分维度
```

维度缺失、额外维度、分数越界、`max_score != 5` 或总分加总不一致时，该 Contract Case 直接 FAIL。

核心指标：

```text
Total Score MAE（总分平均绝对误差）
Dimension Score MAE（评分维度平均绝对误差）
Evidence Grounding（证据支撑度）
Feedback Quality（反馈质量）
Rubric Contract Pass Rate（固定评分契约通过率）
```

英语模型路线固定为：

```text
Evidence Extraction
→ DeepSeek v4 Flash

Scoring + Feedback
→ DeepSeek v4 Flash
```

英语当前不进行 easy / medium / hard 模型路由。

学生侧评测的目标不是建立一个庞大的独立 Benchmark，而是保证：

```text
Teacher Agent 后续读取的业务事实
具有基本可信度
+
学生实时批改链路的核心工程约束
不会被后续实现破坏
```

## 最终评测闭环

```text
Question Authoring Smoke Evaluation（题目创建冒烟评测）
        ↓
Grading Smoke Evaluation（批改冒烟评测）
        ↓
Teacher Evaluation Snapshot Gate（教师评测快照门禁）
        ↓
Teacher Agent Core Cases（教师智能体核心用例）
        ↓
每个 Case 独立运行 5 次
        ↓
┌──────────────────────────────┐
│ Result Pass（结果是否正确）   │
│ Behavior Pass（行为是否正确） │
│ Quality Score（回答质量）     │
└──────────────────────────────┘
        ↓

+
Average Quality Score
+
All-Pass Rate
        ↓
Failed / Unstable Cases
        ↓
Trace + Diagnosis Agent
        ↓

        ↓
Fix → Regression（修复 → 回归）
```
