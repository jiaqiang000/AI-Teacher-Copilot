# AI Teacher Copilot：项目设计推进路线

## 推进原则

项目按 **8 个步骤**编号推进，其中 **Step 3–5 作为一个联合设计阶段统一完成**：先把业务事实和数据边界理清，再联合确定学习画像、长期个性化能力和 Teacher Agent Tools，之后再设计 Skills、Agent Memory 与 Multi-Agent。

---

## 1. 确定业务边界和核心对象

先明确系统中的核心对象：学生、教师、班级、作业、题目、提交记录、批改结果、知识点、错误类型。

需要回答：

- 学生如何提交作业？
- 一次作业如何定义？
- 一道题如何定义？
- 批改结果属于哪一次提交？
- 教师后续需要查询哪些业务信息？

**产出：业务对象图 + 一次完整业务流程。**

---

## 2. 定义单次批改结果的数据结构

明确一题经过完整 Grading Workflow 后最终产出什么，例如：

```text
score
correct
knowledge_points
error_types
reason
feedback
model
difficulty
```

这一步决定后续能否稳定进行学生画像、班级学情分析和 Teacher Agent 查询。

**产出：统一 `GradingResult` Schema。**

---

## 3–5. 联合设计数据基础、学习画像、长期个性化与 Teacher Agent Tools

Step 3、4、5 不再独立串行设计，而是作为一个整体联合确定。

核心依赖关系：

```text
MySQL 业务事实
      ↓
数据能力与学习画像
      ↓
画像算法与长期个性化
      ↓
Teacher Agent Tools
```

### 3. 数据基础与学习画像模型

确定 Teacher Copilot 后续能够使用的数据能力及其存储边界：

```text
MySQL 业务事实层
│
├── Student Profile（学生画像）
├── Class Profile（班级画像）
├── Homework Analysis（作业分析）
└── Question Analysis（题目分析）
```

其中：

```text
MySQL
= 唯一业务事实源

Redis
= Student Profile（学生画像）
+ Class Profile（班级画像）的可重算缓存

Homework Analysis（作业分析）
Question Analysis（题目分析）
= 基于 MySQL 指定范围即时聚合
```

同时确定：

- MySQL 事实表结构
- `knowledge_point（知识点）` 标准化
- `error_type（错误类型）` 标准化
- Student Profile（学生画像）Schema
- Class Profile（班级画像）Schema
- Homework Analysis（作业分析）Schema
- Question Analysis（题目分析）Schema
- MySQL / Redis / 即时计算边界

### 4. 学习画像算法与长期个性化

定义画像字段如何从 MySQL 中的历史 `GradingResult` 事实计算得到：

```text
performance（表现值）标准化
mastery（掌握度）
recent_performance（近期表现）
trend（学习趋势）
weak_point（薄弱知识点）
recurring_error（重复错误）
class aggregation（班级聚合）
```

长期个性化反馈由运行时上下文生成：

```text
Current GradingResult（当前批改结果）
        +
当前题 Knowledge Points（知识点）
        +
Student Profile（学生画像）相关部分
        +
Recurring Errors（重复错误）
        +
近期相关 Grading History（批改历史）
        ↓
Personalized Feedback Context
（个性化反馈上下文）
        ↓
LLM
        ↓
长期个性化反馈
```

### 5. Teacher Agent Tools

Teacher Agent 对业务数据和教学资源的访问统一通过 7 个核心 Tool：

```text
get_student_profile
get_student_grading_history
get_class_profile
get_homework_analysis
get_question_analysis
search_teaching_materials
search_question_bank
```

每个 Tool 统一明确：

- 作用
- 输入参数
- 输出结构
- 数据来源

Tool 按业务对象和能力边界划分，不按单个统计字段拆分。

**产出：数据能力模型 + Profile Schema + 画像算法 + 长期个性化上下文设计 + Teacher Agent Tool Contract。**

完整设计见：

`docs/03-05-teacher-intelligence-data-profile-tools.md`

---

## 6. 设计 Skills 和 Agent Memory

明确以下边界：

- 什么应该是 Skill？
- 什么应该进入 TencentDB Agent Memory？
- 什么必须保留在业务数据库中，不能进入 Memory 作为事实源？

例如：

```text
Skill
→ 班级学情分析 SOP
→ 学生诊断 SOP
→ 分层练习生成 SOP

Agent Memory
→ 教师偏好
→ 教学风格
→ 历史决策
→ 跨会话上下文
```

**产出：MySQL / Tool / Skill / Memory 边界表。**

---

## 7. 设计 Teacher Multi-Agent

在业务数据、Tools、Skills 和 Memory 边界明确之后，再决定 Teacher Copilot 如何拆分多个 Agent，例如：

```text
Supervisor
    ↓
├─ Learning Analyst
├─ Curriculum Agent
├─ Exercise Agent
└─ Reviewer（可选）
```

核心问题是：

> 为什么该任务需要多个专业 Agent 协作，而不是一次 LLM 调用？

需要明确每个 Agent：

- 职责
- 可使用的 Tools
- 可访问的数据
- 可使用的 Skills / Memory
- Agent 之间如何传递结果

**产出：Multi-Agent 架构图 + Agent 职责。**

---

## 8. 设计评测和工程实现

### 学生侧

```text
OCR
→ 小模型快速路径
→ 强模型 fallback
```

重点评测：

- OCR / 作答解析效果
- 批改准确率
- 过程分准确率
- 小模型路由准确率
- 强模型升级比例
- 成本与延迟

### 教师侧

```text
Agent Tool 调用正确率
学情分析准确性
Memory 命中率
Multi-Agent 成本 / 延迟
```

进一步评测 Teacher Agent 是否能够：

- 正确选择 Tool
- 正确读取学生与班级数据
- 基于事实进行学情分析
- 正确利用长期 Memory
- 在 Multi-Agent 协作中稳定完成复杂教学任务

**产出：最终技术架构 + 面试可讲的实验。**

---

## 整体依赖关系

```text
Step 1  业务边界与核心对象
   ↓
Step 2  GradingResult Schema
   ↓
Step 3–5  数据基础 + 学习画像 + 长期个性化 + Teacher Agent Tools
   ↓
Step 6  Skills + Agent Memory
   ↓
Step 7  Teacher Multi-Agent
   ↓
Step 8  评测与最终工程架构
```

核心原则：**先建立准确、可追溯的业务事实，再基于这些事实形成稳定的数据能力与 Tools，最后让 Agent 在这些能力之上进行查询、分析、规划和协作。**
