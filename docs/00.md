# AI Teacher Copilot：项目设计推进路线

## 推进原则

项目按 **8 个步骤**编号推进，其中 **Step 3–5 作为一个联合设计阶段统一完成**：先把业务事实和数据边界理清，再联合确定学习画像、长期个性化能力、Teacher Agent Tools 与 Skills，之后再设计 Agent Memory、Intent Routing 与 Multi-Agent。

---

## 1. 确定业务边界和核心对象

先明确系统中的核心对象：学生、教师、班级、作业、题目、提交记录、批改结果、知识点、错误类型。

需要回答：

- 学生如何提交作业？
- 一次作业如何定义？
- 一道题如何定义？
- 批改结果属于哪一次提交？
- 教师后续需要查询哪些业务信息？

**产出：业务对象图 + 一次完整业务流程。**

---

## 2. 定义单次批改结果的数据结构

明确一题经过完整 Grading Workflow 后最终产出什么，例如：

```text
score
correct
knowledge_points
error_types
reason
feedback
model
difficulty
```

这一步决定后续能否稳定进行学生画像、班级学情分析和 Teacher Agent 查询。

**产出：统一 `GradingResult` Schema。**

---

## 3–5. 联合设计数据基础、学习画像、长期个性化、Teacher Agent Tools 与 Skills

Step 3、4、5 不再独立串行设计，而是作为一个整体联合确定。

核心依赖关系：

```text
MySQL 业务事实
      ↓
数据能力与学习画像
      ↓
画像算法与长期个性化
      ↓
Teacher Agent Tools
      ↓
Teacher Agent Skills
```

### 3. 数据基础与学习画像模型

确定 Teacher Copilot 后续能够使用的数据能力及其存储边界：

```text
MySQL 业务事实层
│
├── Student Profile（学生画像）
├── Class Profile（班级画像）
├── Homework Analysis（作业分析）
└── Question Analysis（题目分析）
```

其中：

```text
MySQL
= 唯一业务事实源

Redis
= Student Profile（学生画像）
+ Class Profile（班级画像）的可重算缓存

Homework Analysis（作业分析）
Question Analysis（题目分析）
= 基于 MySQL 指定范围即时聚合
```

同时确定：

- MySQL 事实表结构
- `knowledge_point（知识点）` 标准化
- `error_type（错误类型）` 标准化
- Student Profile（学生画像）Schema
- Class Profile（班级画像）Schema
- Homework Analysis（作业分析）Schema
- Question Analysis（题目分析）Schema
- MySQL / Redis / 即时计算边界

### 4. 学习画像算法与长期个性化

定义画像字段如何从 MySQL 中的历史 `GradingResult` 事实计算得到：

```text
performance（表现值）标准化
mastery（掌握度）
recent_performance（近期表现）
trend（学习趋势）
weak_point（薄弱知识点）
recurring_error（重复错误）
class aggregation（班级聚合）
```

长期个性化反馈由运行时上下文生成：

```text
Current GradingResult（当前批改结果）
        +
当前题 Knowledge Points（知识点）
        +
Student Profile（学生画像）相关部分
        +
Recurring Errors（重复错误）
        +
近期相关 Grading History（批改历史）
        ↓
Personalized Feedback Context
（个性化反馈上下文）
        ↓
LLM
        ↓
长期个性化反馈
```

### 5. Teacher Agent Tools 与 Skills

Teacher Agent 完整能力规划包含 7 个核心 Tool：

```text
get_student_profile
get_student_grading_history
get_class_profile
get_homework_analysis
get_question_analysis
search_teaching_materials
search_question_bank
```

每个 Tool 统一明确：

- 作用
- Description
- Input Schema
- Output Schema
- 数据来源
- 权限边界
- 错误契约
- 测试

Tool 按业务对象和能力边界划分，不按单个统计字段拆分。

在 7 个 Tool 之上完整规划 5 个 Skill：

```text
诊断分析类
├── student-diagnosis（学生学习诊断）
├── class-learning-analysis（班级学情分析）
└── homework-review（作业讲评分析）

教学行动类
├── personalized-intervention（个性化教学干预）
└── differentiated-practice（分层练习设计）
```

5 个 Skill 形成完整的教师任务链路：

```text
发现问题
│
├── 学生学习诊断
├── 班级学情分析
└── 作业讲评分析
        ↓
采取行动
│
├── 个性化教学干预
└── 分层练习设计
```

当前阶段暂不建设 RAG / Teaching Knowledge Base（教学知识库），因此完整规划中的以下能力暂缓实现：

```text
Tool
└── search_teaching_materials（教学资料检索）

Skill
└── personalized-intervention（个性化教学干预）
    └── 依赖 search_teaching_materials
```

当前阶段实际实现范围为：

```text
6 个 Tool
+
4 个 Skill
```

上述两个能力的 Contract 与 SOP 继续保留在设计文档中，待后续引入 RAG / Teaching Knowledge Base 后再启用，不影响当前数据模型、题库检索和其余 Teacher Agent 能力实现。

Skill 不新增业务事实，也不重新实现数据查询逻辑，而是定义复杂教学任务中：

- 调用哪些 Tool
- Tool 调用顺序
- 事实验证规则
- 分析步骤
- 输出结构
- 失败与降级策略

**产出：数据能力模型 + Profile Schema + 画像算法 + 长期个性化上下文设计 + Teacher Agent Tool Contract + 5 个 Teacher Skill SOP（其中 1 个 Skill 本阶段暂缓实现）。**

完整设计见：

- `docs/03-05-teacher-intelligence-data-profile-tools.md`
- `docs/05-tool-skill.md`

## 6. 设计 Agent Memory（智能体记忆）

Agent Memory（智能体记忆）只保存需要跨会话长期保留、但不属于客观业务事实的信息，例如教师偏好、教学风格、历史教学决策和跨会话上下文。

核心边界：

```text
MySQL / Profile（画像）
= 客观业务事实与可重算学习状态

Agent Memory（智能体记忆）
= 教师长期偏好、教学风格、历史教学决策、跨会话上下文
```

学生分数、掌握度、薄弱知识点、作业完成率、题目错误率等事实仍必须通过 Tool（工具）从 MySQL / Profile 中读取，不能由 Memory 作为事实源。

**产出：Memory Schema（记忆结构）+ Memory Read / Write Flow（记忆读写流程）+ Memory 与业务事实边界。**

## 6.5 Intent Routing（意图识别与任务路由）

Intent Router（意图路由器）不设计复杂的意图标签体系，只负责判断当前教师请求应该走哪条执行路径：

```text
Teacher Request（教师请求）
        ↓
Intent Router（意图路由器）
        ↓
├── Direct Tool（直接工具）
│   简单事实查询
│
├── Single Skill（单技能）
│   一个完整教学任务
│
└── Composite Task（组合任务）
    多个教学任务需要协作
            ↓
       Multi-Agent（多智能体）
```

核心原则：

```text
能用一个 Tool 完成
→ 不进入 Skill

能用一个 Skill 完成
→ 不进入 Multi-Agent

只有多个独立教学任务需要协作
→ 才进入 Multi-Agent
```

**产出：Intent Routing Schema（意图路由结构）+ Tool / Skill / Multi-Agent 路由规则 + 典型请求测试集。**

## 7. 设计 Teacher Multi-Agent（教师多智能体）

Multi-Agent（多智能体）不是默认执行方式，只处理多个教学任务需要协作完成的复杂请求。

当前阶段 Agent 划分固定为：

```text
Teacher Supervisor
（教师主管智能体）
│
├── Learning Analysis Agent
│   （学习分析智能体）
│   ├── student-diagnosis（学生学习诊断）
│   ├── class-learning-analysis（班级学情分析）
│   └── homework-review（作业讲评分析）
│
└── Practice Agent
    （练习设计智能体）
    └── differentiated-practice（分层练习设计）
```

后续 RAG / Teaching Knowledge Base（教学知识库）完成后，再考虑增加 Teaching Intervention Agent（教学干预智能体）。

核心职责边界：

```text
Agent（智能体）
= 谁负责

Skill（技能）
= 一个教学任务怎么完成

Tool（工具）
= 真正查询 / 计算 / 检索数据
```

典型 Multi-Agent 场景：

```text
“分析这次作业，找到主要问题，然后给不同水平学生安排练习。”
        ↓
Teacher Supervisor
        ↓
Learning Analysis Agent
        ↓
homework-review
        ↓
结构化学习分析结果
        ↓
Practice Agent
        ↓
differentiated-practice
        ↓
分层练习方案
```

**产出：Multi-Agent 架构图 + Agent 职责 + Agent / Skill / Tool 边界 + Agent 间结构化结果传递协议。**

完整设计见：

- `docs/06-07-agent-memory-intent-routing-multi-agent.md`

## 8. 设计评测和工程实现

### 学生侧

```text
OCR
→ 小模型快速路径
→ 强模型 fallback
```

重点评测：

- OCR / 作答解析效果
- 批改准确率
- 过程分准确率
- 小模型路由准确率
- 强模型升级比例
- 成本与延迟

### 教师侧

```text
Agent Tool 调用正确率
Skill 执行正确率
学情分析准确性
Memory 命中率
Intent Routing 路由正确率
Multi-Agent 成本 / 延迟
```

进一步评测 Teacher Agent 是否能够：

- 正确选择 Tool
- 正确生成 Tool 参数
- 正确执行 Skill SOP
- 正确读取学生与班级数据
- 基于事实进行学情分析
- 正确利用长期 Memory
- 正确选择 Tool / Skill / Multi-Agent 执行路径
- 在 Multi-Agent 协作中稳定完成复杂教学任务

**产出：最终技术架构 + 面试可讲的实验。**

## 整体依赖关系

```text
Step 1  业务边界与核心对象
   ↓
Step 2  GradingResult Schema
   ↓
Step 3–5  数据基础 + 学习画像 + 长期个性化 + Teacher Agent Tools + Skills
   ↓
Step 6  Agent Memory（智能体记忆）
   ↓
Step 6.5  Intent Routing（意图识别与任务路由）
   ↓
Step 7  Teacher Multi-Agent（教师多智能体）
   ↓
Step 8  评测与最终工程架构
```

核心原则：**先建立准确、可追溯的业务事实，再基于这些事实形成稳定的数据能力与 Tools，通过 Skills 固化复杂教学任务流程；之后用 Memory 补充跨会话上下文，用 Intent Routing 选择最简单可完成任务的执行路径，只在复杂组合任务中启用 Multi-Agent。**
