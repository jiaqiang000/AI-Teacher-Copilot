# AI Teacher Copilot：项目设计推进路线

## 推进原则

项目按 **8 个步骤**编号推进，其中 **Step 3–5 作为一个联合设计阶段统一完成**：先把业务事实和数据边界理清，再联合确定学习画像、长期个性化能力、Teacher Agent Tools 与 Skills；Step 6–7 不再分别堆叠 Memory、Intent Router 和 Multi-Agent，而是以真实教师业务复杂度为驱动，设计 Teacher Lead Agent 从单 Tool、单 Skill、灵活 Tool / Skill 编排到按需 Multi-Agent 的完整执行体系。

---

## 1. 确定业务边界和核心对象

先明确系统中的核心业务对象：学生、教师、班级、作业、题目、题库题、当前提交、批改结果。

同时明确结构化诊断基础：Knowledge Point（知识点）与 Error Type（错误类型）标准分类。

需要回答：

- 教师如何创建和发布 Homework？
- Question 可以从哪些来源产生？
- 教师上传题目图片后如何形成 Question？
- `QuestionBankItem` 与 `Question` 的边界是什么？
- 数学 `difficulty` 在什么时候确定？
- 学生如何提交作业？
- 一次作业如何定义？
- 一道题如何定义？
- `Submission` 如何同时承载当前答案与当前批改状态？
- 同一学生同一道题什么时候允许重新提交？
- 后台异步批改如何把 OCR、解析、批改等阶段实时反馈到聊天框？
- 页面刷新后如何恢复当前批改进度？
- 教师后续需要查询哪些业务信息？

教师创建与发布作业关系固定为：

```text
Teacher
↓
创建 Homework
↓
status = DRAFT
↓
添加 Question
├── 手动输入题目
├── 上传题目图片 → OCR
└── 从 Question Bank 选择 QuestionBankItem
↓
数学自建题在创建阶段识别 difficulty
题库题直接复制已有 difficulty
↓
教师确认 / 调整题号
↓
Homework = PUBLISHED
↓
学生可见
```

题库题与实际作业题固定区分：

```text
QuestionBankItem
= 系统可复用题库资源

Question
= 某个 Homework 中真正布置出去的题

QuestionBankItem
↓ Copy
Question
```

当前学生提交与批改执行关系固定为：

```text
Submission（当前提交）
├── 当前答案
├── status
└── current_stage
        ↓
后台异步 Grading Workflow
        ├── OCR → OCRResult
        └── Math / English Grading
        ↓
GradingResult（当前有效结果）
```

其中：

- 同一 `student_id + question_id` 只保留一个当前 `Submission`。
- `Submission` 同时保存当前答案、`status`、`current_stage`、错误信息和批改时间字段，作为当前批改状态事实源。
- `PENDING / RUNNING` 时禁止再次提交；`SUCCEEDED / FAILED` 后允许复用同一 `Submission` 重新提交并重新批改。
- 重新提交被接受后更新 `image_url`，清除旧 `OCRResult / GradingResult`，将状态重置为 `PENDING / QUEUED` 后重新执行 Workflow。
- 用户体验仍然是提交后实时等待；后端不使用一个同步 HTTP 请求阻塞到所有 OCR / LLM 调用完成。
- 当前 MVP 使用轻量后台异步执行，不引入 Kafka / RabbitMQ / Celery 等复杂任务队列。
- 后台通过 `grading.*` SSE / Streaming Event 推送阶段变化；前端在 DeerFlow Chat 中实时展示 OCR、解析、批改和结果生成等步骤。
- 数学 `difficulty` 已在 Question 创建 / 加入 Homework 时确定；学生 Grading Workflow 只读取 `Question.difficulty` 做模型路由，不再重复判断。
- 因为同一学生同一道题在任意时刻最多只有一个运行中的 Workflow，所以不再使用 `GradingTask`、`Submission.version` 或 `submission_version` 解决版本竞争。

**产出：业务对象图 + 教师作业创建流程 + 学生提交与批改流程。**

## 2. 定义单次批改结果的数据结构

明确一题经过完整 Grading Workflow 后最终产出什么，例如：

```text
score
correct
knowledge_points
errors
reason
feedback
model
difficulty
```

当前模型路线统一为：

```text
Math Question Authoring
├── 教师自行创建数学题 → Qwen3.5-4B 预判 difficulty → 教师确认
└── 题库数学题 → 直接复制 QuestionBankItem.difficulty

Math Grading
├── 读取 Question.difficulty
├── easy / medium → Qwen3.5-4B
└── hard → DeepSeek v4 Flash

English Essay
├── Evidence Extraction → DeepSeek v4 Flash
└── Scoring + Feedback → DeepSeek v4 Flash
```

英语作文当前 `difficulty = null`，不进行 easy / medium / hard 模型路由。

英语作文统一采用系统内置 `EnglishEssayRubricV1（英语作文评分标准 V1）`：

```text
Content（内容）                    5 分
Organization（组织结构与衔接）    5 分
Grammar（语法与句式）             5 分
Vocabulary（词汇）                5 分
Total（总分）                    20 分
```

当前 MVP 中该 Rubric 固定由系统维护，教师不可自定义评分维度、维度权重或英语作文总分；英语作文 `Question.max_score` 固定为 `20`，`Question / QuestionBankItem` 不单独保存 Rubric 配置。

这一步决定后续能否稳定进行学生画像、班级学情分析和 Teacher Agent 查询。

**产出：统一 `GradingResult` Schema。**

## 3–5. 联合设计数据基础、学习画像、长期个性化、Teacher Agent Tools 与 Skills

Step 3、4、5 不再独立串行设计，而是作为一个整体联合确定。

核心依赖关系：

```text
MySQL 业务事实 / 标准字典 / 题库资源
      ↓
数据能力与学习画像
      ↓
画像算法与长期个性化
      ↓
Teacher Agent Tools
      ↓
Teacher Agent Skills
```

### 3. 数据基础与学习画像模型

确定 Teacher Copilot 后续能够使用的数据能力及其存储边界：

```text
MySQL
├── 业务事实
├── Knowledge Point / Error Type 标准字典
└── Question Bank（题库资源）
    ├── question_bank_item
    └── question_bank_item_knowledge_point

业务事实
│
├── Student Profile（学生画像）
├── Class Profile（班级画像）
├── Homework Analysis（作业分析）
└── Question Analysis（题目分析）
```

其中：

```text
MySQL
= 唯一业务事实源
+ 标准参考字典
+ 可复用题库资源

Redis
= Student Profile（学生画像）
+ Class Profile（班级画像）的可重算缓存

Homework Analysis（作业分析）
Question Analysis（题目分析）
= 基于 MySQL 当前有效事实按指定范围即时聚合
= 所有成绩、错误率、知识点表现、成绩分布和单次作业即时异常学生统一由 AnalysisCalculationV1 确定性计算
= 不由 LLM / Skill / Agent 临时计算或重新定义
```

同时确定：

- MySQL 事实表结构
- `QuestionBankItem` 与 Homework `Question` 的数据边界
- 题库题与标准 Knowledge Point Taxonomy 的关联方式
- Knowledge Point / Error Type 标准化体系：系统维护两级标准分类，批改模型从标准 `knowledge_point_key / error_code` 中选择，每条诊断同时保留 `raw_name / raw_type` 原始语义，未覆盖类型使用对应大类下的 `OTHER`，Profile / Analysis 统一基于标准 `key / code` 聚合
- Student Profile（学生画像）Schema
- Class Profile（班级画像）Schema
- Homework Analysis（作业分析）Schema
- Question Analysis（题目分析）Schema
- AnalysisCalculationV1 即时聚合规则
- MySQL / Redis / 即时计算边界

### 4. 学习画像算法与长期个性化

学习画像统一由确定性的 `ProfileAlgorithmV1` 计算，当前版本固定为：

```text
algorithm_version = profile_v1
```

三类输入职责明确分开：

```text
GradingResult.score.rate
→ 学生整体成绩 / 难度表现

diagnosis.knowledge_points[].performance
→ Knowledge Point mastery / recent_performance / trend / weak_point

diagnosis.errors[].error_code + knowledge_point_key
→ recurring_error / common_error
```

`ProfileAlgorithmV1` 的核心窗口与判断规则固定为：

```text
recent window   = 最近 14 天
previous window = 再往前 14 天
recurring error = 最近 28 天

performance
correct   → 1.0
partial   → 0.5
incorrect → 0.0

weak_point
attempt_count >= 3
AND mastery < 0.60

recurring_error
同一 (error_code, knowledge_point_key)
最近 28 天 occurrence_count >= 2
```

`mastery` 使用历史表现值 × 时间权重 × 难度权重的确定性加权公式；`trend` 使用 recent window 与 previous window 的差值判断。Class Profile 仍然直接基于 MySQL 当前有效事实聚合，不读取 Redis Student Profile 作为事实源。

所有完整公式、阈值、空值规则、班级聚合规则、排序规则与缓存失效规则只在以下文档维护，作为唯一权威定义：

- `docs/03-05-teacher-intelligence-data-profile-tools.md`

长期个性化反馈由运行时上下文生成：

```text
Current GradingResult（当前批改结果）
        +
当前题 Knowledge Points（知识点）
        +
Student Profile（学生画像）相关部分
        +
Recurring Errors（重复错误）
        +
近期相关 Grading History（批改历史）
        ↓
Personalized Feedback Context
（个性化反馈上下文）
        ↓
LLM
        ↓
长期个性化反馈
```

### 5. Teacher Agent Tools 与 Skills

Teacher Agent 完整能力规划包含 9 个核心 Tool：

```text
get_student_profile
get_student_grading_history
get_class_profile
list_class_students
list_class_homeworks
get_homework_analysis
get_question_analysis
search_teaching_materials
search_question_bank
```

其中两个对象发现 Tool 专门补齐真实业务范围获取：

```text
list_class_students
= 查询班级真实成员

list_class_homeworks
= 按班级 / 学科 / 时间范围查询作业列表
```

`search_question_bank` 统一查询独立 `QuestionBankItem` 资源，而不是把 Homework 中已经布置的 `Question` 当作题库。

每个 Tool 统一明确：

- 作用
- Description
- Input Schema
- Output Schema
- 数据来源
- 权限边界
- 错误契约
- 测试

Tool 按业务对象和能力边界划分，不按单个统计字段拆分。

在 9 个 Tool 之上完整规划 5 个 Skill：

```text
诊断分析类
├── student-diagnosis（学生学习诊断）
├── class-learning-analysis（班级学情分析）
└── homework-review（作业讲评分析）

教学行动类
├── personalized-intervention（个性化教学干预）
└── differentiated-practice（分层练习设计）
```

5 个 Skill 形成完整的教师任务链路：

```text
发现问题
│
├── 学生学习诊断
├── 班级学情分析
└── 作业讲评分析
        ↓
采取行动
│
├── 个性化教学干预
└── 分层练习设计
```

当前阶段暂不建设 RAG / Teaching Knowledge Base（教学知识库），因此完整规划中的以下能力暂缓实现：

```text
Tool
└── search_teaching_materials（教学资料检索）

Skill
└── personalized-intervention（个性化教学干预）
    └── 依赖 search_teaching_materials
```

当前阶段实际实现范围为：

```text
8 个 Tool
+
4 个 Skill
```

上述暂缓能力的 Contract 与 SOP 继续保留在设计文档中，待后续引入 RAG / Teaching Knowledge Base 后再启用，不影响当前数据模型、题库检索和其余 Teacher Agent 能力实现。

Skill 不新增业务事实，也不重新实现数据查询逻辑，而是定义复杂教学任务中：

- 调用哪些 Tool
- Tool 调用顺序
- 事实验证规则
- 分析步骤
- 输出结构
- 失败与降级策略

**产出：数据能力模型 + Question Bank 数据模型 + Profile Schema + 画像算法 + 长期个性化上下文设计 + Teacher Agent Tool Contract + 5 个 Teacher Skill SOP（其中 1 个 Skill 本阶段暂缓实现）。**

完整设计见：

- `docs/03-05-teacher-intelligence-data-profile-tools.md`
- `docs/05-tool-skill.md`

## 6–7. 业务驱动的 Teacher Agent、Memory 与 Multi-Agent

Step 6–7 合并设计，不再把 Agent Memory、Intent Routing 和 Multi-Agent 当成三个独立系统。

统一采用：

```text
Business-Driven（业务驱动）
+
Single-Agent First（单智能体优先）
```

系统只有一个教师侧主入口：

```text
Teacher
↓
Teacher Lead Agent（教师主智能体）
```

Teacher Lead Agent 根据真实业务复杂度动态选择执行方式：

```text
L1  明确事实 / 业务对象查询
→ Direct Tool（直接工具）

L2  已有标准教学任务
→ Single Skill（单技能）

L3  Skill 未命中，但多个 Tool 可以完成
→ Adaptive Multi-Tool（自主多工具）

L4  一个 Skill 完成主体，还需要额外 Tool
→ Skill + Tool

L5  多个教学任务存在明显串行依赖
→ Multi-Skill（多技能组合，仍由一个 Lead Agent 完成）

L6  大量独立对象可并行处理，或存在明显 Context Isolation（上下文隔离）收益
→ Parallel Sub-Agents（并行子智能体）

L7  大型高价值教学方案需要独立复核
→ Reviewer Agent（审核智能体）
```

Intent Routing（意图与任务路由）不单独设计为一个 Agent，而是 Teacher Lead Agent 的核心职责之一：判断当前业务请求应该使用 Tool、Skill、灵活编排，还是委派 Sub-Agent。

Multi-Agent 只在真实业务满足以下条件时启用：

```text
① Parallelism（任务可并行）
② Context Isolation（上下文隔离）
③ Independent Perspective（独立专业视角 / 审核）
```

因此以下任务仍然坚持单 Agent：

```text
单学生诊断
→ Lead Agent + student-diagnosis

普通作业讲评
→ Lead Agent + homework-review

作业分析 + 分层练习
→ Lead Agent 串行执行 homework-review + differentiated-practice
→ 不因为有两个 Skill 就强行拆成两个 Agent
```

当前真正的 Multi-Agent 核心业务为：

```text
班级周度学情复盘
        ↓
list_class_homeworks
        ↓
发现本周作业范围
        ↓
get_homework_analysis + get_class_profile
        ↓
Teacher Lead Agent 筛选重点学生
        ↓
Diagnosis Workers 并行深度诊断重点学生
        ↓
Fan-in（结果汇总）
        ↓
形成学生分层
        ↓
Practice Workers 并行生成分层 / 个性化练习
        ↓
Fan-in
        ↓
大型方案按需 Reviewer Agent 独立审核
        ↓
最终教学方案
```

全班个性化练习场景则先：

```text
list_class_students
↓
获得完整班级成员
↓
按学生批次 Fan-out Practice Workers
```

当前 Sub-Agent 类型：

```text
Diagnosis Worker（学习诊断子智能体）
→ 批量、并行执行 student-diagnosis

Practice Worker（练习设计子智能体）
→ 批量、并行生成分层 / 个性化练习

Reviewer Agent（审核智能体）
→ 只在大型高价值方案中按需独立审核
```

Agent / Skill / Tool 边界固定为：

```text
Agent
= 理解目标、动态决策、调用能力或执行边界清晰的专业任务

Skill
= 已验证、可复用的教学任务 SOP

Tool
= 真正查询、计算、检索或发现业务对象的原子能力
```

Agent Memory（智能体记忆）同样从真实业务产生，当前只保存：

```text
Teacher Preference（教师偏好）
Teaching Style（教学风格）
Teaching Decision（教学决策）
```

学生成绩、掌握度、薄弱知识点、作业完成率、题目错误率等业务事实仍必须通过 Tool 从 MySQL / Profile 中读取，Memory 不能成为事实源。

完整设计见：

- `docs/06-07-业务驱动的设计.md`

**产出：业务复杂度分层 + Teacher Lead Agent 能力边界 + Tool / Skill 灵活编排规则 + Multi-Agent 真实触发条件 + Diagnosis / Practice / Reviewer Sub-Agent 设计 + Memory 业务边界。**

## 8. 设计评测和工程实现

### 学生侧

```text
上传 / 重新提交
→ 创建 / 重置 Submission
→ PENDING / QUEUED
→ 后台异步执行
→ OCR
→ OCRResult
→ OCR Block 拼装
→ Math / English Workflow
→ GradingResult
→ Submission = SUCCEEDED / COMPLETED
```

模型路线：

```text
Math
├── 读取 Question.difficulty
├── easy / medium → Qwen3.5-4B
└── hard → DeepSeek v4 Flash

English Essay
└── DeepSeek v4 Flash 两阶段
    Evidence Extraction → Scoring + Feedback
```

实时体验：

```text
Submission / Grading Workflow
→ grading.* Progress Event
→ SSE / Streaming
→ GradingProgressAdapter / useGradingStream
→ DeerFlow Chat 中的 GradingProgressMessage
→ 完成后 GradingResultMessage
```

学生端继续使用 DeerFlow Chat 作为主要交互容器：

```text
复用：
├── Chat 页面 / Message Timeline
├── ChainOfThought 类步骤 UI primitives
└── Streaming / SSE 基础能力

新增：
├── GradingProgressAdapter / useGradingStream
├── GradingProgressMessage
└── GradingResultMessage
```

`OCR / PARSING / GRADING` 等是业务 Workflow 阶段，不伪装成 `AIMessage / reasoning / tool_calls`；前端只复用 DeerFlow 的聊天容器、步骤 UI 和流式基础能力。

重点评测：

- OCR / 作答解析效果
- 批改准确率
- 过程分准确率
- 数学 Question Authoring difficulty 判断准确率
- 数学 Grading 模型路由准确率
- 强模型升级比例
- `Submission` 状态与阶段转换正确性
- `PENDING / RUNNING` 时重复提交是否被拦截
- `SUCCEEDED / FAILED` 后同一 `Submission` 是否正确重置并重新批改
- SSE 实时聊天框进度与页面刷新恢复
- 成本与延迟

### 教师侧

```text
Agent Tool 调用正确率
Skill 执行正确率
学情分析准确性
Memory 使用正确率
执行方式选择正确率
Sub-Agent 委派正确率
Multi-Agent 成本 / 延迟收益
```

进一步评测 Teacher Lead Agent 是否能够：

- 正确选择 Tool
- 正确生成 Tool 参数
- 正确区分对象发现 Tool 与画像 / 分析 Tool
- 正确执行 Skill SOP
- Skill 未命中时合理组合多个 Tool
- 根据中间结果继续选择 Tool / Skill
- 正确读取学生与班级数据
- 基于事实进行学情分析
- 正确利用长期 Memory，而不把 Memory 当成业务事实源
- 在单 Agent 足够时不错误升级 Multi-Agent
- 在批量、可并行、上下文隔离收益明显的任务中正确 Fan-out Sub-Agent
- 正确汇总 Sub-Agent 结构化结果
- 大型教学方案中按需使用 Reviewer，而不是所有任务默认审核

**产出：最终技术架构 + 面试可讲的实验。**

## 整体依赖关系

```text
Step 1  业务边界与核心对象 + 教师作业创建 / Question Bank
   ↓
Step 2  GradingResult Schema
   ↓
Step 3–5  数据基础 + 学习画像 + 长期个性化 + Teacher Agent Tools + Skills
   ↓
Step 6–7  业务驱动的 Teacher Lead Agent + Memory + Tool / Skill 编排 + 按需 Multi-Agent
   ↓

```

核心原则：**先建立准确、可追溯的业务事实，再形成稳定的数据能力、Tools 与 Skills；教师先通过 `Homework DRAFT → Question → PUBLISHED` 完成作业创建，`QuestionBankItem` 只作为可复用题库资源，加入作业时复制成独立 `Question`；数学 difficulty 在 Question 创建阶段确定，学生批改链路只读取该属性进行模型路由。学生批改链路由 `Submission` 统一保存当前答案与当前批改状态，后台使用轻量异步 Workflow，通过 SSE 将 OCR、解析、批改等阶段实时展示在 DeerFlow Chat 中；批改进行中禁止重复提交，因此不再需要独立 `GradingTask` 和提交版本竞争机制。Teacher Lead Agent 默认以最简单的单 Agent 路径完成任务，先通过对象发现 Tool 获取真实学生 / 作业范围，只有在真实班级级业务出现可并行、上下文隔离或独立审核收益时，才动态升级为 Multi-Agent。**
